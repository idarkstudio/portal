# Mejores prácticas de seguridad: llamadas salientes HTTPS

<MarkdownChipRow labels={["Seguridad", "Mejores prácticas"]} />

## No almacenes datos sensibles como claves de API en los canisters

### Preocupación de seguridad

Los datos sensibles son un término amplio que varía según la lógica y el
comportamiento de tu aplicación. Aquí tienes una lista no exhaustiva de secretos
que generalmente se consideran sensibles, como claves de API o tokens:

- Secretos que permiten la interacción con puntos finales no públicos.
- Secretos que permiten consultar o modificar puntos finales con datos
  confidenciales.
- Tokens de API que tienen un costo.

Por defecto, los datos almacenados dentro de tu canister no están encriptados.
Por lo tanto, si tu canister se instala en una réplica maliciosa, puede
recuperar y robar tus claves, tokens y secretos en texto plano.

### Recomendación

Asegúrate de no almacenar datos sensibles dentro de tu canister.

[Más información.](/docs/references/https-outcalls-how-it-works#compromised-replicas)

[Recomendaciones de seguridad para la confidencialidad de datos.](/docs/building-apps/security/misc#data-confidentiality-on-the-internet-computer)

## Asegúrate de que tus canisters tengan una cuota suficientemente grande con el servidor HTTP

### Preocupación de seguridad

Cuando se realiza una llamada saliente HTTPS, se amplifica por el número de
réplicas en la subred. El servidor web de destino recibirá no solo una
solicitud, sino tantas solicitudes como el número de nodos en la subred.

La mayoría de los servidores web implementan algún tipo de límite de velocidad;
este es un mecanismo utilizado para restringir el número de solicitudes que un
cliente puede realizar a un servidor web dentro de un período de tiempo
específico, evitando el abuso o el uso excesivo de sus API.

### Recomendación

Debes tener en cuenta estos límites de velocidad al diseñar e implementar tus
canisters. Los límites de velocidad se aplican utilizando diferentes
granularidades de tiempo, por ejemplo, segundos o minutos. Para la aplicación de
límites de velocidad a nivel de segundo, asegúrate de que las solicitudes
simultáneas de todas las réplicas de la subred no violen la cuota. Las
violaciones pueden llevar a prohibiciones temporales o permanentes.

[Más información.](/docs/references/https-outcalls-how-it-works#rate-limiting-by-servers)

## Realiza solicitudes salientes HTTPS solo a puntos finales idempotentes

### Preocupación de seguridad

Como se mencionó anteriormente, si se realiza una llamada saliente HTTPS, se
amplifica por el número de réplicas en la subred. Esto significa que el punto
final consultado recibirá la misma solicitud varias veces. Esto es especialmente
arriesgado en solicitudes que cambian el estado del punto final, dado que una
llamada saliente HTTPS podría llevar a cambiar el estado del punto final de
manera no intencionada varias veces.

### Recomendación

Asegúrate de que los puntos finales llamados por una llamada saliente HTTPS sean
idempotentes, de modo que el punto final consultado tenga el mismo
comportamiento con la misma carga útil de solicitud, sin importar el número de
veces que se llame.

Algunos servidores admiten el uso de claves de idempotencia. Estas claves son
cadenas únicas aleatorias enviadas en la solicitud HTTP como encabezados. Si se
utilizan con la función de llamadas salientes HTTPS, todas las solicitudes
enviadas por cada réplica honesta contendrán la misma clave de idempotencia.
Esto permite que el servidor reconozca las solicitudes duplicadas (es decir,
solicitudes con la misma clave de idempotencia), maneje solo una y modifique el
estado del servidor solo una vez. Ten en cuenta que esta es una función que debe
ser compatible con el servidor.

[Más información.](/docs/references/https-outcalls-how-it-works#post-requests-must-be-idempotent)

## Asegúrate de que las respuestas HTTPS sean idénticas

### Preocupación de seguridad

Cuando las réplicas de una subred reciben respuestas HTTP, estas respuestas
deben ser idénticas. De lo contrario, no se logrará el consenso y la respuesta
HTTP será rechazada pero aún se cobrará.

### Recomendación

Asegúrate de que las respuestas HTTP enviadas a la capa de consenso sean
idénticas.

Idealmente, las respuestas HTTP devueltas por el punto final consultado siempre
serían las mismas. Sin embargo, la mayoría de las veces esto no es posible de
controlar y las respuestas incluyen datos aleatorios (por ejemplo, la respuesta
incluye marcas de tiempo, valores de cookies o algún tipo de identificadores).
En esos casos, asegúrate de utilizar las
[funciones de transformación](/docs/references/https-outcalls-how-it-works#transformation-function)
para garantizar que las respuestas recibidas por cada réplica sean idénticas al
eliminar cualquier dato aleatorio o extraer solo los datos relevantes.

Esto se aplica al cuerpo y a los encabezados de la respuesta HTTP. A menudo se
pasa por alto los encabezados de respuesta y esto lleva a fallos debido a un
consenso fallido.

[Más información.](/docs/references/https-outcalls-how-it-works#responses-must-be-similar)

## Ten en cuenta los tamaños de las solicitudes y respuestas HTTP

### Preocupación de seguridad

El [precio](/docs/references/https-outcalls-how-it-works#pricing) de las
llamadas salientes HTTPS se determina por el tamaño de la solicitud HTTP y el
tamaño máximo de la respuesta, entre otras variables. Por lo tanto, si se
realizan solicitudes grandes, esto podría agotar rápidamente el saldo de ciclos
del canister. Esto puede ser arriesgado en escenarios donde las llamadas
salientes HTTPS se desencadenan por acciones del usuario (en lugar de una
invocación de latido o temporizador).

### Recomendación

Al utilizar llamadas salientes HTTPS, ten en cuenta los tamaños de las
solicitudes y respuestas HTTP. Asegúrate de que el tamaño de la solicitud
emitida y el tamaño de la respuesta HTTP que proviene del servidor sean
razonables.

Cuando se realiza una llamada saliente HTTPS, es posible y muy recomendable
definir el parámetro `max_response_bytes`, que te permite establecer el tamaño
máximo permitido de la respuesta. Si este parámetro no está definido, se
establece de forma predeterminada en el límite de tamaño de respuesta duro de la
función de llamadas salientes HTTPS, que es de 2 MiB. El costo de ciclos de la
respuesta siempre se cobra en función de `max_response_bytes` o 2 MB si no se
establece.

Por último, ten en cuenta que los usuarios pueden incurrir en costos de ciclos
por las llamadas salientes HTTPS en caso de que estas llamadas puedan ser
desencadenadas por acciones del usuario.

[Más información.](/docs/references/https-outcalls-how-it-works#recipe-for-coding-a-canister-http-call)

## Realiza validación de entrada en las llamadas salientes HTTPS

### Preocupación de seguridad

Las llamadas salientes HTTPS que utilizan datos enviados por el usuario son
susceptibles a varios ataques de inyección. Esto puede llevar a varios
problemas, como los mencionados anteriormente.

### Recomendación

Realiza validación de entrada al utilizar datos enviados por el usuario en las
llamadas salientes HTTPS.

[Más información.](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html)
