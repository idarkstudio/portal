## Confidencialidad de datos en ICP

### Problema de seguridad

Al almacenar datos en ICP, existen dos niveles de acceso a los datos.

1. Los nodos pueden leer todos los datos almacenados en una subred. Esto incluye
   todos  
   los mensajes enviados hacia o desde un canister, junto con todos los datos
   almacenados  
   en un canister. Esto significa que un nodo podría extraer todos los datos
   disponibles  
   para un canister. Esto cambiará con la implementación de seguridad basada en
   TEE para los nodos.

2. Los clientes finales solo pueden acceder a los datos que los nodos y
   canisters hayan  
   puesto a su disposición. Si los nodos de la subred no se comportan mal y no
   filtran datos,  
   los clientes solo pueden leer las respuestas a los mensajes de ingreso y
   consultas que  
   ellos mismos han enviado. El canister decide qué datos se exponen al cliente.

La información parcial de los datos almacenados en el árbol de estado de la
subred siempre  
se filtrará. Por lo tanto, los datos con valores de baja entropía pueden
filtrarse por completo  
y quedar completamente expuestos, como un valor Booleano que solo puede ser
"True" o "False".  
La filtración de datos con alta entropía es despreciable.

Existen dos tipos de datos relacionados con el usuario que pueden almacenarse en
el  
árbol de estado de la subred. El primero es cuando un usuario envía un mensaje
de ingreso  
a un canister; el hash del mensaje y la respuesta se almacenan en el árbol de
estado de la  
subred para ser recuperados de forma segura por el cliente. El mensaje de
ingreso debe  
contener un nonce de alta entropía que es implementado por el agente y
normalmente no se  
expone al usuario. La respuesta del mensaje es determinada por el canister y
puede que  
no contenga un valor de alta entropía. Si la respuesta del canister consiste en
un valor  
de baja entropía, entonces los datos pueden filtrarse a usuarios que no sean el
emisor  
del mensaje de ingreso.

El segundo tipo de datos relacionados con el usuario son las variables
certificadas  
mantenidas por un canister que también se exponen a través del árbol de estado
de la subred.  
Si un canister coloca datos de baja entropía en el árbol de estado, estos datos
pueden filtrarse  
a usuarios que no deberían tener acceso a ellos.

### Recomendación

Para los desarrolladores que necesiten proteger la confidencialidad de sus datos
contra  
usuarios externos, deben asegurarse de que los datos en el árbol de estado de la
subred  
tengan un nivel suficiente de entropía. Se recomienda un mínimo de 128 bits. Si
los datos no  
tienen suficiente entropía por sí solos, entonces se recomienda agregar algunos
datos  
artificiales usando aleatoriedad.

En particular, un canister puede asegurarse de que las respuestas a los mensajes
de ingreso  
no filtren datos a usuarios externos (que no sean el remitente) incluyendo datos
de alta  
entropía en la respuesta. O, un canister puede asegurarse de que los datos en
las variables  
certificadas no se filtren agregando datos de alta entropía a las variables que
deben  
mantenerse confidenciales.

Además, al igual que las respuestas de los mensajes de ingreso, las secciones
personalizadas  
privadas del canister que contengan datos de baja entropía podrían filtrarse a
usuarios  
no autorizados. Por lo tanto, se debe usar un nivel suficiente de entropía para
las secciones  
personalizadas privadas del canister. Se recomienda un mínimo de 128 bits. Si
los datos no  
tienen suficiente entropía por sí solos, entonces se recomienda agregar algunos
datos  
artificiales usando aleatoriedad.

## Uso de aleatoriedad segura en canisters

Los desarrolladores de canisters a menudo requieren acceso a aleatoriedad segura
en sus  
canisters para realizar ciertas operaciones. Los requisitos para una fuente
segura de  
aleatoriedad incluyen:

- **Imparcialidad:** El valor no debe estar influenciado por nadie.
- **Impredecibilidad:** El valor debe ser desconocido para todos antes de
  generarse.

ICP expone la API del sistema  
[`raw_rand`](/docs/references/ic-interface-spec#ic-raw_rand) para este
propósito  
específico, la cual no acepta entrada alguna y retorna 32 bytes de
aleatoriedad  
criptográficamente segura. Las garantías de aleatoriedad segura de `raw_rand` se
logran  
gracias a las propiedades criptográficas del  
[RandomTape](https://internetcomputer.org/how-it-works/execution-layer/#random-number-generation).  
Siempre se recomienda usar `raw_rand` como fuente de aleatoriedad en canisters
y  
**evitar** el uso de otras fuentes con baja entropía, como el tiempo actual.

Para ilustrar el uso de `raw_rand`, se pueden encontrar a continuación dos
ejemplos  
en Motoko y Rust, incluyendo sus beneficios y advertencias.

### 1. Uso directo de `raw_rand` como generador de números aleatorios

En este ejemplo de Motoko, el canister proporciona el tamaño solicitado de bytes
aleatorios  
mediante la llamada a `raw_rand`. Sin embargo, solo puede generar 32 bytes de
aleatoriedad  
segura en un solo mensaje, por lo que se requieren llamadas subsiguientes a la
API del sistema  
para llenar el tamaño solicitado.

```motoko
import Random "mo:base/Random";
import Array "mo:base/Array";

actor Randomness {
  public func random_bytes(n : Nat) : async [Nat8] {
    let byteArray : [var Nat8] = Array.init<Nat8>(n, 0);
    let entropy = await Random.blob();
    var f = Random.Finite(entropy);
    var i = 0;
    loop {
      if (i == n) {
        return Array.freeze<Nat8>(byteArray);
      } else {
        switch (f.byte()) {
          case (?byte) {
            byteArray[i] := byte;
            i := i + 1;
          };
          case null {
            let entropy = await Random.blob();
            f := Random.Finite(entropy);
          };
        };
      };
    };
  };
};
```

#### Beneficios:

- Los bytes aleatorios están garantizados como seguros.

#### Advertencias:

- El método no escala bien cuando se solicita una gran cantidad de bytes
  aleatorios, ya que  
  se debe llamar a `raw_rand` por cada 32 bytes.

### 2. Usar `raw_rand` como semilla para un generador de números pseudoaleatorios (PRNG)

En este ejemplo en Rust, usamos la salida de `raw_rand` como semilla en un PRNG
conocido  
como ChaCha20 en los hooks de `init` y `post_upgrade`, y generamos aleatoriedad
llamando  
al método `random_bytes`.

```rust
use candid::{CandidType, Principal};
use rand_chacha::rand_core::{RngCore, SeedableRng};
use rand_chacha::ChaCha20Rng;
use std::cell::RefCell;
use std::time::Duration;

thread_local! {
    static RNG: RefCell<Option<ChaCha20Rng>> = RefCell::new(None);
}

const SEEDING_INTERVAL: Duration = Duration::from_secs(3600);

#[derive(CandidType)]
enum RngError {
    RngNotInitialized(String),
}

type RandomBytesResult = Result<String, RngError>;

async fn seed_randomness() {
    let (seed,): ([u8; 32],) = ic_cdk::call(Principal::management_canister(), "raw_rand", ())
        .await
        .expect("Failed to call the management canister");
    RNG.with_borrow_mut(|rng| *rng = Some(ChaCha20Rng::from_seed(seed)));
}

fn schedule_seeding(duration: Duration) {
    ic_cdk_timers::set_timer(duration, || {
        ic_cdk::spawn(async {
            seed_randomness().await;
            // Schedule reseeding on a timer with duration SEEDING_INTERVAL
            schedule_seeding(SEEDING_INTERVAL);
        })
    });
}

#[ic_cdk::init]
fn init() {
    // Initialize randomness during canister install or reinstall
    schedule_seeding(Duration::ZERO);
}

#[ic_cdk::post_upgrade]
fn post_upgrade() {
    // Initialize randomness after a canister upgrade
    schedule_seeding(Duration::ZERO);
}

// This must always be an update method or the PRNG state won't be updated
#[ic_cdk::update]
fn random_bytes(size: u32) -> RandomBytesResult {
    let mut buf = vec![0; size as usize];
    RNG.with_borrow_mut(|rng| match rng.as_mut() {
        Some(rand) => {
            rand.fill_bytes(&mut buf);
            Ok(hex::encode(buf))
        }
        None => Err(RngError::RngNotInitialized(
            "Randomness is not initialized. Please try again later".to_string(),
        )),
    })
}
```

#### Beneficios:

- Este método escala para grandes cantidades de bytes aleatorios, ya que
  `raw_rand` necesita  
  ser llamado solo una vez, y el cálculo posterior del PRNG es local al
  canister.

#### Advertencias:

- `setup_randomness` debe **siempre** ser inicializado tanto en el hook `init`
  como en el  
  `post_upgrade`, ya que `init`  
  [no se invoca durante una actualización del canister](/docs/references/ic-interface-spec#system-api-upgrades).
- Los métodos `init` y `post_upgrade` no permiten llamadas async, por lo que se
  programa un  
  temporizador inmediatamente para inicializar la semilla de aleatoriedad.
- Una vez que se ha inicializado la semilla, el resultado de todas las llamadas
  futuras a  
  `random_bytes` será predecible para cualquiera que tenga la semilla
  (proveedores de nodos),  
  ya que el PRNG es determinista. Esto rompe la propiedad de imprevisibilidad de
  la aleatoriedad  
  segura. Por lo tanto, para equilibrar seguridad y rendimiento, se recomienda
  volver a sembrar  
  frecuentemente el PRNG mediante un temporizador. El ejemplo anterior ya hace
  esto con una  
  duración de **1 hora**. Sin embargo, dependiendo de la sensibilidad de su
  dapp, los  
  desarrolladores pueden elegir un intervalo de resiembra apropiado configurando
  `SEEDING_INTERVAL`.
- `random_bytes` debe ser **siempre** un método `update`, para que el PRNG
  pueda  
  preservar el estado y ofrecer aleatoriedad única en cada solicitud.

## Prueba tu código de canister incluso con llamadas a la API del sistema

### Problema de seguridad

Dado que los canisters interactúan con la API del sistema, es más difícil probar
el código  
porque las pruebas unitarias no pueden llamar a la API del sistema. Esto puede
llevar a una  
falta de pruebas unitarias.

### Recomendación

- Crea módulos poco acoplados que no dependan de la API del sistema y realiza
  pruebas unitarias  
  sobre ellos. Consulta esta  
  [recomendación](https://mmapped.blog/posts/01-effective-rust-canisters.html#target-independent)  
  (de  
  [effective Rust canisters](https://mmapped.blog/posts/01-effective-rust-canisters.html)).

- Para las partes que aún interactúan con la API del sistema, crea una
  abstracción ligera de la  
  API del sistema que sea simulada en las pruebas unitarias. Consulta la  
  [recomendación](https://mmapped.blog/posts/01-effective-rust-canisters.html#target-independent)  
  (de  
  [effective Rust canisters](https://mmapped.blog/posts/01-effective-rust-canisters.html)).  
  Por ejemplo, se puede implementar un ‘Runtime’ como el siguiente y luego
  usar  
  ‘MockRuntime’ en las pruebas (código de Dimitris Sarlis):

```rust
use ic_cdk::api::{
    call::call, caller, data_certificate, id, print, time, trap,
};

#[async_trait]
pub trait Runtime {
    fn caller(&self) -> Result<Principal, String>;
    fn id(&self) -> Principal;
    fn time(&self) -> u64;
    fn trap(&self, message: &str) -> !;
    fn print(&self, message: &str);
    fn data_certificate(&self) -> Option<Vec<u8>>;
    (...)
}

#[async_trait]
impl Runtime for RuntimeImpl {
    fn caller(&self) -> Result<Principal, String> {
        let caller = caller();
        // The anonymous principal is not allowed to interact with the canister.
        if caller == Principal::anonymous() {
            Err(String::from(
                "Anonymous principal not allowed to make calls.",
            ))
        } else {
            Ok(caller)
        }
    }

    fn id(&self) -> Principal {
        id()
    }

    fn time(&self) -> u64 {
        time()
    }

    (...)

}

pub struct MockRuntime {
    pub caller: Principal,
    pub canister_id: Principal,
    pub time: u64,
    (...)
}

#[async_trait]
impl Runtime for MockRuntime {
    fn caller(&self) -> Result<Principal, String> {
        Ok(self.caller)
    }

    fn id(&self) -> Principal {
        self.canister_id
    }

    fn time(&self) -> u64 {
        self.time
    }

    (...)

}
```

## Haz que las compilaciones del canister sean reproducibles

### Problema de seguridad

Debe ser posible verificar que un canister hace lo que dice hacer. ICP  
proporciona un hash SHA256 del módulo WASM desplegado. Para que esto sea útil,  
la compilación del canister debe ser reproducible.

### Recomendación

Haz que las compilaciones del canister sean reproducibles. Consulta esta  
[recomendación](https://mmapped.blog/posts/01-effective-rust-canisters.html#reproducible-builds)  
(de  
[effective Rust canisters](https://mmapped.blog/posts/01-effective-rust-canisters.html)).  
Consulta también la  
[documentación para desarrolladores al respecto](/docs/building-apps/best-practices/reproducible-builds).

## No confíes en que el tiempo sea estrictamente monotónico

### Problema de seguridad

El tiempo leído desde la API del sistema es monotónico pero no estrictamente  
monotónico. Por lo tanto, dos llamadas consecutivas pueden devolver el mismo  
tiempo, lo cual podría causar errores de seguridad cuando se utiliza la API de  
tiempo.

### Recomendación

Consulta la sección "Time is not strictly monotonic" en  
[How to audit an ICP canister](https://www.joachim-breitner.de/blog/788-How_to_audit_an_Internet_Computer_canister).

## Rust: Evita la aritmética de punto flotante para información financiera

### Problema de seguridad

Los números flotantes en Rust pueden comportarse de forma inesperada. Puede  
haber pérdida de precisión no deseada en ciertas circunstancias. Al dividir
por  
cero, el resultado podría ser `-inf`, `inf` o `NaN`. Al convertir a entero,  
esto puede llevar a resultados inesperados. (No existe `checked_div` para  
números flotantes.)

### Recomendación

Usa
[`rust_decimal::Decimal`](https://docs.rs/rust_decimal/latest/rust_decimal/)  
o [`num_rational::Ratio`](https://docs.rs/num-rational/latest/num_rational/).  
Decimal usa una representación de punto fijo con denominadores en base 10, y  
Ratio representa números racionales. Ambos implementan `checked_div` para  
manejar la división por cero, cosa que no está disponible con floats. Números  
de uso común como 0.1 y 0.2 pueden representarse de forma más intuitiva con  
Decimal y exactamente con Ratio. Rarezas de redondeo como `0.1 + 0.2 != 0.3`,  
que ocurren con floats en Rust, no suceden con Decimal  
(ver https://0.30000000000000004.com/). Con Ratio, se puede establecer de
forma  
explícita la precisión deseada. Con Decimal o Ratio, aunque aún es necesario  
gestionar la precisión, todo lo anterior hace que la aritmética sea más fácil  
de razonar.
