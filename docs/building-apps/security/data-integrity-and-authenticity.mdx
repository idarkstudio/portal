## Variables certificadas

### Preocupación de seguridad

ICP ofrece tres modos de operación para los canisters: `update`, `query` y
`composite_query`. Por simplicidad, agruparemos `composite_query` bajo consultas
para el resto de esta sección. Para obtener más información, consulta la
[descripción detallada entre las llamadas `update` y `query`](/docs/building-apps/interact-with-canisters/query-calls).

Las llamadas de actualización son lentas y costosas, pero proporcionan garantías
de integridad, ya que sus respuestas incluyen una firma de umbral firmada por la
subred.

Por otro lado, las llamadas de consulta son rápidas, ya que una sola réplica
formula la respuesta, pero **no hay garantía de integridad, ya que la respuesta
puede ser manipulada por una sola réplica o nodo límite**. Por ejemplo, si la
aplicación NNS obtiene información de propuestas del canister de gobernanza a
través de llamadas de consulta y el nodo que responde es malicioso, puede
enmascarar una propuesta malintencionada que cause daño irrevocable como inocua
modificando la carga útil de la propuesta en la respuesta y engañar a los
votantes para que voten sí. Otra consecuencia de las llamadas de consulta es que
los usuarios no pueden confiar en
[canister_inspect_message](/docs/building-apps/security/iam) como una
protección. **Esto hace que las llamadas de consulta, en su forma original, no
sean adecuadas para servir datos para aplicaciones críticas de seguridad.**

### Uso de variables certificadas para consultas seguras

En ciertos casos de uso, hay una tercera opción en la que los resultados de la
consulta pueden devolver datos que han sido certificados por la subred en una
llamada de actualización anterior. Este es el concepto de datos certificados y
requiere cambios en la llamada de actualización para crear la certificación, la
llamada de consulta para devolver el certificado y el frontend para verificar el
certificado. El uso de datos certificados proporciona lo mejor de ambos mundos
con tiempos de respuesta similares a las consultas y respuestas certificadas
similares a las actualizaciones. Esto forma el núcleo de las
[variables certificadas](/docs/tutorials/developer-liftoff/level-2/2.2-advanced-canister-calls#certified-variables).

Algunos ejemplos de variables certificadas son la certificación de activos en
[Internet Identity](https://github.com/dfinity/internet-identity/blob/b29a6f68bbe5a49d048e12bc7a3263a9f43d080b/src/internet_identity/src/main.rs#L775-L808),
[NNS dapp](https://github.com/dfinity/nns-dapp/blob/372c3562127d70c2fde059bc9c268e8ae858583e/rs/src/assets.rs#L121-L145)
o la implementación de firma de canister en Internet
Identity](https://github.com/dfinity/internet-identity/blob/main/src/internet_identity/src/signature_map.rs).

:::tip

Las variables certificadas son una característica avanzada que requiere una
implementación cuidadosa de estructuras de datos autenticadas y verificación en
los lados del canister y del cliente, respectivamente. **Si el cliente no
requiere tiempos de respuesta rápidos, llama al método de consulta como una
llamada de actualización (consulta replicada).** La respuesta sería certificada
por la subred y un solo nodo malicioso o límite no puede modificar la respuesta.

:::

:::tip

ICP también proporciona consultas firmadas por réplicas, donde las respuestas de
consulta están firmadas por el nodo réplica que responde; sin embargo, no tiene
las mismas garantías de seguridad que una llamada de `actualización` y solo
protege de nodos límite maliciosos. Las consultas firmadas por réplicas están
habilitadas de forma predeterminada tanto en el
[agente ICP Rust](https://docs.rs/ic-agent/latest/ic_agent/) como en el
[agente ICP JavaScript](https://www.npmjs.com/package/@dfinity/agent).
[Lee más sobre la función](https://internetcomputer.org/blog/features/replica-signed-queries).

:::

### ¿Qué son los datos certificados?

Además de las llamadas de actualización, la subred certifica (crea una firma de
umbral) una parte de los datos del canister en cada ronda. Esto se almacena en
el árbol de estado con la etiqueta `certified_data`. Sin embargo, dado que se
certifica en cada ronda, la cantidad de datos que se pueden almacenar en
`certified_data` está limitada a 32 bytes. Por lo tanto, cuando modificas el
estado de tu canister durante una llamada de actualización, si puedes convertir
el estado en una representación única que quepa en 32 bytes, puedes almacenarlo
en `certified_data` y se certificará. Naturalmente, esto se puede hacer
calculando un hash de la estructura de datos del estado del canister. Por eso,
las variables certificadas son difíciles de implementar. Dependiendo de tus
estructuras de datos, deberás desarrollar un tipo diferente de función de hash.

Las llamadas de consulta posteriores pueden devolver los datos tal cual,
incluida la firma en los `certified_data`, que el frontend puede verificar con
la clave pública raíz de IC. Esto significa que no se pueden realizar
agregaciones de datos u otros cálculos en las llamadas de consulta, ya que no
habría forma de producir una firma sobre esos datos recién creados. Hay dos
soluciones alternativas: o bien estos datos se calculan previamente en la
llamada de actualización o se envían todos los datos en bruto al frontend, que
los verifica y realiza los cálculos. Combinando estas características, un
canister debería poder certificar una variable en una respuesta de consulta con
este
[diseño](https://medium.com/dfinity/how-internet-computer-responses-are-certified-as-authentic-2ff1bb1ea659).

A alto nivel, en tu canister:

1. Elige una
   [estructura de datos autenticada](https://cs.brown.edu/research/pubs/pdfs/2003/Tamassia-2003-ADS.pdf)
   como árboles de Merkle para almacenar un valor en la memoria del canister.
2. En la **llamada de actualización**,
   - Realiza el cálculo y almacena el resultado en el árbol de Merkle.
   - La ruta de búsqueda para el resultado debe actuar como su `clave`.
     Idealmente, esta `clave` debería ser los parámetros proporcionados por el
     llamante en el método de consulta.
   - Vuelve a calcular la prueba de Merkle (`root_hash`).
   - Almacena el `root_hash` como los datos certificados del canister.
   - Devuelve la `clave` como respuesta.
3. En la **llamada de consulta**,
   - Obtén el resultado de la estructura de Merkle utilizando los parámetros de
     consulta como la ruta de búsqueda.
   - Obtén los `certified_data` actuales del canister.
   - Calcula el testigo para el resultado utilizando la misma ruta de búsqueda.
     El testigo de Merkle proporciona una prueba de inclusión de que el
     resultado solicitado existe en el árbol de Merkle bajo la ruta dada.
   - Devuelve `(resultado, certified_data, testigo)` como respuesta.

El resto de la sección muestra un ejemplo de canister, que puede servir una
respuesta certificada para una `consulta` utilizando `certified_data` que se
verifica en el frontend. Los ejemplos están escritos en Rust y Motoko, pero el
diseño general se puede implementar en otros lenguajes.

### Construyendo un canister con variables certificadas

Consideremos la siguiente interfaz de canister:

```c
type User = record {
    name: text;
    age: nat8;
};

type CertifiedUser = record {
    user : User;
    certificate : blob;
    witness : blob;
};

service : {
    "set_user": (User) -> (nat64);
    "get_user": (nat64) -> (CertifiedUser) query;
}
```

El canister expone el siguiente servicio:

- **set_user**: El llamador proporciona un objeto `User` al canister. El  
  canister lo registra y devuelve un `index` correspondiente a la entrada como  
  respuesta. Dado que `certified_data` solo puede almacenar 32 bytes de datos,
  utiliza una  
  estructura de datos especializada de `ic_certified_map` para almacenar los
  datos del `User`.

  - La estructura de datos internamente almacena los datos en un `HashTree` (o  
    [árbol de Merkle](https://es.wikipedia.org/wiki/%C3%81rbol_de_Merkle)) y
    registra el  
    `root_hash` de la estructura de datos en el `certified_data`, que es de 32  
    bytes.
  - El `root_hash` garantiza criptográficamente que solo un árbol puede  
    corresponder a ese hash. El `root_hash` también se conoce como la prueba de
    Merkle.

- **get_user**: El llamador proporciona un `index: nat64` al canister y recibe
  una  
  respuesta certificada para el `User` correspondiente. La respuesta
  `CertifiedUser`  
  debe tener la siguiente estructura para verificar la respuesta:
  - **user**: La respuesta propiamente dicha.
  - **certificate**: El contenido para verificar la firma en el  
    `certified_data`. ICP proporciona la API del sistema `data_certificate()`
    para esto.
  - **witness**: Permite que la verificación final de la respuesta se complete  
    con la entrada solicitada y el `certified_data`.

Puedes encontrar un ejemplo de implementación del canister a continuación.

```motoko

import CertifiedData "mo:base/CertifiedData";
import Blob "mo:base/Blob";
import Nat8 "mo:base/Nat8";
import Debug "mo:base/Debug";
import Text "mo:base/Text";
import Nat64 "mo:base/Nat64";
import Array "mo:base/Array";
import CertTree "mo:ic-certification/CertTree";
import CV "mo:cbor/Value";
import CborEncoder "mo:cbor/Encoder";
import CborDecoder "mo:cbor/Decoder";

actor CertifiedVariable {

  type User = {
    name : Text;
    age : Nat8;
  };

  type CertifiedUser = {
    user : User;
    certificate : Blob;
    witness : Blob;
  };

  stable var count : Nat64 = 0;
  stable let cert_store : CertTree.Store = CertTree.newStore();
  let ct = CertTree.Ops(cert_store);

  public func set_user(user : User) : async Nat64 {
    count += 1;
    let path : [Blob] = [Text.encodeUtf8("user"), blobOfNat64(count)];
    ct.put(path, encodeUser(user));
    ct.setCertifiedData();
    return count;
  };

  public query func get_user(index : Nat64) : async CertifiedUser {
    let certificate = switch (CertifiedData.getCertificate()) {
      case (?certificate) {
        certificate;
      };
      case (null) {
        Debug.trap("Certified data not set");
      };
    };

    let path : [Blob] = [Text.encodeUtf8("user"), blobOfNat64(index)];

    let value = switch (ct.lookup(path)) {
      case (?value) {
        value;
      };
      case (null) {
        Debug.trap("Lookup failed");
      };
    };

    let user : User = decodeUser(value);
    let witness = ct.encodeWitness(ct.reveal(path));

    let certifiedUser : CertifiedUser = {
      certificate = certificate;
      witness = witness;
      user = user;
    };

    return certifiedUser;
  };

  func encodeUser(user : User) : Blob {
    let bytes : CV.Value = #majorType5([
      (#majorType3("name"), #majorType3(user.name)),
      (#majorType3("age"), #majorType0(Nat64.fromNat(Nat8.toNat(user.age)))),
    ]);

    let #ok(encoded_user) = CborEncoder.encode(bytes);
    return Blob.fromArray(encoded_user);
  };

  func decodeUser(bytes : Blob) : User {
    let #ok(#majorType5(map)) = CborDecoder.decode(bytes);
    let name_tag = Array.find<(CV.Value, CV.Value)>(map, func x = x.0 == #majorType3("name"));
    let age_tag = Array.find<(CV.Value, CV.Value)>(map, func x = x.0 == #majorType3("age"));

    let name = switch (name_tag) {
      case (?name_value) {
        let #majorType3(name) = name_value.1;
        name;
      };
      case (null) {
        Debug.trap("Decoding failed for name");
      };
    };

    let age = switch (age_tag) {
      case (?age_value) {
        let #majorType0(age) = age_value.1;
        Nat8.fromNat(Nat64.toNat(age));
      };
      case (null) {
        Debug.trap("Decoding failed for age");
      };
    };

    return {
      name = name;
      age = age;
    };
  };

  func blobOfNat64(n : Nat64) : Blob {
    let byteMask : Nat64 = 0xff;
    func byte(x : Nat64) : Nat8 {
      Nat8.fromNat(Nat64.toNat(x));
    };
    Blob.fromArray([
      byte(((byteMask << 56) & n) >> 56),
      byte(((byteMask << 48) & n) >> 48),
      byte(((byteMask << 40) & n) >> 40),
      byte(((byteMask << 32) & n) >> 32),
      byte(((byteMask << 24) & n) >> 24),
      byte(((byteMask << 16) & n) >> 16),
      byte(((byteMask << 8) & n) >> 8),
      byte(((byteMask << 0) & n) >> 0),
    ]);
  };

};

```

```rust
use candid::CandidType;
use ic_certified_map::HashTree;
use ic_certified_map::{leaf_hash, AsHashTree, Hash, RbTree};
use serde::{Deserialize, Serialize};
use std::borrow::Cow;
use std::cell::Cell;
use std::cell::RefCell;

#[derive(CandidType, Serialize, Deserialize, Clone)]
struct User {
    name: String,
    age: u8,
}

impl AsHashTree for User {
    fn root_hash(&self) -> Hash {
        let user_serialized = serde_cbor::to_vec(&self).unwrap();
        leaf_hash(&user_serialized[..])
    }
    fn as_hash_tree(&self) -> HashTree<'_> {
        HashTree::Leaf(Cow::from(serde_cbor::to_vec(&self).unwrap()))
    }
}

#[derive(CandidType)]
struct CertifiedUser {
    user: User,
    certificate: Vec<u8>,
    witness: Vec<u8>,
}

thread_local! {
    static INDEX : Cell<u64> = Cell::new(0);
    static TREE: RefCell<RbTree<&'static str, RbTree<[u8; 8], User>>> = RefCell::new(RbTree::new());
}

#[ic_cdk::update]
fn set_user(user: User) -> u64 {
    let index = INDEX.with(|index| {
        let count = index.get() + 1;
        index.set(count);
        count
    });

    TREE.with_borrow_mut(|tree| {
        match tree.get(b"user") {
            Some(_) => {
                tree.modify(b"user", |inner| {
                    inner.insert(index.to_be_bytes(), user);
                });
            }
            None => {
                let mut inner = RbTree::new();
                inner.insert(index.to_be_bytes(), user);
                tree.insert("user", inner);
            }
        }
        ic_cdk::api::set_certified_data(&tree.root_hash());
    });
    index
}

#[ic_cdk::query]
fn get_user(index: u64) -> CertifiedUser {
    let certificate = ic_cdk::api::data_certificate().expect("No data certificate available");

    TREE.with_borrow(|tree| {
        let user = match tree.get(b"user") {
            Some(inner) => {
                let user = inner.get(&index.to_be_bytes()[..]).expect("User not found");
                user.to_owned()
            }
            None => {
                panic!("Tree isn't initialized");
            }
        };

        let mut witness = vec![];
        let mut witness_serializer = serde_cbor::Serializer::new(&mut witness);
        let _ = witness_serializer.self_describe();
        tree.nested_witness(b"user", |inner| inner.witness(&index.to_be_bytes()[..]))
            .serialize(&mut witness_serializer)
            .unwrap();

        CertifiedUser {
            user,
            certificate,
            witness,
        }
    })
}
```

### Verificación de variables certificadas

Una vez que tienes la respuesta `CertifiedUser`, para garantizar la integridad,
el  
frontend debe verificar la certificación en la respuesta. Esto se divide en  
varios pasos implementados en el ejemplo de Rust y JavaScript a continuación.

:::note

El ejemplo incluye algunos pasos adicionales para configurar el canister con
algunos datos  
`User` antes de la verificación. Puedes ignorar la sección marcada entre  
`// ==== START of canister data setup` y `// ==== END of canister data setup`.

:::

1. Verificar el certificado del IC: Recalcular el `root_hash` de
   `certificate.tree`  
   (árbol de estado podado con el `certified_data` del canister) y verificar
   la  
   `certificate.signature` usando `root_hash` como mensaje,  
   `certificate.delegation`, y la `root_key` del IC como clave pública. Esto  
   confirma que la firma es válida para el árbol de estado actual.
2. Validar que la respuesta no esté desactualizada verificando que el tiempo en
   `/time` dentro  
   de `certificate.tree` sea menor que un cierto delta con respecto al tiempo
   actual. El  
   delta recomendado es de 5 minutos, pero debe adaptarse al caso de uso.
3. Recalcular el `root_hash` del witness y verificar que sea igual al  
   `certified_data`. El `certified_data` puede obtenerse desde  
   `certificate.tree` bajo la ruta `/canister/<canister_id>/certified_data`.
4. Verificar si los parámetros de la consulta están en el witness. En este
   ejemplo, la ruta de  
   búsqueda es `/user/<index>` y debe estar presente en el witness.
5. Validar si el valor encontrado en `/user/<index>` coincide con `user` de la  
   respuesta.
6. Si todos los pasos anteriores se completan exitosamente, retornar `user` como
   la respuesta válida.

```rust
use arbitrary::{Arbitrary, Unstructured};
use candid::Encode;
use candid::Principal;
use candid::{CandidType, Decode, Deserialize};
use futures::future::join_all;
use ic_agent::identity::AnonymousIdentity;
use ic_agent::Agent;
use ic_certificate_verification::validate_certificate_time;
use ic_certificate_verification::VerifyCertificate;
use ic_certification::hash_tree::HashTree;
use ic_certification::{Certificate, LookupResult};
use rand::prelude::*;
use serde_cbor::Deserializer;
use std::time::{SystemTime, UNIX_EPOCH};

#[derive(CandidType, Deserialize, Debug, PartialEq, Eq, Arbitrary)]
struct User {
    name: String,
    age: u8,
}

#[derive(CandidType, Deserialize)]
struct CertifiedUser {
    user: User,
    certificate: Vec<u8>,
    witness: Vec<u8>,
}

static URL: &str = "http://localhost:41749";
static CANISTER: &str = "a3shf-5eaaa-aaaaa-qaafa-cai";
const MAX_CERT_TIME_OFFSET_NS: u128 = 300_000_000_000; // 5 min
const MAX_CALLS: usize = 10;

#[tokio::main]
async fn main() {

    let agent = Agent::builder()
        .with_url(URL)
        .with_identity(AnonymousIdentity)
        .build()
        .expect("Unable to create agent");

    // This should be done only in demo environments.
    // When interacting with mainnet, hardcode the root_key.
    agent
        .fetch_root_key()
        .await
        .expect("Unable to fetch root key");
    let root_key = agent.read_root_key();

    let canister_id = Principal::from_text(CANISTER).unwrap();

    // ==== START of canister data setup
    let mut rng = rand::thread_rng();

    // Make MAX_CALLS to set_user
    let mut get_user_calls = Vec::new();
    for _ in 0..MAX_CALLS {
        let bytes: [u8; 16] = rng.gen();
        let mut u = Unstructured::new(&bytes[..]);
        let temp_user = User::arbitrary(&mut u).unwrap();

        println!("Calling set_user with {:?}", temp_user);
        let response = agent
            .update(&canister_id, "set_user")
            .with_effective_canister_id(canister_id)
            .with_arg(Encode!(&temp_user).unwrap())
            .call_and_wait();
        get_user_calls.push(response);
    }
    let results: Vec<u64> = join_all(get_user_calls)
        .await
        .into_iter()
        .map(|result| {
            Decode!(
                result
                    .expect("Query call get_user failed")
                    .as_slice(),
                u64
            )
            .unwrap()
        })
        .collect();

    // From response indexes, choose a random index for get_user
    let index: usize = rng.gen();
    let index: u64 = *results.get(index % MAX_CALLS).unwrap();
    // ==== END of canister data setup

    println!("Fetching index {:?}", index);

    let query_response = agent
        .query(&canister_id, "get_user")
        .with_effective_canister_id(canister_id)
        .with_arg(Encode!(&index).unwrap())
        .call()
        .await
        .expect("Unable to call query call get_user");

    let certified_user = Decode!(&query_response, CertifiedUser).unwrap();

    let mut deserializer = Deserializer::from_slice(&certified_user.certificate);
    let certificate: Certificate = serde::de::Deserialize::deserialize(&mut deserializer).unwrap();

    let start = SystemTime::now();
    let current_time = start
        .duration_since(UNIX_EPOCH)
        .expect("Time went backwards")
        .as_nanos();

    // Step 1: Check if signature in the certificate can be validated with the
    // root_hash of the tree in certificate as message and root_key as public_key
    let verification_result = certificate.verify(canister_id.as_slice(), &root_key[..]);

    println!(
        "Step 1: Digest match & Signature verification: {:?}",
        verification_result
    );

    // Step 2: Check if the response is not stale with the given time offset MAX_CERT_TIME_OFFSET_NS.
    let time_verification_result =
        validate_certificate_time(&certificate, &current_time, &MAX_CERT_TIME_OFFSET_NS);

    println!("Step 2: Time skew: {:?}", time_verification_result);

    // Step 3: Check if witness root_hash matches the certified_data
    let lookup_result =
        certificate
            .tree
            .lookup_path([b"canister", canister_id.as_slice(), b"certified_data"]);

    let certified_data: [u8; 32] = match lookup_result {
        LookupResult::Found(result) => result.try_into().unwrap(),
        _ => panic!("Certified data not found"),
    };

    let mut deserializer = Deserializer::from_slice(&certified_user.witness);
    let witness_decoded: HashTree<Vec<u8>> =
        serde::de::Deserialize::deserialize(&mut deserializer).unwrap();
    let witness_digest = witness_decoded.digest();

    println!(
        "Step 3: Witness digest matches certified data: {:?} ",
        witness_digest == certified_data
    );

    // Step 4: Check if the query parameters are in the witness
```

```js
function verifyTime(rawTime) {
  const idlMessage = new Uint8Array([
    ...new TextEncoder().encode("DIDL\x00\x01\x7d"),
    ...new Uint8Array(rawTime),
  ]);
  const decodedTime = IDL.decode([IDL.Nat], idlMessage)[0];
  const time = Number(decodedTime) / 1e9;
  const now = Date.now() / 1000;
  const diff = Math.abs(time - now);
  if (diff > 5) {
    return false;
  }
  return true;
}

function bigEndian(n) {
  let buf = new Uint8Array(8);

  for (let i = 7; i >= 0; i--) {
    buf[i] = Number(n & 0xffn);
    n >>= 8n;
  }
  return buf;
```

## Utilizar certificación de activos HTTP y evitar servir tu dapp a través de `raw.icp0.io`

### Preocupación de seguridad

Las dapps en ICP pueden utilizar la
[certificación de activos](https://wiki.internetcomputer.org/wiki/HTTP_asset_certification)
para asegurarse de que los activos HTTP entregados al navegador sean auténticos
(es decir, firmados por umbral por la subred). Si una aplicación no realiza la
certificación de activos, solo se puede servir de forma insegura a través de
`raw.icp0.io`, donde no se verifica la certificación de activos. Esto es
inseguro ya que un solo nodo malicioso o nodo frontera puede modificar
libremente los activos entregados al navegador.

Si una aplicación se sirve a través de `raw.icp0.io` además de `icp0.io`, un
adversario puede engañar a los usuarios (phishing) para que utilicen el inseguro
`raw.icp0.io`.

### Recomendación

- Solo sirve activos a través de `<canister-id>.icp0.io`, donde los nodos
  frontera aplican la verificación de respuesta en los activos servidos. No
  sirvas a través de `<canister-id>.raw.icp0.io`.

- Sirve activos utilizando el canister de activos, que crea automáticamente la
  certificación de activos, o agrega el encabezado `ic-certificate` que incluye
  la certificación de activos, como se hace, por ejemplo, en la
  [dapp NNS](https://github.com/dfinity/nns-dapp) y
  [Internet Identity](https://github.com/dfinity/internet-identity).

- Verifica en el método `http_request` del canister si la solicitud se realizó a
  través de raw. Si es así, devuelve un error y no sirvas ningún activo.
