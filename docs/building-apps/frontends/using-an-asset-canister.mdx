# Aplicaciones Frontend

<MarkdownChipRow labels={["Principiante", "Asset canisters"]} />

Las aplicaciones suelen emplear una interfaz de frontend para mostrar elementos
como un panel de control, una página de cuenta, un reproductor multimedia u
otros recursos en el navegador web, facilitando así la interacción del usuario.
Estos recursos pueden estar en forma de HTML, JavaScript o CSS, o utilizar
frameworks de frontend como React.

Las aplicaciones Frontend se alojan en ICP utilizando **asset canisters**. Estos
canisters compilan los recursos del frontend, como CSS y JavaScript, en un
módulo Wasm que puede ser desplegado en ICP como un

<GlossaryTooltip>canister</GlossaryTooltip>.

Los términos 'asset canister' y 'frontend canister' a veces se usan
indistintamente. **Asset canister** suele referirse al código Rust que `dfx`
utiliza en segundo plano para compilar los recursos de frontend en Wasm.
**Frontend canister** se usa generalmente para describir el frontend de un
proyecto.

Las aplicaciones Frontend pueden adoptar las siguientes formas:

- Un frontend canister que se comunica con backend canisters para proporcionar
  una dapp full-stack.
- Backend canisters que se comunican con una aplicación frontend externa que no
  está alojada en ICP. Para facilitar esta comunicación, se puede utilizar el  
  [ICP JavaScript agent](/docs/building-apps/interact-with-canisters/agents/javascript-agent).  
  [Más información sobre la API de solicitudes en JS](/docs/building-apps/interact-with-canisters/agents/javascript-agent).
- Un frontend canister que no se comunica con backend canisters y solo
  proporciona recursos web.

Flujo de trabajo típico para crear un frontend de aplicación

1. El desarrollador escribe el código frontend, como HTML, JS o CSS.
2. El desarrollador configura el archivo `dfx.json` para incluir un frontend
   canister con tipo `"assets"`.
3. El desarrollador despliega el proyecto. `dfx` compilará los archivos de
   frontend en un asset canister.
4. Los usuarios abren la aplicación en el navegador accediendo a la URL  
   `https://<canister-id>.icp0.io` o un  
   [dominio personalizado](/docs/building-apps/frontends/custom-domains/using-custom-domains)  
   si se ha registrado uno para el canister.
5. El canister sirve los recursos web al navegador a través de su endpoint
   `http_request`, que se invoca en cada solicitud HTTP.
6. Cuando el código JS se ejecuta en el navegador, puede llamar a los endpoints
   del backend canister utilizando la  
   [librería ICP JavaScript agent](/docs/building-apps/interact-with-canisters/agents/javascript-agent),  
   similar a `web3.js` y `ethers.js` en Ethereum.

### Limitaciones

El Server-Side Rendering (SSR) no funciona en canisters porque requiere código
JS que no está incorporado en los canisters. En el futuro, esto podría ser
posible con Azle. Hasta entonces, si se necesita SSR, una solución es alojar el
frontend fuera de ICP mientras se mantiene la lógica principal en un backend
canister.

## Cómo funcionan los asset canisters

Para alojar recursos web, un canister debe implementar un método que acepte y
procese una solicitud HTTP, incluyendo la URL, método HTTP y datos de cabecera.
Luego, debe devolver una respuesta HTTP con el estado de la solicitud, datos de
cabecera y contenido en el cuerpo. Este método puede devolver contenido HTML,
CSS y JavaScript en la respuesta HTTP.

Para configurar un canister que implemente estos métodos, se debe definir en el
archivo `dfx.json` del proyecto como `"type": "asset"`. Este parámetro instruye
a `dfx` para compilar el canister con código base que facilite estas solicitudes
HTTP. Este código base está escrito en Rust y luego se compila en un módulo
WebAssembly que puede instalarse en un canister.

## Plantillas de frontend canister

Todos los proyectos creados con  
[`dfx new`](/docs/building-apps/developer-tools/dfx/dfx-new)  
tienen la opción de incluir una plantilla de frontend canister con código basado
en uno de los siguientes frameworks: SvelteKit, React, Vue o Vanilla JS. Estas
plantillas están disponibles en `dfx` a partir de la versión 0.17.0.

Para los asset canisters creados por `dfx new`, la configuración predeterminada
será similar a la siguiente:

```json
{
  "canisters": {
    "hello_backend": {
      "main": "src/hello_backend/main.mo",
      "type": "motoko"
    },
    "hello_frontend": {
      "dependencies": ["hello_backend"],
      "source": ["src/hello_frontend/dist"],
      "type": "assets",
      "workspace": "hello_frontend"
    }
  },
  "defaults": {
    "build": {
      "args": "",
      "packtool": ""
    }
  },
  "output_env_file": ".env",
  "version": 1
}
```

En esta configuración, los siguientes parámetros son importantes:

- `"source": [ "src/hello_frontend/dist" ]`:  
  Define los subdirectorios predeterminados que contienen los archivos de
  recursos. Para que los recursos se sirvan en el frontend canister, sus
  directorios deben estar incluidos en esta lista de `source`.
- `"type": "assets"`:  
  Define el tipo de canister como `assets` e instruye a `dfx` para compilarlo
  como tal.

## Limitaciones

Un frontend canister puede alojar aproximadamente 1 GiB en archivos estáticos.  
Se recomienda distribuir los archivos en múltiples canisters si el tamaño total
de los recursos supera esta cantidad. Si se excede este límite, el canister
puede fallar al actualizarse.

## URLs de la aplicación

Los frontend canisters sirven los recursos web de la aplicación a través de una
URL que contiene el ID del canister. Las implementaciones locales utilizan URLs
como  
`http://127.0.0.1:4943/?canisterId=<canister-id>`,  
mientras que las aplicaciones desplegadas en mainnet usan URLs públicas con el
ID del canister seguido de `.ic0.app`, `.icp0.io` o `raw.icp0.io`.

### Interfaces HTTP sin procesar

El dominio `raw.icp0.io` permite acceder a la interfaz HTTP sin procesar del
canister. Para simulaciones locales de este comportamiento, se debe implementar
un método en el canister que consuma solicitudes HTTP y devuelva respuestas.  
Aquí tienes un ejemplo en Motoko:

```motoko no-repl
public shared(msg) func http_request(req: HttpRequest) : async HttpResponse {
    {
        status = { code = 200; reason = "OK" };
        headers = [( "Content-Type", "text/plain" )];
        body = Text.encodeUtf8("Hello, World!");
    }
};
```

### URLs dinámicas

Las URLs dinámicas no son compatibles con el frontend canister predeterminado.  
Si un desarrollador quiere soportarlas, puede implementar lógica personalizada
usando  
[opciones de terceros](https://crates.io/crates/ic-pluto).

## Páginas 404 y aliasing

Se puede utilizar la biblioteca Rust `ic-http-certification` para servir páginas
404 o configurar redirecciones a través de su función wildcard, por ejemplo:

```rust
use ic_http_certification::HttpCertificationPath;

let path = HttpCertificationPath::wildcard("/js");
```

Actualmente, las páginas 404 solo pueden servirse como contenido sin procesar.

[Más información sobre la librería de certificación HTTP](/docs/building-apps/network-features/using-http/http-certification/serving-static-assets-over-http).
