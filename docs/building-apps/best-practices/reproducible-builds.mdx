# Mejores prácticas para desarrolladores: Compilaciones reproducibles

<MarkdownChipRow labels={["Intermedio", "Mejores prácticas"]} />

Si estás utilizando un canister que no desarrollaste tú mismo, es posible que
quieras  
verificar que el canister está ejecutando el código que esperas antes de darle
control  
para tomar decisiones importantes por ti, como aceptar ICP para un pago.
Verificar el  
código de un canister requiere confirmar que el módulo Wasm es el resultado
correcto  
de compilar el código fuente del canister y que el canister, de hecho, está
ejecutando  
ese módulo Wasm y no otro.

Por lo tanto, se recomienda que los autores de canisters aseguren que es
posible  
realizar compilaciones de Wasm de confianza y  
[reproducibles](https://reproducible-builds.org/docs/definition/) a partir de
su  
código fuente. Estas compilaciones permiten que cualquiera siga los mismos pasos
que  
los autores del canister y obtenga exactamente el mismo módulo Wasm, que luego
puede  
compararse con el módulo Wasm que se ejecuta en ICP.

## Consideraciones para desarrolladores

Al desarrollar código que se espera que sea reproducible, se recomienda usar  
[Docker o una tecnología similar](#build-environments-using-docker) para
configurar  
convenientemente el sistema operativo y las herramientas de compilación y fijar
sus  
versiones para el usuario. Si las herramientas de compilación que estás
utilizando no  
garantizan compilaciones completamente reproducibles, Docker también puede
ayudar  
minimizando las diferencias en rutas, variables de entorno, etc. Las
herramientas de  
compilación y la imagen base de Docker deben provenir de una fuente en la que
el  
usuario pueda confiar. Idealmente, se debe minimizar el número de dependencias,
ya que  
el usuario podría tener que recompilar todas tus dependencias para reproducir  
correctamente tu compilación.

Sin embargo, las herramientas de compilación no son perfectas y pueden fallar
al  
garantizar compilaciones reproducibles. Si la reproducibilidad es crítica para
tu  
canister (por ejemplo, si maneja fondos de otros usuarios),  
[pruébalo](#testing-reproducibility).

## Obtener el hash del módulo Wasm

ICP no permite acceder al módulo Wasm de un canister arbitrario. Esta es una
decisión  
de diseño, ya que los desarrolladores podrían querer mantener algo de código
privado.  
Sin embargo, ICP sí permite que cualquiera acceda al SHA-256 del módulo Wasm.

Para obtener este hash, primero debes identificar el principal del canister cuyo
código  
quieres verificar. Por ejemplo, para verificar el código del canister de
Internet  
Identity, el principal es `rdmx6-jaaaa-aaaaa-aaadq-cai`. Luego, la forma más
fácil de  
acceder a estos datos es usando  
[`dfx`](/docs/building-apps/getting-started/install) desde una línea de comandos
con  
el siguiente comando:

```bash
dfx canister --network ic info rdmx6-jaaaa-aaaaa-aaadq-cai
```

Esto devolverá el(los) controlador(es) del canister y el hash del módulo Wasm:

```
Controllers: r7inp-6aaaa-aaaaa-aaabq-cai
Module hash: 0x86ab08ea53e4da5bba4f27baa931e2edc5ab2a1f228c204a5340992c16389f66
```

Necesitarás ejecutar este comando desde un directorio que contenga un archivo  
`dfx.json` válido. Si no tienes un directorio así, puedes crear uno usando  
`dfx new`.

Aquí, ICP nos indica que el hash del módulo Wasm del canister  
`rdmx6-jaaaa-aaaaa-aaadq-cai` es  
`0x86ab08ea53e4da5bba4f27baa931e2edc5ab2a1f228c204a5340992c16389f66`.

La verificación anterior te proporciona el hash **actual** del módulo Wasm del  
canister, pero los **controladores** de un canister pueden cambiar el código
en  
cualquier momento, por ejemplo, para actualizar el canister. Sin embargo, si la
lista  
de controladores está vacía o el único controlador es un canister  
[blackhole](https://github.com/ninegua/ic-blackhole), sabes que el canister es  
inmutable, ya que nadie tiene el poder de cambiar el código.

## Verificar que la compilación sea reproducible

A continuación, verifica si este hash corresponde a un determinado código
fuente. Esto  
solo funciona si el proceso de compilación del código es reproducible.

Como autor de un canister, hay algunas cosas que debes proporcionar a tus
usuarios para  
permitirles reproducir tu compilación:

- El mismo código fuente que utilizaste para crear el módulo Wasm del canister.

- Instrucciones sobre cómo recrear tu entorno de compilación.

- Instrucciones sobre cómo repetir el proceso de compilación del Wasm a partir
  del  
  código fuente. El proceso debe ser determinista para garantizar que produzca  
  exactamente el mismo Wasm. También debe ser confiable, de forma que el usuario
  pueda  
  convencerse de que el Wasm es una traducción fiel del código fuente y no un
  artefacto  
  de una herramienta de compilación maliciosa. En particular, busca los
  directorios  
  `.dfx`, `node_modules` y `target` que podrían contener archivos precompilados.

### Proporcionar el código fuente

Normalmente, se recomienda que los desarrolladores versionen su código en `git`
u otro  
sistema de control de versiones, y el código versionado puede estar disponible
en un  
repositorio público como GitHub. En este caso, como desarrollador, debes anotar
el  
commit específico que se utilizó al producir el código que fue desplegado en ICP
y  
comunicarlo a los usuarios que puedan querer verificar tu canister.
Alternativamente,  
también puedes proporcionar un paquete (por ejemplo, un archivo zip o tarball)
que  
contenga el código fuente que utilizaste para construir tu canister.

### Reproducir entornos de compilación

Antes de compilar tu código, debes documentar en detalle el entorno de
compilación que  
estás utilizando. En particular, para los lenguajes compatibles con el IC SDK
(Motoko,  
Rust, TypeScript, Python):

- Anota el sistema operativo de tu máquina local y su versión.

- Si estás utilizando el IC SDK, anota la versión usada. Puedes instalar
  versiones  
  arbitrarias del IC SDK usando  
  [`dfxvm`](/docs/building-apps/developer-tools/dfxvm/dfxvm-install).

- Si estás compilando código en Motoko de una forma distinta a `dfx build`,
  anota la  
  versión de `moc` que estás utilizando.

- Si estás compilando en Rust, anota la versión de `cargo` que estás utilizando.

- Si estás compilando en TypeScript, anota la versión de  
  [Azle](https://demergent-labs.github.io/azle/).

- Si estás compilando en Python, anota la versión de Python y
  [Kybra](https://demergent-labs.github.io/kybra/).

- Si estás usando un framework para desarrollo frontend, como React, Vite o
  webpack, anota sus versiones.

- Si tu proceso de compilación depende de variables de entorno (como la zona
  horaria o  
  la configuración regional), anótalas.

Debes comunicar todo esto a tu usuario en las instrucciones para la
compilación  
reproducible. Idealmente, proporciona una receta o script ejecutable para
recrear el  
entorno de compilación usando herramientas como Docker o Nix. Se recomienda usar
Docker,  
ya que también te permite fijar el sistema operativo utilizado para compilar
el  
software.

### Entornos de compilación usando Docker

[Contenedores Docker](https://docs.docker.com/) son una solución popular para  
proporcionar entornos de compilación reproducibles.

:::info

Para desarrolladores que usan macOS, se recomienda instalar Docker usando  
[lima](https://github.com/lima-vm/lima), ya que resulta más estable que Docker
Desktop  
o Docker Machine. En particular, evita algunos bugs de QEMU en máquinas Apple
M1.

:::

Después de configurar Docker, puedes usar un `Dockerfile` para proporcionar al
usuario  
una versión específica del sistema operativo, así como otras herramientas
necesarias,  
como `dfx`, Node.js y la herramienta de Rust.

:::caution

Se recomienda mantenerse en `x86_64` para ejecutar el contenedor Docker,  
ya que las compilaciones generalmente no son reproducibles entre arquitecturas.
Consulta  
la
[documentación](https://github.com/lima-vm/lima/blob/master/docs/multi-arch.md)  
sobre cómo configurar contenedores Docker multiplataforma si tu entorno host no
es `x86_64`.

:::

A continuación, se muestra un ejemplo de Dockerfile que crea un entorno de
compilación  
estandarizado para Rust.

```dockerfile title="Dockerfile"
FROM ubuntu:22.04

ENV NVM_DIR=/root/.nvm
ENV NVM_VERSION=v0.39.1
ENV NODE_VERSION=18.1.0

ENV RUSTUP_HOME=/opt/rustup
ENV CARGO_HOME=/opt/cargo
ENV RUST_VERSION=1.62.0

ENV DFX_VERSION=0.23.0

# Install the basic environment needed for our build tools.
RUN apt -yq update && \
    apt -yqq install --no-install-recommends curl ca-certificates \
        build-essential pkg-config libssl-dev llvm-dev liblmdb-dev clang cmake rsync

# Install Node.js using nvm
ENV PATH="/root/.nvm/versions/node/v${NODE_VERSION}/bin:${PATH}"
RUN curl --fail -sSf https://raw.githubusercontent.com/creationix/nvm/${NVM_VERSION}/install.sh | bash
RUN . "${NVM_DIR}/nvm.sh" && nvm install ${NODE_VERSION}
RUN . "${NVM_DIR}/nvm.sh" && nvm use v${NODE_VERSION}
RUN . "${NVM_DIR}/nvm.sh" && nvm alias default v${NODE_VERSION}

# Install Rust and Cargo
ENV PATH=/opt/cargo/bin:${PATH}
RUN curl --fail https://sh.rustup.rs -sSf \
        | sh -s -- -y --default-toolchain ${RUST_VERSION}-x86_64-unknown-linux-gnu --no-modify-path && \
    rustup default ${RUST_VERSION}-x86_64-unknown-linux-gnu && \
    rustup target add wasm32-unknown-unknown &&\
    cargo install ic-wasm

# Install dfx
RUN sh -ci "$(curl -fsSL https://internetcomputer.org/install.sh)"

COPY . /canister
WORKDIR /canister
```

#### Qué hace esto

Hay un par de cosas que vale la pena señalar sobre este `Dockerfile`:

- Comienza a partir de una imagen oficial de Docker, de modo que todas las
  herramientas instaladas son estándar y provienen de fuentes estándar. Esto
  brinda al usuario la confianza de que el entorno de construcción no ha sido
  manipulado y, por lo tanto, que se puede confiar en el proceso de construcción
  usando Docker.

- Para garantizar que se instalen versiones específicas de las herramientas de
  construcción, se instalan directamente en lugar de utilizar un gestor de
  paquetes. Los gestores de paquetes generalmente no permiten fijar versiones
  específicas de las herramientas de construcción.

Para usar este `Dockerfile`, inicia Docker
[correctamente](https://docs.docker.com), coloca el `Dockerfile` en el
directorio del proyecto de tu canister y crea el contenedor de Docker
ejecutando:

```bash
docker build -t mycanister .
```

Esto crea una imagen de contenedor Docker llamada `mycanister`, con Node.js,
Rust y `dfx` instalados. El código fuente de tu canister se copiará al
directorio `/canister`. Debes ejecutar `docker build` desde el directorio del
proyecto del canister. Luego puedes entrar a una terminal interactiva dentro del
contenedor Docker ejecutando:

```bash
docker run -it --rm mycanister
```

Desde aquí, puedes experimentar con los pasos necesarios para construir tu
canister. Una vez que estés seguro de que los pasos son deterministas, también
puedes agregarlos al `Dockerfile`. Por ejemplo, para ejecutar un script de
construcción, agrega la línea:

```dockerfile
RUN ./build_script.sh
```

Puedes ver un ejemplo en el  
[Dockerfile del canister de Internet Identity](https://github.com/dfinity/internet-identity/blob/397d0087a29855564c47f0fd3323f60b5b67a8fa/Dockerfile).

### Script de construcción de ejemplo

A continuación se muestra un script de ejemplo que puede usarse para construir
un proyecto Rust de manera programática:

:::info

Este es un script de construcción de ejemplo para un proyecto en Rust y no
incluye un ejemplo completamente exhaustivo de lo que puede contener un script
de construcción, ni incluye instrucciones de construcción para otros lenguajes

```bash
#!/bin/bash
#
# additional setup, e.g., build frontend assets:
# ...
# Rust build:

```

Un script de construcción como el anterior se puede especificar como un script
de construcción personalizado en `dfx.json`:

```json title="dfx.json"
"canisters": {
  "example_backend": {
    "candid": "src/example_backend/example_backend.did",
    "package": "example_backend",
    "type": "custom",
    "wasm": "./example_backend.wasm",
    "build": "./build_script.sh"
  }
}
```

### Garantizando el determinismo del proceso de construcción

A continuación, considera si es necesario hacer que la construcción sea
determinista. Para que el proceso de construcción sea determinista:

- #### Paso 1: Necesitarás asegurarte de que cualquier dependencia de tu canister siempre se resuelva de la misma manera. La mayoría de las herramientas de construcción permiten fijar las dependencias a una versión específica.

Para `npm`, ejecutar `npm install` creará un archivo `package-lock.json` con
algunas versiones fijas de todas las dependencias (transitivas) de tu proyecto
que satisfacen los requisitos especificados en tu `package.json`. Sin embargo,
`npm install` sobrescribirá el archivo `package-lock.json` cada vez que se
invoque. Por lo tanto, una vez que estés listo para crear la versión final de tu
canister, ejecuta `npm install` solo una vez. Luego, haz commit del
`package-lock.json` a tu sistema de control de versiones. Finalmente, al
verificar la construcción para reproducibilidad, usa `npm ci` en lugar de
`npm install`.

Para código Rust, Cargo generará automáticamente un archivo `Cargo.lock` con las
versiones fijas de tus dependencias (transitivas). Al igual que con
`package-lock.json`, deberías hacer commit de este archivo a tu sistema de
control de versiones una vez que estés listo para producir la versión final de
tu canister. Además, Cargo por defecto ignora las versiones bloqueadas de las
dependencias. Pasa la opción `--locked` al comando `cargo` para asegurarte de
que se usen las dependencias bloqueadas.

- #### Paso 2: Tus propios scripts de construcción no deben introducir no-determinismo.

Fuentes de no-determinismo incluyen aleatoriedad, marcas de tiempo, concurrencia
u ofuscadores de código. Fuentes menos obvias incluyen configuraciones
regionales (locales), rutas absolutas de archivos, el orden de archivos en un
directorio y URLs remotas cuyo contenido puede cambiar. Además, depender de
complementos de construcción de terceros te expone a cualquier no-determinismo
introducido por estos.

- #### Paso 3: Dadas las mismas dependencias y scripts de construcción deterministas, las herramientas de construcción en sí mismas (`moc` para Motoko, `cargo` para Rust, `npx` para TypeScript, `pip` para Python o `webpack` para desarrollo frontend) también deben ser deterministas.

Estas herramientas buscan ser deterministas. Sin embargo, son piezas de software
complejas y garantizar el determinismo no es trivial. Por lo tanto, los errores
de no-determinismo pueden, y de hecho, ocurren.

#### Consideraciones deterministas en Motoko

El compilador de Motoko busca ser determinista y reproducible; si encuentras
problemas de reproducibilidad, por favor envía un
[nuevo issue](https://github.com/dfinity/motoko/issues/new/choose), y el equipo
tratará de abordarlos en la medida de lo posible.

#### Consideraciones deterministas en Rust

Para Rust, consulta la
[lista de problemas actuales de posible no-determinismo en Rust](https://github.com/rust-lang/rust/labels/A-reproducibility).  
Si has observado diferencias entre código Rust compilado a Wasm bajo Linux y
macOS, se recomienda fijar la plataforma de construcción y su versión.

#### Consideraciones deterministas en Webpack

Para webpack,  
[la asignación determinista de nombres de módulos y chunks](https://webpack.js.org/configuration/optimization/)  
que deberías usar ha sido introducida desde la versión 5.

### Probando la reproducibilidad

Si la reproducibilidad es vital para tu código, deberías probar la construcción
para aumentar tu confianza en su reproducibilidad. La herramienta  
[reprotest](https://salsa.debian.org/reproducible-builds/reprotest) puede
ayudarte a automatizar pruebas de reproducibilidad, ya que prueba tu
construcción ejecutándola en dos entornos diferentes que difieren en
características como rutas, tiempo, orden de archivos y otras, y compara los
resultados. Para verificar tu construcción con `reprotest`, agrega la siguiente
línea a tu `Dockerfile`:

```dockerfile
RUN apt -yqq install --no-install-recommends reprotest disorderfs faketime rsync sudo wabt
```

Al usar `dfx build --network ic`, necesitas preconstruir tus dependencias
frontend ejecutando `npm ci` antes de `dfx build --network ic` o estableciendo
el tipo de construcción personalizada en `dfx.json` y ejecutando `npm ci` en tu
script de construcción. Tu directorio del proyecto debe contener un archivo
`canister_ids.json` que contenga los IDs de tus canisters en la red principal. A
continuación se muestra un ejemplo de archivo `canister_ids.json`:

```json title="canister_ids.json"
{
  "example_backend": {
    "ic": "rrkah-fqaaa-aaaaa-aaaaq-cai"
  },
  "example_frontend": {
    "ic": "ryjl3-tyaaa-aaaaa-aaaba-cai"
  }
}
```

Ahora, desde el directorio raíz de tu proyecto de canister, puedes probar la
reproducibilidad de tu construcción utilizando los comandos:

```
docker build -t mycanister .
docker run --rm --privileged -it mycanister
/canister# mkdir artifacts
/canister# reprotest -vv --store-dir=artifacts --variations '+all,-time' 'dfx build --network ic' '.dfx/ic/canisters/*/*.wasm'
```

#### Qué hace esto

- El primer comando construye el contenedor Docker utilizando el `Dockerfile`
  proporcionado anteriormente.
- El segundo comando abre una shell interactiva en el contenedor, indicada por
  el flag `-it`. Puedes ejecutarlo en modo privilegiado usando el flag
  `--privileged`, ya que `reprotest` utiliza módulos del kernel para algunas
  variaciones del entorno de construcción. También puedes ejecutarlo en modo no
  privilegiado excluyendo algunas de las variaciones; consulta el  
  [manual de reprotest](https://manpages.debian.org/stretch/reprotest/reprotest.1.en.html).  
  El flag `--rm` destruirá el contenedor después de que cierres la shell.
- Una vez dentro del contenedor, se crea un directorio para los artefactos de
  construcción y se lanza `reprotest` en modo detallado utilizando los flags
  `-vv`. Debes proporcionarle el comando de construcción que deseas ejecutar
  como primer argumento; en este ejemplo es `dfx build --network ic`. Luego
  ejecutará la construcción en dos entornos diferentes.
- Finalmente, necesitas decirle a `reprotest` qué rutas comparar al final de las
  dos construcciones. En este ejemplo, compara el código Wasm de todos los
  canisters, que se encuentra en el directorio `.dfx/ic`.  
  Se recomienda comparar los artefactos producidos por `reprotest` mientras se
  cambia manualmente la hora del sistema.

:::info

Este flujo de trabajo omite la variación de tiempo porque el compilador de Rust
utiliza `jemalloc` para la asignación dinámica de memoria, y esta biblioteca no
es  
[compatible](https://github.com/wolfcw/libfaketime/issues/130) con `faketime`,
que es usado por `reprotest` para implementar la variación de tiempo.

:::

Si la comparación no encuentra diferencias, verás una salida similar a esta:

```
=======================
Reproduction successful
=======================
No differences in ./.dfx/ic/canisters/*/*.wasm
6b2a15a918219138836e88e9c95f9c5d2d7b6d465df83ae05d6fd2b0f14f8a97  ./.dfx/ic/canisters/example_backend/example_backend.wasm
a047686c1d517e21d447bcd42c9394a12cdb240e06425b830c99d3a689b5ee20  ./.dfx/ic/canisters/example_frontend/assetstorage.wasm
a047686c1d517e21d447bcd42c9394a12cdb240e06425b830c99d3a689b5ee20  ./.dfx/ic/canisters/example_frontend/example_frontend.wasm
```

Esto es un buen indicador de que tu construcción no está siendo afectada por tu
entorno.

:::info

Ten en cuenta que `reprotest` no puede comprobar que tus dependencias estén
fijadas correctamente.  
Se recomienda ejecutar el contenedor que construye `reprotest` en varios
sistemas operativos anfitriones y comparar los resultados.  
Si la comparación encuentra diferencias entre el código Wasm producido en dos
construcciones, se mostrará un diff.  
Probablemente querrás usar el flag `--store-dir` de `reprotest` para guardar las
salidas y el diff en algún lugar donde puedas analizarlos.  
Si tienes dificultades para lograr la reproducibilidad, considera también usar  
[DetTrace](https://github.com/dettrace/dettrace), que es una abstracción de
contenedor que intenta hacer que las construcciones arbitrarias sean
deterministas.

:::

Finalmente, si tu construcción es reproducible, puedes comparar el hash del
código Wasm resultante con el hash del código que se está ejecutando en un
canister, el cual puedes obtener de la siguiente forma:

```
dfx canister --network ic info <canister-id>
```

Ten cuidado, ya que este hash puede cambiar si los controladores actualizan el
código del canister.

## Consideraciones a largo plazo

Incluso después de lograr reproducibilidad en tus construcciones, aún hay otras
cosas que considerar a largo plazo.

La reproducibilidad puede ser más exigente si esperas que tu código de canister
permanezca durante años y siga siendo reproducible. Los mayores desafíos son
asegurar que tu:

- Herramienta de construcción esté disponible en el futuro.

- Dependencias estén disponibles.

- Herramienta de construcción aún se ejecute y construya correctamente tus
  dependencias.

Las distribuciones y archivos de paquetes pueden eliminar versiones antiguas de
paquetes, incluyendo tanto tu herramienta como sus dependencias.  
Los sitios web pueden dejar de estar disponibles y las URLs pueden dejar de
funcionar.  
Es prudente respaldar todas tus herramientas de construcción y dependencias.  
Deberías considerar involucrarte en proyectos como  
[Software Heritage](https://www.softwareheritage.org/), que hacen esto a gran
escala.

Podrías tener que ajustar tu proceso de construcción para asegurar que tu
canister siga compilándose.  
Incluso si la construcción cambia, si aún produce el mismo resultado, tus
usuarios pueden confiar en que tu canister está ejecutando el código correcto.  
El argumento de confianza es más fácil si tus dependencias provienen de una
fuente confiable, como el proyecto Software Heritage.
