# Confianza en los canisters

<MarkdownChipRow labels={["Principiante", "Educación", "Concepto"]} />

Las aplicaciones que brindan transacciones DeFi u otras transacciones valiosas,
como la capacidad de transferir activos, requieren que los usuarios confíen en
la aplicación para actuar de manera honesta y confiable. ¿Cómo se puede asegurar
que es seguro confiar los activos a un canister?

Los usuarios deben tener confianza en que:

1. El canister hace lo que se supone que debe hacer.

2. El comportamiento del canister no cambiará inesperadamente.

## Confianza en que el canister hace lo que se supone que debe hacer

El comportamiento correcto de un canister se puede verificar en dos pasos.
Primero, inspeccione el código fuente utilizado para generar el código Wasm
implementado en un canister para asegurarse de que implementa la funcionalidad
esperada o reclamada y solo esta funcionalidad.

Segundo, asegúrese de que el módulo Wasm que ejecuta el canister se haya
generado a partir del código fuente reclamado. Aquí, la reproducibilidad de la
compilación es crucial: el desarrollador debería haber construido el módulo Wasm
de manera que se pueda reconstruir exactamente el mismo Wasm desde cero. Luego,
el usuario puede comparar el hash del módulo Wasm reconstruido con el hash del
módulo informado por ICP. Los desarrolladores y los usuarios pueden encontrar
orientación sobre cómo garantizar la reproducibilidad en
[compilaciones reproducibles](/docs/building-apps/best-practices/reproducible-builds).

Además, los desarrolladores pueden utilizar la función de
[historial del canister](/docs/building-apps/canister-management/history) para
realizar un seguimiento de los cambios en el hash del módulo Wasm del canister.

## Confianza en que el comportamiento del canister no cambiará inesperadamente

Los contratos inteligentes de los canisters son implementados y gestionados por
controladores. El nivel de descentralización de un controlador puede variar
desde ser gestionado por una sola persona o equipo de personas hasta ser
gestionado por el NNS, un SNS u otro tipo de DAO en la cadena. Entre otras
capacidades, los controladores pueden cambiar el código de los canisters que
controlan porque el código del canister es **mutable**. Los controladores tienen
control total sobre los activos, como tokens ICP o bitcoins, que posee el
canister que administran. Esta característica acerca los canisters al software
típico y los hace adecuados para una amplia gama de aplicaciones donde la lógica
del software puede cambiarse según sea necesario.

Para aplicaciones críticas como las utilizadas en DeFi, la mutabilidad
centralizada puede ser peligrosa. El controlador podría convertir un canister
benigno en un canister que roba activos.

:::info

Los controladores de los canisters, si no están descentralizados de manera
voluntaria, tienen control total sobre los activos del usuario que posee el
canister, como tokens ICP o bitcoins que posee el canister en nombre del
usuario. El controlador, si es malicioso, puede robar estos activos. En otras
palabras, como usuario, si interactúa con un canister que maneja sus activos,
inspeccione el canister para saber cómo los maneja. Si determina que el canister
almacena activos en sus subcuentas, asegúrese de que el controlador del canister
esté descentralizado.

:::

## Canisters de agujero negro

Un efecto similar también se puede lograr configurando el controlador de un
canister para que sea el propio canister. En este caso, sin embargo, debe
verificar cuidadosamente que el canister no pueda enviar una solicitud para
actualizarse, por ejemplo, emitiendo una solicitud de reinstalación. Aquí, la
inspección del código y las compilaciones reproducibles son cruciales.

Finalmente, una solución algo más útil es transferir el control del canister a
un llamado
[canister de "agujero negro"](https://github.com/ninegua/ic-blackhole). Este
canister solo tiene a sí mismo como controlador, pero permite a terceros obtener
información útil sobre los canisters que controla el agujero negro, como el
saldo de ciclos disponibles de un canister en el agujero negro. Una instancia de
un canister de agujero negro es
[e3mmv-5qaaa-aaaah-aadma-cai](https://icscan.io/canister/e3mmv-5qaaa-aaaah-aadma-cai),
que está [ampliamente documentado](https://github.com/ninegua/ic-blackhole).
Tenga en cuenta que el repositorio vinculado aquí menciona la inmutabilidad del
canister, pero esto es una distracción.

## Verificación de los controladores de un canister

Un usuario puede verificar la lista de controladores de un canister utilizando
[`dfx canister info`](/docs/building-apps/developer-tools/dfx/dfx-canister#dfx-canister-info):

```
dfx canister info <canister-id> --network ic
```

Un usuario también puede obtener la lista de controladores de un canister a
través de una solicitud
[`read_state`](/references/ic-interface-spec.md/#http-read-state) para obtener
la información relevante del
[canister](/references/ic-interface-spec.md#state-tree-canister-information),
que incluye la lista de controladores. Un canister no puede obtener esta
información.

Si un canister no tiene controladores, no se puede cambiar y, por lo tanto, es
inmutable. Solo puede ser desinstalado por el NNS a través de una propuesta del
NNS, asumiendo que se mantiene la integridad de la plataforma.

## Control mediante gobernanza distribuida

Un enfoque más complejo pero poderoso es otorgar el control del canister a una
organización autónoma descentralizada (DAO). Es posible ceder el control a un
[DAO SNS que está integrado en la plataforma](/docs/building-apps/governing-apps/overview)
o construir una gobernanza personalizada. La ventaja de esta última opción es
que la gobernanza del canister se puede adaptar específicamente al canister o
proyecto del que forma parte. Se pueden imaginar diferentes niveles de
complejidad y control que este mecanismo de gobernanza puede implementar. En
ambos casos, los requisitos de confianza se trasladan a la DAO que controla el
canister, donde se aplican todas las consideraciones sobre inspección de código
y reproducibilidad.
