# Consideraciones de arquitectura de aplicaciones

<MarkdownChipRow labels={["Principiante", "Educación", "Concepto"]} />

Una pregunta común al desarrollar una aplicación es cómo y dónde almacenar los
datos. A diferencia de las plataformas tradicionales, ICP no proporciona una
base de datos. En su lugar, ICP puede persistir los cambios en el estado del
<GlossaryTooltip>canister</GlossaryTooltip> utilizando memoria estable. Esto
significa que los desarrolladores tienen mucha libertad para organizar y
almacenar los datos. La práctica recomendada es utilizar bibliotecas ya
existentes, como la biblioteca de
[regiones estables](/docs/motoko/main/stable-memory/stable-regions) de Motoko o
la biblioteca de
[estructuras estables](https://github.com/dfinity/stable-structures) de Rust,
para almacenar datos en la memoria estable.

Otra pregunta que los desarrolladores deben hacerse es cómo estructurar su
aplicación. Es posible construir una aplicación que conste de múltiples
canisters que se comuniquen entre sí. Un error común para los nuevos
desarrolladores es diseñar la aplicación para millones de usuarios desde el
principio sin comprender los compromisos subyacentes del sistema. Es mejor
comenzar con la arquitectura más simple posible y mejorarla de forma iterativa
con el crecimiento de usuarios.

## Arquitectura de un canister por servicio

Los canisters se pueden considerar como microservicios, donde cada canister es
responsable de un servicio específico de la aplicación, como gestionar usuarios,
almacenar datos o procesar datos. Tenga en cuenta que todos los beneficios y
desventajas de la arquitectura de microservicios tradicional también se aplican
aquí. La estructura de proyecto predeterminada generada por
[`dfx new`](/docs/building-apps/developer-tools/dfx/dfx-new) se puede ver como
la arquitectura de microservicios más simple, con el canister de frontend siendo
responsable de servir activos web y el canister de backend siendo responsable de
la lógica principal de la aplicación.

## Arquitectura de un solo canister

Un solo canister puede alojar toda la pila de la aplicación, incluidos sus
activos web, lógica principal y datos. Para escribir un solo canister que aloje
activos de frontend y lógica principal de backend, deberá utilizar una
biblioteca para la API de almacenamiento de activos, como la biblioteca
`ic-certified-assets` para canisters de Rust. Algunos ejemplos de proyectos de
un solo canister incluyen:

- [Ejemplo de saludo HTTPS](https://github.com/krpeacock/server/tree/main/examples/http_greet).

- [Ejemplo de integración de Identidad en Internet](https://github.com/dfinity/internet-identity/tree/main/demos/using-dev-build).

Aunque esta arquitectura es simple, puede escalar a miles de usuarios y
gigabytes de datos.

## Arquitectura de un canister por subred

ICP escala horizontalmente a través de

<GlossaryTooltip>subredes</GlossaryTooltip>, por lo que las aplicaciones también
pueden escalar utilizando más subredes. Una forma de lograr esto es tener uno o
varios canisters por subred y luego fragmentar los datos en estos canisters para
distribuir la carga. Esta es la arquitectura más escalable y, en teoría, podría
admitir millones de usuarios y terabytes de datos. Dado que los datos y la
lógica de la aplicación se distribuyen en múltiples subredes, esto requiere
conocimientos expertos de programación distribuida. El costo de desarrollo y
mantenimiento es mucho mayor en comparación con la arquitectura de un solo
canister.

## Arquitectura de un canister por usuario

Esta arquitectura se basa en la visión de que los usuarios de Web3 deben tener
control total sobre sus datos. La idea es crear un canister por usuario y hacer
que el usuario sea el controlador de su canister. El canister principal de la
aplicación luego orquestará los canisters de usuario para implementar la
funcionalidad de la aplicación. Dado que los usuarios son los controladores de
sus canisters, pueden instalar su propio código, decidir cómo participar en la
aplicación y determinar qué datos compartir. Estos beneficios para los usuarios
conllevan altos costos de desarrollo porque el canister principal debe
programarse de tal manera que pueda manejar todas las acciones posibles de
canisters de usuarios potencialmente maliciosos. Esta es una forma de
programación nueva e sin precedentes. **Todavía no ha habido una implementación
exitosa de esta visión.** Algunos proyectos que optaron por esta arquitectura,
pero solo [NFID Vaults](https://nfidvaults.com) han dado la propiedad de los
canisters a los usuarios. Un error común es pensar que la arquitectura de un
canister por usuario es la más escalable; en realidad, la arquitectura de un
canister por subred es más eficiente porque puede utilizar múltiples subredes
sin tener la sobrecarga de demasiados canisters.
