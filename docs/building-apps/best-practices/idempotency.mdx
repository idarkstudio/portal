# Mejores prácticas para desarrolladores: reintentos seguros e idempotencia

<MarkdownChipRow labels={["Intermedio", "Mejores prácticas"]} />

En caso de problemas de red u otro comportamiento inesperado, los clientes de
ICP (como los agentes) que emiten llamadas de actualización de ingreso pueden no
poder determinar si su solicitud de ingreso ha sido procesada. Por ejemplo, esto
puede suceder si el cliente pierde su conexión hasta que el estado de la
solicitud se haya eliminado del árbol de estado del sistema, ya que ICP
eliminará la solicitud del árbol de estado del sistema algún tiempo después del
vencimiento del ingreso. De manera similar, los canisters que llaman a otros
canisters utilizando llamadas de espera acotada pueden no poder determinar si la
llamada fue exitosa o no.

Esto puede ser arriesgado ya que los llamantes (usuarios externos o aplicaciones
para mensajes de ingreso, o canisters para llamadas entre canisters) podrían
decidir reintentar transacciones, lo que podría llevar a graves vulnerabilidades
de seguridad como el doble gasto.

Por lo tanto, es importante diseñar y/o utilizar APIs de canister de manera que
sea posible reintentar solicitudes de manera segura, incluso cuando ICP no
proporciona información sobre intentos de solicitud anteriores. Esta página
describe enfoques generales que tanto los autores de canisters como los clientes
pueden adoptar para habilitar reintentos seguros.

Por favor, lee la
[referencia sobre mensajes de ingreso](/docs/building-apps/essentials/message-execution)
para aprender sobre los conceptos básicos de mensajería y posibles errores.

## APIs de canister idempotentes

Decimos que un punto de conexión de un canister es idempotente si ejecutarlo
varias veces es equivalente a ejecutarlo una vez.[^1] Cuando un punto de
conexión es idempotente o puede hacerse idempotente por el desarrollador, esto
proporciona una forma fácil de implementar reintentos seguros.

Dado un punto de conexión idempotente, puedes implementar reintentos desde una
aplicación externa volviendo a intentar la llamada hasta que observes una
respuesta certificada, ya sea un estado de respuesta o rechazo; consulta la
ilustración a continuación. Si alguna vez se observa una respuesta de este tipo,
es seguro que la transacción se ha ejecutado al menos una vez, lo que, gracias a
la idempotencia, tiene el mismo resultado que ejecutarla exactamente una vez.
Sin embargo, es posible que la aplicación no esté dispuesta a esperar una
respuesta indefinidamente y se pueda implementar un tiempo de espera. Al vencer
el tiempo de espera, se debe mostrar un error al usuario indicándole que espere
hasta que el último mensaje que se haya enviado haya expirado (según lo definido
por el `ingress_expiry` de la solicitud) y luego verifique manualmente el estado
de la transacción. Idealmente, los tiempos de espera deberían ser raros y no
ocurrir durante el funcionamiento normal.

![Reintentando una llamada idempotente](/img/docs/retry_idempotency.png)

La situación es similar para las llamadas entre canisters con espera acotada.
Dado un punto de conexión idempotente, el canister que realiza la llamada puede
seguir intentando hasta que se observe una respuesta distinta de `SYS_UNKNOWN`,
o rendirse después de un tiempo de espera si esperar indefinidamente no es una
opción.

A continuación se presentan dos enfoques para hacer que los puntos de conexión
sean idempotentes: números de secuencia y deduplicación de ID (ventana de
tiempo).

### Números de secuencia de actualización

Un punto de conexión puede utilizar números de secuencia para proporcionar
idempotencia al tomar un parámetro de número de secuencia además de otros
parámetros. En el caso extremo, un canister podría mantener un solo número de
secuencia esperado para cada punto de conexión, y una llamada solo se aceptaría
si contenía el siguiente número de secuencia esperado, lo que haría que el
número de secuencia esperado se incrementara al ejecutar la llamada. Esto
implica trivialmente que cualquier llamada solo se puede ejecutar una vez. De
manera más práctica, se mantiene un número de secuencia esperado para cada
principal del llamante, o, en el caso de canisters similares a los libros de
contabilidad, para cada cuenta del libro de contabilidad. Ten en cuenta que
Ethereum implementa este mecanismo.

Las ventajas de este enfoque son:

1. Los números de secuencia son simples de implementar y entender.
2. Cuando corresponde, tiene una huella de memoria modesta porque solo se debe
   almacenar el siguiente número de secuencia esperado (por ejemplo, por cuenta
   activa).

El enfoque también tiene algunas desventajas:

1. Limita el rendimiento. Cuando se utilizan números de secuencia por llamante,
   significa que el llamante generalmente solo puede realizar una llamada de
   ingreso por bloque de consenso, lo que se traduce en un rendimiento de
   aproximadamente 1 llamada de ingreso por segundo para ese usuario. La
   situación es mejor para las llamadas entre canisters, ya que las solicitudes
   (si se entregan) se entregarán en el orden en que se enviaron. Por lo tanto,
   el canister que realiza la llamada puede emitir múltiples solicitudes
   simultáneamente, utilizando números de secuencia adecuados. Bajo carga
   normal, todas las solicitudes deberían entregarse. Sin embargo, bajo una
   carga pesada donde el sistema puede descartar algunas solicitudes, las
   solicitudes que siguen a una solicitud descartada pueden volverse inválidas.

2. Limita la concurrencia. El usuario debe secuencializar todas sus llamadas.
   Esto es fácil de hacer cuando el usuario es otro canister, pero puede ser
   mucho más difícil cuando el canister se llama a través de mensajes de
   ingreso. En particular, es complicado cuando el usuario utiliza múltiples
   clientes o dispositivos para acceder al canister, por ejemplo. Este problema
   de concurrencia también hace que el enfoque no sea aplicable en casos en los
   que se permite a los usuarios anónimos activar llamadas de actualización.

3. Si el número de secuencia se almacena por usuario o por cuenta, rastrearlos
   para demasiados usuarios puede agotar la memoria del canister, incluso si
   cada número individual es pequeño. Esto podría ser explotado por un atacante
   para agotar la memoria. Por lo tanto, el enfoque es más adecuado para casos
   en los que el usuario debe pagar por el uso de alguna manera (por ejemplo,
   los libros de contabilidad suelen requerir una tarifa tanto para crear una
   cuenta como para transferir fondos), lo que dificulta a los atacantes al
   requerirles que inviertan fondos significativos en un ataque.

### Deduplicación de ID

Otro enfoque para la idempotencia es hacer que las llamadas sean únicamente
identificables en el lado del canister receptor (por ejemplo, mediante el uso de
IDs elegidos por el usuario, números de secuencia o una combinación de varios
campos de argumentos) para asegurarse de que una llamada dada se ejecute como
máximo una vez. Luego, el canister deduplica las llamadas antes de ejecutarlas;
si se ha ejecutado una llamada con el mismo ID anteriormente, se ignora
simplemente la nueva llamada (devolviendo potencialmente el resultado de la
llamada anterior). De esta manera, el usuario puede volver a intentar la llamada
de manera segura hasta que obtenga una respuesta.

Por ejemplo, el estándar de libro de contabilidad ICRC proporciona deduplicación
de esta manera. El uso de valores idénticos para todos los parámetros de
llamada, incluidos los parámetros `created_at_time` y `memo`, al emitir una
transacción hace que la llamada de transacción sea idempotente mediante la
deduplicación de llamadas con los mismos parámetros.

Sin embargo, una implementación ingenua de este enfoque puede agotar la memoria
del canister, ya que todos los IDs ejecutados con éxito deben mantenerse
indefinidamente. Por lo tanto, la deduplicación generalmente se limita a una
ventana de tiempo determinada. Por ejemplo, el libro de contabilidad ICP utiliza
una ventana de 24 horas, y el estándar ICRC define un parámetro de configuración
`TX_WINDOW` que determina la duración de la ventana.

Además, los libros de contabilidad ICP/ICRC utilizan el parámetro
`created_at_time` para limitar el período de validez de una llamada. En términos
generales, la llamada solo se considera válida si su `created_at_time` no está
en el futuro y como máximo 24 horas en el pasado.[^2] Esto evita el problema de
que la ventana de deduplicación expire y permita que una llamada reintentada
tenga éxito nuevamente.

Pero incluso con esta mejora utilizada en los libros de contabilidad, el enfoque
de ventana de tiempo asume implícitamente que el cliente podrá obtener una
respuesta definitiva a su llamada dentro de la ventana de tiempo. Por ejemplo,
después de que expiren las 24 horas, el usuario no puede determinar fácilmente
si se realizó su transferencia de libro de contabilidad; su única opción es
analizar los bloques del libro de contabilidad, lo cual es algo tedioso y debe
hacerse con cuidado para evitar problemas de asincronía; consulta la sección
sobre
[resultados de llamadas consultables](#resultados-de-llamadas-consultables).

Confiar únicamente en una ventana de tiempo para la deduplicación no garantiza
el uso limitado de memoria. En teoría, un número ilimitado de actualizaciones
podría ocurrir dentro de la ventana de tiempo, aunque en la práctica esto está
limitado por los límites de escalabilidad de ICP. Los libros de contabilidad
ICP/ICRC también definen una capacidad máxima: un límite en la cantidad de
transacciones deduplicadas (es decir, IDs de deduplicación) que se pueden
almacenar en su almacén de deduplicación. Una vez que se alcanza esta capacidad,
se rechazan las transacciones adicionales hasta que las transacciones más
antiguas expiren del almacén de deduplicación al final de la ventana de tiempo.
Otra extensión del enfoque es garantizar la deduplicación para la ventana de
tiempo indicada anteriormente, pero seguir almacenando los IDs de deduplicación
incluso más allá de esa ventana, siempre que no se alcance la capacidad. De esta
manera, los clientes obtienen una garantía de deduplicación sólida para la
ventana de tiempo y un intento de deduplicación de transacciones incluso después
de la ventana.

Una alternativa es prescindir de la ventana de tiempo y almacenar los datos de
deduplicación para siempre. Esto requiere almacenar estos datos en múltiples
canisters para evitar agotar la memoria del canister, de manera similar a cómo
los libros de contabilidad ICP/ICRC almacenan los datos de transacciones en el
canister de archivo. Esto traslada la parte tediosa de consultar los datos de
deduplicación (por ejemplo, bloques de libro de contabilidad) del usuario al
canister.

En resumen, las ventajas de este enfoque son:

1. Puede admitir un alto rendimiento.
2. No requiere sincronización por parte del usuario y admite casos de uso como
   múltiples dispositivos.

Las desventajas son:

1. Es más complicado de implementar que los números de secuencia.
2. Si se utiliza una ventana de tiempo, generalmente asume implícitamente que el
   usuario conoce el resultado de la llamada dentro de la ventana de tiempo.
3. El uso de memoria puede aumentar considerablemente con un alto rendimiento
   admitido y ventanas de deduplicación largas. Por ejemplo, admitir 100
   transacciones por segundo con una ventana de deduplicación de 24 horas puede
   requerir cientos de megabytes de espacio en el montón. Esto se puede mitigar
   utilizando múltiples canisters para almacenar los datos de deduplicación, a
   expensas de una mayor complejidad de implementación y mayor latencia.

## Otros enfoques para reintentos seguros

En ausencia de puntos de conexión idempotentes, o incluso además de ellos, los
clientes pueden utilizar otros puntos de conexión para hacer que sus reintentos
sean seguros.

### Resultados de llamadas consultables

Si el canister, además del punto de conexión de actualización, también expone
una consulta que puede informar al usuario sobre el resultado de la
actualización, el cliente también puede utilizar esto para reintentos seguros de
la siguiente manera:

1. Intentar realizar la actualización.
2. Si el resultado de la actualización es desconocido (por ejemplo, no está
   presente en el historial de ingreso, o se devuelve un error `SYS_UNKNOWN`
   para una llamada entre canisters), consultar el punto de conexión de
   resultado de llamada para determinar si la actualización se aplicó o no.
   Además, es necesario asegurarse de que la llamada enviada anteriormente no se
   pueda aplicar en el futuro. Si ambas condiciones son verdaderas, la llamada
   se puede reintentar o informar de manera segura como fallida.

En la práctica, este patrón puede ser más complicado. Por ejemplo, el libro de
contabilidad ICP expone un método `query_blocks` que se puede utilizar para
implementar el patrón anterior para transferencias iniciadas como mensajes de
ingreso:

1. Llamar al método `query_blocks` en el libro de contabilidad para determinar
   cuál es el último bloque (según se especifica en el campo `chain_length` de
   la respuesta) en ese momento. Llamémoslo `last_block`.
2. Intentar realizar una transferencia. Este mensaje de ingreso incluye un campo
   `ingress_expiry`.
3. Si el resultado de la transferencia es desconocido, asegurarse de que la
   transferencia no se aplicará en un momento posterior:
   - Si se utilizan mensajes de ingreso, llamar al punto de conexión
     `read_state` en el canister del libro de contabilidad para obtener la rama
     `/time` del árbol de estado del sistema. Repetir esto hasta que el tiempo
     informado supere el tiempo `ingress_expiry`.
   - Si se utilizan llamadas entre canisters, realizar todas las llamadas
     subsiguientes (`query_blocks`) enumeradas a continuación desde el mismo
     canister que inició la transferencia. Las
     [garantías de ordenamiento](/docs/references/message-execution-properties)
     aseguran que la transferencia no pueda ocurrir más tarde.
4. Llamar nuevamente al método `query_blocks` en el libro de contabilidad para
   recuperar todos los bloques del libro de contabilidad desde `last_block` y
   verificar que la `timestamp` también supere el tiempo `ingress_expiry`. En
   caso de fallo, reintentar hasta obtener un resultado. Luego, examinar los
   bloques devueltos para determinar si la transacción se ha incluido o no.

### Transferencias de 2 pasos

Otro enfoque aplicable a los libros de contabilidad (como ICRC-1 o ICP) es
realizar transferencias en dos pasos:

1. Primero, transferir los tokens a una subcuenta intermedia del remitente que
   sea específica para esta transacción. Por ejemplo, si la transacción tiene un
   ID único, el cliente puede aplicar una función hash al ID para obtener una
   subcuenta. La cantidad transferida debe ser la cantidad deseada más la tarifa
   de transacción del libro de contabilidad.
2. Si el resultado de la transferencia anterior es desconocido, consultar el
   saldo de la subcuenta específica de la transacción. Al igual que en el
   enfoque de
   ["resultados de llamadas consultables"](#resultados-de-llamadas-consultables),
   si se utilizan mensajes de ingreso, esto debe repetirse hasta que la
   `timestamp` que acompaña la respuesta supere el `ingress_expiry`. Si el saldo
   es 0, la transacción se puede informar de manera segura como fallida, o se
   puede reintentar (comenzando desde el paso 1). Si el saldo es al menos el
   saldo esperado, se puede proceder.
3. Si la transferencia a la subcuenta específica de la transacción se realizó
   correctamente (según se determine tanto por el resultado de la transferencia
   como por la consulta de saldo anterior), el cliente envía otra transferencia
   desde la subcuenta específica de la transacción a la cuenta de destino
   deseada. Esto se puede repetir tantas veces como sea necesario hasta que se
   conozca un resultado de la llamada. Una vez que se conoce un resultado, la
   transferencia general se puede declarar como exitosa, incluso si este paso
   falla con un error, ya que esto indica que algún intento anterior de
   transferir el dinero al destino tuvo éxito.

[^1]:
    "Equivalente" se entiende desde la perspectiva del usuario aquí. Múltiples
    ejecuciones pueden desencadenar cambios como los del saldo del ciclo del
    canister, pero no son relevantes para el usuario.

[^2]:
    Más precisamente, el libro de contabilidad también permite una pequeña
    deriva de tiempo de `created_at_time` hacia el futuro, lo cual debe tenerse
    en cuenta al limpiar la ventana de deduplicación.
