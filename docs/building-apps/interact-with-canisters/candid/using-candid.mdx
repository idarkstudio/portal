# Usando Candid

<MarkdownChipRow labels={["Principiante", "Tutorial"]} />

Candid proporciona una forma independiente del lenguaje para interactuar con

<GlossaryTooltip>canisters</GlossaryTooltip>.

:::info

Aunque Candid es una forma robusta, segura por tipos y a prueba de futuro para
facilitar la comunicación entre canisters, no es obligatorio. Se pueden
intercambiar bytes arbitrarios si todos los canisters que forman parte del flujo
de comunicación están diseñados para entenderlos (de modo que usen el mismo
protocolo subyacente, escrito en el mismo lenguaje, etc.).

[Aprende más en la documentación de referencia de Candid](/docs/references/candid-ref).

:::

Al usar Candid, puedes especificar valores de argumentos de entrada y mostrar
valores de retorno de los métodos de canister sin importar si interactúas con
ICP desde un terminal usando el SDK de IC, a través de un navegador web, o desde
un programa escrito en JavaScript, Motoko, Rust o cualquier otro lenguaje.

## El archivo `.did`

Los tipos de Candid pueden usarse para describir un servicio a través de un
archivo de descripción de servicio Candid (`.did`), el cual puede ser escrito
manualmente o generado desde una implementación de servicio.

### Archivos `.did` auto-generados

Si escribes un canister en Motoko, el compilador genera automáticamente una
descripción Candid cuando compilas el programa. Si usas `dfx`, normalmente verás
los archivos `.did` auto-generados en el directorio `/declarations` de tu
proyecto. Dado que estos archivos son auto-generados, se recomienda no editarlos
manualmente; serán sobrescritos en la siguiente ejecución de `dfx build`.

Para los canisters escritos en Rust, se puede usar la herramienta extractora de
Candid con las versiones del Rust [IC CDK](https://crates.io/crates/ic-cdk)
`0.11.0` y posteriores. Consulta las instrucciones completas para usar el
[extractor de Candid](/docs/building-apps/developer-tools/cdks/rust/generating-candid).

### Escribiendo archivos `.did`

Para otros lenguajes, tendrás que escribir manualmente la descripción de la
interfaz Candid. Define un servicio, luego agrega el nombre de un método
público, seguido de los tipos de datos que el método acepta y retorna:

Aquí hay un ejemplo que define el método público `greet`, que acepta el tipo
`text` y retorna el tipo `text` utilizando una llamada de consulta.

```candid
service : {
    "greet" : (text) -> (text) query;
};
```

[Aprende más sobre los tipos de datos soportados en la documentación de referencia de Candid](/docs/references/candid-ref#supported-types).

### Dividiendo descripciones de interfaces en múltiples archivos (Motoko)

En algunos flujos de trabajo, puede ser beneficioso dividir las descripciones de
interfaces en múltiples archivos `.did`. Por ejemplo, un archivo puede ser usado
para definir las definiciones de tipo que son utilizadas por varios canisters,
mientras que otro archivo se usa para definir el servicio principal de uno de
esos canisters.

Puedes importar ambas descripciones de interfaz en tu canister con dos
sentencias de importación:

```motoko no-repl
import A "a.did";  // Importa solo definiciones de tipo
import service B "b.did";  // Importa tanto definiciones de tipo como servicio principal
```

## `InitArgs` del servicio

Considera la siguiente definición de servicio:

```
service : (InitArgs) -> {
   ...
};

```

Esta definición puede considerarse como una configuración de despliegue. Para
inicializar este servicio, debes suministrar `(InitArgs)` como un argumento de
`init`.

Un ejemplo de esta definición de servicio se puede encontrar en el
[archivo Candid del canister EVM RPC](https://github.com/internet-computer-protocol/evm-rpc-canister/blob/main/candid/evm_rpc.did#L253).

## Nombrando los argumentos y resultados

Nombrar los argumentos o resultados de un método es puramente para fines de
documentación. El nombre que uses no cambia el tipo del método ni los valores
que se pasan. En cambio, los argumentos y resultados se identifican por su
**posición**, independientemente del nombre. Esto es muy diferente de los campos
**nombrados** de un **registro**, los cuales son semánticamente relevantes.

## Reutilizando tipos complejos

A menudo, múltiples métodos en un servicio pueden hacer referencia al mismo tipo
complejo. En ese caso, el tipo puede ser nombrado y reutilizado múltiples veces.
Por ejemplo:

```candid
type address = record {
  street : text;
  city : text;
  zip_code : nat;
  country : text;
};
service address_book : {
  set_address: (name : text, addr : address) -> ();
  get_address: (name : text) -> (opt address) query;
}
```

Estas definiciones de tipo simplemente abrevian un tipo **existente**; no
definen un nuevo tipo. No importa si usas `address` en la firma de la función o
escribes los registros. Además, dos abreviaturas con diferentes nombres pero
definiciones equivalentes describen el mismo tipo y son intercambiables. En
otras palabras, Candid usa tipado **estructural**.

## Especificando un método de consulta

En el último ejemplo, podrías haber notado el uso de la anotación `query` para
el método `get_address`. Por ejemplo:

```candid
service address_book : {
  set_address: (name : text, addr : address) -> ();
  get_address: (name : text) -> (opt address) query;
}
```

Esta anotación indica que el método `get_address` puede ser invocado como una
**consulta** de ICP. Como se discute en
[métodos de consulta y actualización](/docs/building-apps/interact-with-canisters/advanced-calls),
una consulta proporciona una forma eficiente de recuperar información de un
canister sin pasar por el consenso, por lo que poder identificar un método como
consulta es una de las principales ventajas de usar Candid para interactuar con
ICP.

## Codificación y decodificación

El objetivo de Candid es permitir la invocación continua de los métodos del
servicio, pasando argumentos codificados a un formato binario y transferidos por
un método de transporte subyacente (como mensajes hacia o dentro de Internet
Computer) y decodificados en el otro lado.

Como usuario de Candid, no tienes que preocuparte por los detalles de este
formato binario. Si planeas **implementar** Candid tú mismo (por ejemplo, para
soportar un nuevo lenguaje host), puedes consultar la
[especificación de Candid](https://github.com/dfinity/candid) para más detalles.
Sin embargo, algunos aspectos del formato son importantes saber:

- El formato binario de Candid comienza con `DIDL…` (o, en hex, `4449444c…`). Si
  ves esto en alguna salida de registro de bajo nivel, es muy probable que estés
  observando un valor codificado en Candid.

- El formato binario de Candid siempre codifica _secuencias_ de valores, porque
  los parámetros y resultados de los métodos son secuencias de tipos.

- El formato binario es bastante compacto. Un `(vec nat64)` con 125_000 entradas
  ocupa 1_000_007 bytes.

- El binario es auto-descriptivo e incluye una descripción (condensada) del tipo
  de los valores que contiene. Esto permite que el lado receptor detecte si un
  mensaje fue enviado como un tipo diferente e incompatible.

- Mientras el emisor serialice los argumentos como el tipo que el lado receptor
  espera, la deserialización tendrá éxito.

## Actualizaciones de servicio

Los servicios evolucionan con el tiempo; ganan nuevos métodos, los métodos
existentes devuelven más datos o esperan argumentos adicionales. Normalmente,
los desarrolladores querrán hacerlo sin romper los clientes existentes.

Candid soporta tal evolución definiendo reglas precisas que indican cuándo el
nuevo tipo de servicio podrá seguir comunicándose con todas las demás partes que
usan la descripción de la interfaz anterior. La formalidad subyacente es la de
_subtipado_.

Los servicios pueden evolucionar de manera segura de las siguientes formas:

- Se pueden agregar nuevos métodos.

- Los métodos existentes pueden devolver valores adicionales; es decir, la
  secuencia de tipos de resultado puede extenderse. Los clientes antiguos
  simplemente ignorarán los valores adicionales.

- Los métodos existentes pueden reducir su lista de parámetros. Los clientes
  antiguos aún pueden enviar los argumentos extra, pero serán ignorados.

- Los métodos existentes pueden extender su lista de parámetros con argumentos
  opcionales (tipo `opt …`). Al leer mensajes de clientes antiguos, que no pasan
  ese argumento, se asume un valor `null`.

- Los tipos de los parámetros existentes pueden ser _cambiados_, pero solo a un
  _supertipo_ del tipo anterior.

- Los tipos de resultados existentes pueden ser _cambiados_, pero solo a un
  _subtipo_ del tipo anterior.

Para información sobre los supertipos y subtipos de un tipo dado, consulta la
correspondiente [referencia](/docs/references/candid-ref) para ese tipo.

Veamos un ejemplo concreto de cómo un servicio podría evolucionar. Considera un
servicio con la siguiente API:

```candid
service counter : {
  add : (nat) -> ();
  subtract : (nat) -> ();
  get : () -> (int) query;
  subscribe : (func (int) -> ()) -> ();
}
```

Este servicio puede evolucionar a la siguiente interfaz:

```candid
type timestamp = nat;
service counter : {
  set : (nat) -> ();
  add : (int) -> (new_val : nat);
  subtract : (nat, trap_on_underflow : opt bool) -> (new_val : nat);
  get : () -> (nat, last_change : timestamp) query;
  subscribe : (func (nat) -> (unregister : opt bool)) -> ();
}
```

### Valores textuales en Candid

El propósito principal de Candid es conectar programas escritos en algún
lenguaje anfitrión (como Motoko, Rust o JavaScript) con ICP. En la mayoría de
los casos, no es necesario tratar los datos de tu programa como valores Candid.
En su lugar, trabajas con un lenguaje anfitrión como JavaScript usando valores
familiares de JavaScript y luego confías en Candid para transportar esos valores
al canister escrito en Rust o Motoko. El canister receptor de los valores los
trata como valores nativos de Rust o Motoko.

Sin embargo, hay algunos casos, como cuando se registran eventos, se depura o se
interactúa con un servicio desde la línea de comandos, donde puede ser útil ver
los valores de Candid directamente en una forma legible para los humanos. En
estos escenarios, puedes usar la **presentación textual** para los valores de
Candid.

La sintaxis es similar a la de los tipos Candid. Por ejemplo, una presentación
textual típica de un valor Candid podría verse de la siguiente manera:

```candid
(record {
  first_name = "John";
  last_name = "Doe";
  age = 41;
  membership_status = variant { active };
  email_addresses =
    vec { "john@doe.com"; "john.doe@example.com" };
})
```

:::info

El formato **binario** de Candid no incluye los nombres reales de los campos,
sino solo **hashes** numéricos. Por lo tanto, al imprimir de forma legible un
valor sin conocer el tipo esperado, no se incluirán los nombres de los campos de
los registros y variantes. El valor anterior podría ser impreso de la siguiente
manera:

```candid
(record {
   4846783 = 14;
   456245371 = variant {373703110};
   1443915007 = vec {"john@doe.com"; "john.doe@example.com"};
   2797692922 = "John"; 3046132756 = "Doe"
})
```

:::

### Mejores prácticas

#### Usa nombres descriptivos para los tipos

Es recomendable usar registros de Candid con nombres descriptivos para los
tipos:

```candid
type Recycler =
 record {
   identity: principal;
   location: record {
               Country__1; // <-- Usa nombres descriptivos para los tipos,
               text; // <----- En lugar de términos genéricos.
             };
   name: text;
   nick: text;
 };
```

#### Deprecación de campos

Para descontinuar un campo de Candid, puedes actualizar su tipo a `opt empty`,
lo que indica que el campo ya no se utiliza:

```
record {
  first_name : text; middle_name : opt empty; second_name : text; score : nat; country : text
}
```

Sin embargo, es una buena práctica marcar un campo como `reserved` para evitar
que futuros desarrolladores lo utilicen de manera inesperada:

```
record {
  first_name : text; middle_name : reserved; second_name : text; score : nat; country : text
}
```

Para más información, consulta la entrada del blog sobre
[Candid para ingenieros](https://mmapped.blog/posts/20-candid-for-engineers#faq).

### Interactuar con un servicio

#### Línea de comandos

Para interactuar con un servicio, usa el comando
[`dfx canister call`](/docs/building-apps/developer-tools/dfx/dfx-canister#dfx-canister-call).

Para pasar argumentos Candid al comando `dfx canister call`, consulta la
[referencia de Candid](/docs/references/candid-ref), o si los argumentos de
Candid son demasiado largos para caber en la línea de comandos, usa la opción
`--argument-file`.

También puedes omitir los argumentos y dejar que el SDK de ICP genere un valor
aleatorio que coincida con el tipo del método.

#### Navegador

El lenguaje de descripción de interfaces Candid proporciona un lenguaje común
para especificar la firma de un canister. Según la firma de tipo del servicio
ofrecido por el contrato inteligente, Candid proporciona una interfaz web (la UI
de Candid) que permite llamar a funciones de canister para pruebas y depuración
desde un navegador web sin necesidad de escribir código frontend.

Cuando un canister se despliega, devolverá una URL de la UI de Candid como parte
de la salida, indicada como la "URL del canister backend". La URL completa
debería verse de la siguiente manera, pero con el `canister_id` reflejando el ID
de tu proyecto.

```
http://127.0.0.1:4943/?canisterId=<canister_id> // URL local
https://a4gq6-oaaaa-aaaab-qaa4q-cai.icp0.io/?id=ts425-saaaa-aaaab-qbksq-cai // URL en el Playground o en la red principal
```

Para más información sobre la herramienta que crea una interfaz web a partir de
la interfaz Candid de cualquier canister, consulta el repositorio de
[UI de Candid](https://github.com/dfinity/candid/tree/master/tools/ui).

:::caution

En este momento, no es posible deshabilitar la instalación y despliegue de la UI
de Candid para tu canister.

:::

#### Interactuar con un servicio desde un canister de Motoko

Si estás escribiendo un canister en Motoko, el compilador de Motoko traduce
automáticamente la firma del `actor` o `actor class` de nivel superior de tu
canister en una descripción Candid, y el comando `dfx build` asegura que la
descripción del servicio se haga referencia correctamente donde sea necesario.
Asegura que el identificador del canister y la descripción Candid se pasen
correctamente al compilador de Motoko. El compilador de Motoko luego traduce el
tipo Candid al tipo nativo de Motoko. Para obtener más información sobre el
mapeo de tipos entre Candid y Motoko, puedes consultar la
[referencia de tipos soportados](/docs/references/candid-ref).

Los canisters de Motoko generan automáticamente un archivo de descripción
Candid, ubicado en el directorio de tu proyecto en
`.dfx/local/canisters/hello/hello.did`.

#### Interactuar con un servicio desde un canister de Rust

Si escribes un canister en Rust, el comando `dfx build` asegura que la
descripción del servicio se haga referencia correctamente donde sea necesario.
Sin embargo, necesitas escribir manualmente la descripción del servicio Candid,
siguiendo las convenciones descritas en la
[especificación de Candid](https://github.com/dfinity/candid/blob/master/spec/Candid.md#core-grammar).

El CDK de Rust luego traduce el tipo Candid al tipo nativo de Rust. Esta
traducción te permite llamar al método del canister de manera nativa. Para
obtener más información sobre el mapeo de tipos entre Candid y Rust, puedes
consultar la [referencia de tipos soportados](/docs/references/candid-ref).

También hay una característica experimental para generar automáticamente una
descripción de servicio Candid; consulta este
[caso de prueba](https://github.com/dfinity/candid/blob/master/rust/candid/tests/types.rs#L99)
como ejemplo.

Para más información y bibliotecas que te ayuden a crear servicios o canisters
Candid en Rust, consulta la documentación del
[crate de Candid](https://docs.rs/candid/),
[ejemplos de CDK en Rust](https://github.com/dfinity/cdk-rs/tree/main/examples)
y
[los tutoriales de Rust](/docs/building-apps/developer-tools/cdks/rust/intro-to-rust).

#### Interactuar con un servicio desde JavaScript

El paquete npm de [dfinity/agent](https://www.npmjs.com/package/@dfinity/agent)
incluye soporte para importar canisters utilizando Candid.

Cuando la dependencia de importación de un canister es procesada por el comando
`dfx build` y la configuración de `webpack`, este procesamiento asegura que el
identificador del canister y la descripción Candid se pasen correctamente al
programa de JavaScript. En segundo plano, la descripción Candid del servicio se
traduce en un módulo de JavaScript, ubicado en
`.dfx/local/canister/counter/counter.did.js` por `dfx build`. El paquete
`dfinity/agent` luego traduce el tipo Candid en valores nativos de JavaScript y
te permite llamar al método del canister de manera nativa. Para obtener más
información sobre el mapeo de tipos entre Candid y JavaScript, consulta la
[referencia de tipos soportados](/docs/references/candid-ref).

### Publicar interfaces Candid de forma privada

Por defecto, `dfx` hace pública la información de metadatos `candid:service`
para promover la interoperabilidad y facilitar el uso de la UI de Candid. La UI
de Candid lee estos metadatos para determinar la interfaz de tu canister. No
publica más información de la que ya es pública. Esta metadata puede ser
devuelta mediante el comando
[`dfx canister metadata`](/docs/building-apps/developer-tools/dfx/dfx-canister#dfx-canister-metadata):

```
dfx canister metadata <canister_id> candid:service
```

Sin embargo, puedes hacer que esta información de metadatos sea privada para que
solo sea accesible por los controladores de tu canister. Para hacerlo, agrega la
siguiente configuración a la definición de tu canister en el archivo `dfx.json`
de tu proyecto:

```json title="dfx.json"
      "metadata": [
        {
          "name": "candid:service",
          "visibility": "private"
        }
      ]
```

Luego, vuelve a desplegar tu canister y confirma que la interfaz ya no es
pública.

### Crear una nueva implementación de Candid

Existen bibliotecas comunitarias de Candid para los siguientes lenguajes
anfitriones:

- [AssemblyScript](https://github.com/rckprtr/cdk-as/tree/master/packages/cdk/assembly/candid)
- [C#/.NET](https://github.com/BoomDAO/ICP.NET/tree/main/src/Candid)
- [Elm](https://github.com/chenyan2002/ic-elm/)
- [Haskell](https://hackage.haskell.org/package/candid)
- [Java](https://github.com/ic4j/ic4j-candid)
- [Kotlin](https://github.com/seniorjoinu/candid-kt)

Si deseas crear una implementación de Candid para un lenguaje o herramienta para
la cual aún no existe una implementación, debes consultar la
[especificación de Candid](https://github.com/dfinity/candid/blob/master/spec/Candid.md).

Si agregas una implementación de Candid para un nuevo lenguaje o herramienta,
puedes usar los
[datos de prueba oficiales de Candid](https://github.com/dfinity/candid/tree/master/test)
para probar y verificar que tu implementación sea compatible con Candid, incluso
en casos algo más complejos.
