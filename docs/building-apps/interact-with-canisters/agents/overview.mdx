# Agentes

<MarkdownChipRow labels={["Intermedio", "Agentes"]} />{" "}

En el ecosistema de Internet Computer, una biblioteca utilizada para realizar
llamadas a la interfaz pública de ICP se denomina **agente**. Un agente tiene
varias responsabilidades clave, lo que lo hace conveniente para trabajar en el
lenguaje de tu elección.

Si tienes un canister en ejecución, ya sea en tu máquina local o en vivo en
Internet Computer, tendrás dos formas principales de interactuar con tu contrato
inteligente:

1. Usando la API v2 con un agente que sigue la especificación de la interfaz.
2. Usando la interfaz HTTPS del canister.

Los contratos inteligentes pueden definir sus propias API utilizando el **Candid
Interface Declaration Language (IDL)** y responderán a llamadas a través de la
API pública.

ICP admite dos tipos de llamadas: `queries` y `updates`.

- **Queries**: Son rápidas y no pueden modificar el estado del canister.
- **Updates**: Requieren consenso y tardan entre 2 y 4 segundos en completarse.

Debido a la latencia de las actualizaciones, las mejores prácticas para modelar
el rendimiento de tu aplicación sugieren realizar actualizaciones de forma
**asíncrona** y anticipada.

Si puedes realizar una actualización por adelantado y almacenarla en la memoria
de tu canister, los usuarios tendrán una mejor experiencia al solicitar esos
datos.  
Asimismo, si tu aplicación necesita realizar una actualización, es recomendable
evitar bloquear la interacción mientras se lleva a cabo.  
Utiliza **renderizado optimista** siempre que sea posible y continúa con la
ejecución de la aplicación como si la llamada ya hubiera tenido éxito.

## Qué hace un agente

### Estructuración de datos

Cuando un agente realiza una llamada a un canister en ICP, envía una solicitud
`POST` a  
`/api/v2/canister/<effective_canister_id>/call`, que incluye los siguientes
componentes:

- `request_type`
- Autenticación
  - `sender`, `nonce` y `ingress_expiry`
- `canister_id`
- `method_name`
- `request_id`: Requerido para llamadas de tipo `update`.
- `arg`: El resto de la carga útil.

Al conocer la interfaz Candid del canister, el agente ensamblará el campo
`"arg"` con datos de la aplicación cliente, asegurándose de que coincida con la
interfaz Candid del método que se llamará. Luego, todos los componentes
anteriores se ensamblan en un certificado, que se transforma en un buffer
codificado en CBOR.

Para solicitudes de tipo `update`, el agente también genera un hash con el resto
de los campos y lo pasa como un `request_id` único. Este `request_id` se usa
para la consulta mientras ICP alcanza consenso sobre la actualización.

El agente toma el certificado codificado en CBOR y lo adjunta al cuerpo de la
solicitud `POST`. El canister procesará la solicitud de forma asíncrona, y el
agente podrá comenzar a hacer consultas con `read_state` hasta que la respuesta
del canister esté lista.

### Decodificación de datos

Una vez que ICP devuelve los datos, el agente extrae el certificado de la carga
útil y lo verifica. El certificado puede autenticarse como genuino utilizando la
clave pública `rootKey` de la subred NNS.

La red responderá con un buffer codificado en CBOR, que el agente podrá
decodificar y transformar en una estructura útil utilizando tipos semánticos
específicos del lenguaje. Por ejemplo, si el tipo devuelto por el canister es
`text`, se convertirá en un `string` en JavaScript, y así sucesivamente.

### Gestión de autenticación

Las llamadas a Internet Computer siempre deben incluir una identidad
criptográfica adjunta. Esta identidad puede ser **anónima** o **autenticada**,
utilizando una firma criptográfica.

Dado que las identidades son obligatorias, los canisters pueden utilizar la
identidad adjunta a una llamada para decidir cómo responder. Esto permite que
los contratos usen esas identidades para otros propósitos.

#### Identidades aceptadas

ICP acepta llamadas con los siguientes tipos de firmas en las identidades:

- [Ed25519](https://ed25519.cr.yp.to/index.html)
- [ECDSA](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.186-4.pdf)
  - En la curva P-256 (también conocida como `secp256r1`), usando `SHA-256` como
    función hash.
  - En la curva Koblitz `secp256k1`.

Las firmas simples están soportadas para estos esquemas.

Al codificar estas identidades como un `principal`, los agentes adjuntan un byte
de sufijo que indica si la identidad es **autenticada** o **anónima**.

- Una identidad **autenticada** utilizando una de las curvas mencionadas tendrá
  un sufijo de `2`.
- Una identidad **anónima** es representada por un solo byte `4`, lo que en su
  codificación textual se resuelve como `"2vxsx-fae"`.
