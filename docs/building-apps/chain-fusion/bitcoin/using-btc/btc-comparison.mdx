# Comprendiendo ICP para desarrolladores de Bitcoin

<MarkdownChipRow labels={["Intermedio", "Bitcoin"]} />

Esta guía está diseñada para ayudar a los desarrolladores de Bitcoin a
comprender los conceptos fundamentales de ICP para poder utilizarlo
correctamente como una solución de Capa 2 para Bitcoin.

## Mapeo de terminología

ICP utiliza una terminología diferente para conceptos similares a los de
Bitcoin. Esta tabla resume las principales diferencias terminológicas entre
Bitcoin e ICP:

| Término de Bitcoin | Término de ICP |
| ------------------ | -------------- |
| Account            | Principal      |

Además, ICP ha implementado estándares de tokens similares a los de Bitcoin:

| Estándar de Bitcoin | Estándar de ICP                                                                      |
| ------------------- | ------------------------------------------------------------------------------------ |
| BRC-20              | [ICRC-1/ICRC-2](../../../../references/icrc1-standard)                               |
| BRC-721             | [ICRC-7](https://github.com/dfinity/ICRC/blob/icrc7-wg-draft/ICRCs/ICRC-7/ICRC-7.md) |

## Smart contracts

El lenguaje de script de Bitcoin, Script, hace que los contratos inteligentes
complejos sean difíciles de implementar directamente en la red principal de
Bitcoin debido a las capacidades limitadas del lenguaje.

Los desarrolladores de Bitcoin que deseen construir contratos inteligentes
complejos deberán utilizar una capa de contrato inteligente de Bitcoin
(denominada Capa 2 o L2), como ICP. Cada solución L2 ofrece un conjunto único de
herramientas para desarrolladores.

Los contratos inteligentes de canister en ICP tienen propiedades especiales que
permiten a los desarrolladores desarrollar servicios escalables. Los canisters
pueden estar escritos en cualquier lenguaje que se compile en Wasm, incluyendo
[Rust](/docs/building-apps/developer-tools/cdks/rust/intro-to-rust),
[Typescript](https://demergent-labs.github.io/azle/),
[Motoko](/docs/motoko/main/getting-started/motoko-introduction) y
[Python](https://demergent-labs.github.io/kybra/). Esto permite una mayor
complejidad en el desarrollo de contratos inteligentes en comparación con el
lenguaje de script de Bitcoin.

Para obtener más información sobre la funcionalidad completa de los contratos
inteligentes de canister, consulta la
[documentación de contratos inteligentes](/docs/building-apps/essentials/canisters).

Específicamente, a través de la integración a nivel de protocolo de ICP con la
[red de Bitcoin](/docs/building-apps/chain-fusion/bitcoin/overview), los
contratos inteligentes de ICP pueden interactuar directamente con la red de
Bitcoin. Los contratos inteligentes de canister pueden ejecutar
[consultas contra el conjunto completo de UTXO de Bitcoin](/docs/building-apps/chain-fusion/bitcoin/using-btc/read-state),
incluyendo encontrar el saldo de cualquier dirección de Bitcoin. Pueden
[realizar](/docs/building-apps/chain-fusion/bitcoin/using-btc/generate-addresses)
transacciones,
[firmar](/docs/building-apps/chain-fusion/bitcoin/using-btc/sign-transactions) y
[enviar](/docs/building-apps/chain-fusion/bitcoin/using-btc/submit-transactions)
transacciones a la red de Bitcoin.

La integración de Threshold Schnorr permite a los desarrolladores interactuar
directamente con Runes y Ordinals en los canisters. Un ejemplo de canister
Schnorr está disponible en Motoko y Rust.

Para obtener más información sobre la integración de Bitcoin en ICP, consulta la
[documentación de integración de Bitcoin](/docs/building-apps/chain-fusion/bitcoin/overview).

## Consenso

Bitcoin utiliza la prueba de trabajo como su mecanismo de consenso. Utilizando
la prueba de trabajo, la cadena de bloques de Bitcoin espera diez minutos antes
de validar transacciones bloque por bloque, lo que plantea desafíos en cuanto a
seguridad y escalabilidad.

En lugar de imponer restricciones de tiempo, ICP se basa en firmas
criptográficas para finalizar un bloque. Un fabricante de bloques selecciona
mensajes disponibles, fusionándolos en un bloque. El protocolo de consenso
mantiene un árbol de bloques notarizados. Cada réplica crea una participación de
finalización distinta para cada bloque notarizado, sirviendo como un indicador
definitivo de que se ha logrado el consenso. Todo este proceso podría llevar
menos de dos segundos.

Para mejorar la escalabilidad, ICP divide los canisters en grupos más pequeños,
cada uno ejecutándose dentro de una subred con un conjunto diverso de réplicas.
Este enfoque permite agregar subredes adicionales según sea necesario.

Para obtener más información sobre el mecanismo de consenso de ICP, consulta el
[recurso de consenso](https://internetcomputer.org/how-it-works/consensus).

La mayor seguridad y escalabilidad mejoradas de ICP lo hacen adecuado como una
solución de Capa 2 para Bitcoin.
