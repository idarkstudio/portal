### Cómo funciona

<MarkdownChipRow labels={["Avanzado", "Ethereum", "Tutorial"]} />

El canister de
[Ethereum Virtual Machine](https://ethereum.org/en/developers/docs/evm/) (EVM)
[Remote Procedure Call](https://ethereum.org/en/developers/docs/apis/json-rpc/)
(RPC) permite la comunicación entre los canisters de ICP y los servicios RPC.
Estos servicios, como Cloudflare y Alchemy, proporcionan API públicas para
interactuar con redes blockchain. El canister EVM RPC actúa como un puente para
que los canisters de una dapp se comuniquen con cadenas compatibles con EVM y
consulten información de ellas. Proporciona endpoints que los desarrolladores de
ICP pueden usar para interactuar con contratos inteligentes de Ethereum y
garantiza que las respuestas recibidas de la red Ethereum sean seguras y útiles
dentro de un canister.

Para realizar llamadas a estas cadenas externas, el canister EVM RPC utiliza la
función [HTTPS outcalls](/docs/references/https-outcalls-how-it-works) de ICP
para realizar llamadas a endpoints JSON-RPC.  
Las HTTPS outcalls permiten realizar solicitudes HTTP salientes a servidores
Web2 tradicionales. La respuesta de estos servidores puede usarse de manera
segura dentro de un canister sin riesgo de divergencia de estado entre las
réplicas en un subnet.

Cuando un canister realiza una HTTPS outcall, llama a la API del canister de
gestión usando el método `http_request`. El adaptador de red en cada réplica
ejecuta la solicitud HTTP enviándola al servidor externo.  
Cuando el servidor externo devuelve una respuesta, esta pasa por un consenso en
el subnet, donde al menos 2/3 de los nodos deben estar de acuerdo con la
respuesta.  
Una vez validada, la respuesta se envía al canister de gestión, que la devuelve
al canister que originó la solicitud.

En el caso del canister EVM RPC, un canister realiza una solicitud al canister
EVM RPC para un método RPC específico, y el canister EVM RPC hace la HTTPS
outcall a uno o más endpoints RPC en nombre de ese canister.

Por defecto, para métodos Candid-RPC como `eth_getTransactionReceipt`, el
canister EVM RPC envía la misma solicitud a al menos tres proveedores RPC
diferentes y compara los resultados.  
Si hay discrepancias, el llamador recibe un conjunto de resultados
`Inconsistent`, que debe manejar según su caso de uso.  
Si no hay discrepancias, el método devuelve un resultado `Consistent` con un
valor Candid correspondiente a la respuesta JSON-RPC.

## Autenticación

Algunos endpoints JSON-RPC requieren una clave API para autenticarse con el
proveedor RPC.  
El canister EVM RPC ya está configurado con las claves API necesarias, aunque
los desarrolladores pueden optar por usar proveedores personalizados (con o sin
claves API) si lo desean.  
Las claves API suelen requerir una suscripción, pero los desarrolladores que
utilizan las claves preconfiguradas del canister EVM RPC no necesitan
suscribirse a estos servicios.

Al no usar claves API, los desarrolladores deben tener en cuenta:

- Los límites en la cantidad de solicitudes por hora, día, mes, etc., según el
  proveedor.
- Límites de tasa compartidos con otras dapps en el mismo subnet.

Al adjuntar claves API personales a una solicitud, los desarrolladores deben
considerar:

- Todos los nodos en el subnet de ICP podrán ver la clave API.
- Si esto es necesario, se recomienda configurar una lista de direcciones IP
  permitidas y monitorear el uso de la clave API.

Al usar claves administradas por el canister EVM RPC, los desarrolladores deben
considerar:

- Están administradas por DFINITY, por lo que la configuración de la API debería
  estar actualizada.
- Es más probable que sean afectadas por un ataque de denegación de servicio
  (DoS).
- Las URL de las API pueden cambiar inesperadamente.
- Pueden implicar costos adicionales en ciclos, según el proveedor RPC.

## Solicitudes Candid-RPC tipadas

El canister EVM RPC incluye una interfaz Candid completamente tipada para
proporcionar soporte de primera clase a ciertos métodos RPC.  
El principal beneficio de los métodos "Candid-RPC" es la lógica integrada de
consenso entre múltiples API.  
Esto requiere transformar y normalizar las respuestas de las HTTPS outcalls caso
por caso, intercambiando flexibilidad por mayor confianza en los resultados.

A continuación, se muestra un resumen de los tipos y métodos de los endpoints
Candid-RPC:

```candid
type EthMainnetService = variant { Alchemy; Ankr; BlockPi; Cloudflare; PublicNode; ... };
type EthSepoliaService = variant { Alchemy; Ankr; BlockPi; PublicNode; ... };
type L2MainnetService = variant { Alchemy; Ankr; BlockPi; PublicNode; ... };

type RpcServices = variant {
  EthMainnet : opt vec EthMainnetService;
  EthSepolia : opt vec EthSepoliaService;
  ArbitrumOne : opt vec L2MainnetService;
  BaseMainnet : opt vec L2MainnetService;
  OptimismMainnet : opt vec L2MainnetService;
  Custom : record {
    chainId : nat64;
    services : vec record { url : text; headers : opt vec HttpHeader };
  };
};

type RpcConfig = record {
  responseSizeEstimate : opt nat64,
  ...
};

type MultiRpcResult<T> = variant {
  Consistent : Result<T, RpcError>;
  Inconsistent : vec (
    variant {  Ethereum : EthereumService;  Sepolia : SepoliaService; ... },
    Result<T, RpcError>
  );
};

eth_getLogs : (RpcServices, RpcConfig, EthGetLogsParam)
  -> (MultiRpcResult<vec LogEntry>);

eth_getBlockByNumber : (RpcServices, RpcConfig, BlockTag)
  -> (MultiRpcResult<Block>);

eth_getTransactionReceipt : (RpcServices, RpcConfig, Hash)
  -> (MultiRpcResult<opt TransactionReceipt>);

eth_getTransactionCount : (RpcServices, RpcConfig, GetTransactionCountArgs)
  -> (MultiRpcResult<TransactionCount>);

eth_feeHistory : (RpcServices, RpcConfig, FeeHistoryArgs)
  -> (MultiRpcResult<FeeHistory>);

eth_sendRawTransaction : (RpcServices, RpcConfig, text)
  -> (MultiRpcResult<SendRawTransactionResult>);

```

Los tipos Candid compartidos se definen de la siguiente manera:

- `EthMainnetService`: Un servicio RPC compatible con la red principal de
  Ethereum.
- `EthSepoliaService`: Un servicio RPC compatible con la red de prueba Sepolia.
- `L2MainnetService`: Un servicio RPC compatible con una
  [red de capa 2](https://www.investopedia.com/what-are-layer-1-and-layer-2-blockchain-scaling-solutions-7104877)
  de Ethereum.
- `RpcServices`: Representa la cadena y los servicios que se utilizarán para la
  llamada RPC.  
  Por defecto, el canister usa al menos tres servicios RPC diferentes.
- `RpcConfig`: Permite personalizar cómo se realiza la solicitud RPC.

## Solicitudes JSON-RPC generales

Existe un endpoint JSON-RPC de propósito general para casos donde se requiera
funcionalidad más allá de la interfaz Candid-RPC, permitiendo llamar a una gama
más amplia de servicios RPC y blockchains EVM.

Este endpoint también mejora la experiencia de desarrollo cuando se usa la
librería Rust
[ethers-providers](https://docs.rs/ethers-providers/latest/ethers_providers/) o
el paquete npm [ethers](https://www.npmjs.com/package/ethers), que implementan
funciones tipadas con conversiones convenientes para cada método JSON-RPC.

`request`

```
type RpcService = variant {
  EthMainnet : EthMainnetService;
  EthSepolia : EthSepoliaService;
  ArbitrumOne : L2MainnetService;
  BaseMainnet : L2MainnetService;
  OptimismMainnet : L2MainnetService;
  Provider : nat64;
  Custom : record { url : text; headers : opt vec HttpHeader };
};

request : (
  service : RpcService,
  jsonRequest : text,
  maxResponseBytes : nat64
) -> (
  Result<text, RpcError>
);
```

- `EthMainnet`: Selecciona un proveedor incorporado para la red principal de
  Ethereum.

- `EthSepolia`: Selecciona un proveedor incorporado para la red de prueba
  Sepolia.

- `ArbitrumOne`: Selecciona un proveedor incorporado para la red de capa 2 de
  Arbitrum.

- `BaseMainnet`: Selecciona un proveedor incorporado para la red de capa 2 Base.

- `OptimismMainnet`: Selecciona un proveedor incorporado para la red de capa 2
  Optimism.

- `Chain`: Selecciona un proveedor de la lista de proveedores incorporados con
  el ID de cadena especificado. Se puede encontrar una lista extensa de IDs de
  cadena en [ChainList.org](https://chainlist.org). Especificar `Chain` sin un
  proveedor registrado resulta en un error.

- `Provider`: Selecciona el proveedor RPC con el ID especificado.

- `Custom`: Utiliza la información proporcionada de la API JSON-RPC. Esta opción
  se puede utilizar para pasar una clave de API personalizada. `header` en
  `Custom` permite enviar encabezados HTTP con la solicitud, generalmente para
  pasar la clave de API.

La lista de todos los proveedores incorporados se puede encontrar llamando al
método `getProvider` del canister. Si se encuentran múltiples proveedores para
una solicitud RPC, el canister prioriza los proveedores con `primary`
establecido en `true` y elige la opción con el ID más bajo.

En muchos casos, estos métodos JSON-RPC funcionan sin canonización para el
consenso de llamadas HTTP salientes. Abordamos casos individuales a medida que
surgen utilizando la misma lógica de canonización que el endpoint Candid-RPC
correspondiente.
