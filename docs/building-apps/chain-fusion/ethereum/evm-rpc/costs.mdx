# Costos de EVM RPC

<MarkdownChipRow labels={["Avanzado", "Ethereum", "Tutorial"]} />

Cada llamada realizada al canister EVM RPC tiene un costo en
[cycles](/docs/building-apps/getting-started/tokens-and-cycles).

Las solicitudes JSON-RPC generalmente cuestan entre 10^8 y 10^9 cycles, lo que
equivale aproximadamente a $0.0001 - $0.001 USD.

Debido a que los métodos Candid-RPC del canister EVM RPC utilizan reintentos
incorporados y múltiples proveedores, la cantidad de cycles requeridos para cada
llamada RPC no es predecible de antemano. La idea de estos métodos es enviar un
presupuesto máximo de cycles para realizar la solicitud.

:::info

El canister EVM RPC seguirá reintentando la solicitud hasta que se queden sin
cycles enviados con la solicitud. Esto es importante para solicitudes como
`eth_getLogs`, donde una solicitud puede devolver 100 veces más datos que la
misma solicitud unos días antes si hay un aumento en la actividad de contratos
inteligentes. Como resultado, el presupuesto óptimo de cycles es diferente para
cada caso de uso. Se sugiere enviar 10_000_000_000 cycles como punto de partida
y ajustar a partir de ahí.

:::

La siguiente fórmula muestra cómo calcular el costo en cycles para una solicitud
RPC:

```
(
  5_912_000
  + 60_000 * nodes_in_subnet // Number of nodes in the subnet
  + 2400 * request_size // Size of the HTTP request in bytes
  + 800 * max_response_size // Maximum HTTP response size in bytes
) * nodes_in_subnet
  * rpc_services // Number of RPC services used to check consistency
```

El costo total de una solicitud RPC (asumiendo una solicitud de 1 kB, una
respuesta de 1 kB, una subred de 34 nodos y 1
[XDR](/docs/building-apps/essentials/gas-cost) = $1.336610 USD) es de
aproximadamente $0.00051 USD.

Tenga en cuenta que el costo se multiplica por el número de servicios RPC
utilizados para la lógica de consistencia. Si especifica tres servicios
diferentes, costará tres veces más que una llamada a un solo proveedor de RPC.

Además, es necesario enviar `10_000_000 * nodes_in_subnet * rpc_services` cycles
adicionales, que serán reembolsados, ya que sirven como un búfer para cualquier
aumento futuro en los costos de la API JSON-RPC de terceros.

El canister EVM RPC reembolsa automáticamente cualquier ciclo enviado más allá
del costo de la solicitud RPC, por lo que es posible enviar más cycles de los
necesarios sin consecuencias. El envío de cycles adicionales también
proporcionará un presupuesto para volver a intentar la solicitud con un tamaño
de respuesta máxima más grande para los métodos Candid-RPC como `eth_getLogs` y
`eth_getBlockByNumber`.

## cycles de garantía

Además del costo de la solicitud RPC en sí, los llamadores también deben pasar
al menos 0.00028 TC de "cycles de garantía" para tener en cuenta posibles
futuros aumentos de precios de la API aguas abajo. Actualmente, el canister
reembolsa todos estos cycles, pero esto puede cambiar en el futuro.

## Adjuntando la cantidad correcta de ciclos

Para determinar cuántos ciclos deben enviarse con su llamada RPC, puede usar el
método de consulta `requestCost`. Esto se utiliza para predecir los costos de
las llamadas al método `request`:

```
`requestCost`

requestCost : (
  source : JsonRpcSource,
  jsonRequest : text,
  maxResponseBytes :  nat64
) -> (
  Result<nat, RpcError>
) query;
```

Este método de consulta acepta los mismos argumentos que el método
[`request`](evm-rpc-canister.mdx#custom-json-rpc-requests) del canister y
devuelve el número de ciclos necesarios para realizar una llamada equivalente.

Una vez que hayas determinado cuántos ciclos necesitará tu llamada, puedes
enviarlos en tu solicitud a través de un CDK o usando `dfx` con la bandera
`--with-cycles`.

<TabItem value="rust" label="Rust">

```rust
use candid::candid_method;
use ic_cdk_macros::update;

use e2e::declarations::EVM_RPC_STAGING_FIDUCIARY::{
    Block, BlockTag, GetBlockByNumberResult, MultiGetBlockByNumberResult, MultiGetLogsResult,
    ProviderError, RpcError, RpcService, RpcServices, EVM_RPC_STAGING_FIDUCIARY as evm_rpc,
};

fn main() {}

#[update]
#[candid_method(update)]
pub async fn test() {
    assert!(ic_cdk::api::is_controller(&ic_cdk::caller()));

    // Define request parameters
    let params = (
        RpcService::Chain(1), // Ethereum mainnet
        "{\"jsonrpc\":\"2.0\",\"method\":\"eth_gasPrice\",\"params\":null,\"id\":1}".to_string(),
        1000 as u64,
    );

    // Get cycles cost
    let (cycles_result,): (Result<u128, RpcError>,) =
        ic_cdk::api::call::call(evm_rpc.0, "requestCost", params.clone())
            .await
            .unwrap();
    let cycles = cycles_result
        .unwrap_or_else(|e| ic_cdk::trap(&format!("error in `request_cost`: {:?}", e)));

    // Call without sending cycles
    let (result_without_cycles,): (Result<String, RpcError>,) =
        ic_cdk::api::call::call(evm_rpc.0, "request", params.clone())
            .await
            .unwrap();
    match result_without_cycles {
        Ok(s) => ic_cdk::trap(&format!("response from `request` without cycles: {:?}", s)),
        Err(RpcError::ProviderError(ProviderError::TooFewCycles { expected, .. })) => {
            assert_eq!(expected, cycles)
        }
        Err(err) => ic_cdk::trap(&format!("error in `request` without cycles: {:?}", err)),
    }

    // Call with expected number of cycles
    let (result,): (Result<String, RpcError>,) =
        ic_cdk::api::call::call_with_payment128(evm_rpc.0, "request", params, cycles)
            .await
            .unwrap();
    match result {
        Ok(response) => {
            // Check response structure around gas price
            assert_eq!(
                &response[..36],
                "{\"id\":1,\"jsonrpc\":\"2.0\",\"result\":\"0x"
            );
            assert_eq!(&response[response.len() - 2..], "\"}");
        }
        Err(err) => ic_cdk::trap(&format!("error in `request` with cycles: {:?}", err)),
    }

    // Call a Candid-RPC method
    // This would benefit from a caller-side library with generic type definitions for result values
    let (results,): (MultiGetBlockByNumberResult,) = ic_cdk::api::call::call_with_payment128(
        evm_rpc.0,
        "eth_getBlockByNumber",
        (
            RpcServices::EthMainnet(None),
            (),
            BlockTag::Number(123.into()),
        ),
        10000000000,
    )
    .await
    .unwrap();
    match results {
        MultiGetBlockByNumberResult::Consistent(result) => match result {
            GetBlockByNumberResult::Ok(block) => {
                assert_eq!(block.hash, "aaaaaa");
            }
            GetBlockByNumberResult::Err(err) => {
                ic_cdk::trap(&format!("error in `eth_getBlockByNumber`: {:?}", err))
            }
        },
        MultiGetBlockByNumberResult::Inconsistent(results) => ic_cdk::trap(&format!(
            "inconsistent results in `eth_getBlockByNumber`: {:?}",
            results
        )),
    }
}
```

Para medir con precisión el costo de las llamadas HTTPS y protegerse de
respuestas accidentalmente grandes, el llamador debe especificar el número
máximo esperado de bytes. Debido al costo potencialmente alto de realizar
llamadas con un tamaño de respuesta máximo subóptimo, generalmente es mejor
interés del llamador elegir un valor para `maxResponseBytes` caso por caso para
cada situación. Los desarrolladores pueden determinar este valor midiendo el
tamaño de las respuestas JSON esperadas desde un entorno de prueba de API como
[Alchemy Sandbox](https://sandbox.alchemy.com/).

Los métodos Candid RPC utilizan un valor predeterminado incorporado para el
tamaño de respuesta, que se puede anular con el valor `RpcConfig`.

Puede optar por llamar repetidamente al método `request` con un valor cada vez
mayor para `maxResponseBytes` para manejar tamaños de respuesta variables.
Dejamos esta elección de estrategia al llamador para las llamadas JSON-RPC sin
procesar. Para los métodos de conveniencia de Candid-RPC, el canister duplica el
tamaño máximo de respuesta y vuelve a intentarlo hasta que el tamaño de
respuesta sea suficiente, comenzando con un valor predeterminado razonable para
cada método RPC. En contraste, el canister JSON-RPC solo realiza una solicitud,
dejando la lógica de reintento al llamador. Vale la pena señalar que el llamador
paga efectivamente por cada llamada como si estuviera enviando estas solicitudes
desde su propio canister.

El canister EVM RPC vuelve a intentar la llamada si:

- Quedan suficientes cycles enviados por el llamador.

- La llamada falla debido a que `maxResponseBytes` se establece demasiado bajo.
  Cada método RPC tiene una configuración predeterminada de `maxResponseBytes`
  que se puede anular.

Además, el parámetro `RpcConfig` admite una `responseSizeEstimate` opcional que
se puede ajustar para reducir el costo de las solicitudes RPC.
