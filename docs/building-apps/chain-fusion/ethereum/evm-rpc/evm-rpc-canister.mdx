# Usando el canister EVM RPC

<MarkdownChipRow labels={["Avanzado", "Ethereum", "Tutorial"]} />

## Métodos RPC compatibles

Los siguientes métodos JSON-RPC están disponibles como parte de la interfaz
Candid del canister:

- [`eth_feeHistory`](https://docs.alchemy.com/reference/eth-feehistory):
  Consulta los datos históricos de tarifas para estimar los precios de gas para
  transacciones.
- [`eth_getLogs`](https://docs.alchemy.com/reference/eth-getlogs): Consulta los
  registros de un bloque o transacción especificados.
- [`eth_getBlockByNumber`](https://docs.alchemy.com/reference/eth-getblockbynumber):
  Consulta información sobre un bloque dado.
- [`eth_getTransactionCount`](https://docs.alchemy.com/reference/eth-gettransactioncount):
  Consulta el número de transacciones para una dirección especificada.
- [`eth_getTransactionReceipt`](https://docs.alchemy.com/reference/eth-gettransactionreceipt):
  Consulta detalles sobre una transacción enviada.
- [`eth_sendRawTransaction`](https://docs.alchemy.com/reference/eth-sendrawtransaction):
  Envía una transacción firmada a la red de Ethereum.
- [`eth_call`](https://docs.alchemy.com/reference/eth-call): Consulta el estado
  de un contrato inteligente.

Otros métodos RPC, incluidos los específicos de redes no Ethereum, se pueden
acceder utilizando el método `request` del canister.

## Proveedores RPC compatibles

El canister EVM RPC tiene soporte incorporado para los siguientes proveedores de
Ethereum JSON-RPC:

- [Alchemy](https://docs.alchemy.com/docs/how-to-read-data-with-json-rpc):
  Ethereum mainnet, Sepolia testnet, L2 chains.
- [Ankr](https://www.ankr.com/infrastructure/build-on-ethereum/): Ethereum
  mainnet, Sepolia testnet, L2 chains.
- [BlockPI](https://blockpi.io/): Ethereum mainnet, Sepolia testnet, L2 chains.
- [Cloudflare Web3](https://www.cloudflare.com/application-services/products/web3/):
  Ethereum mainnet.
- [Public Node](https://www.publicnode.com/): Ethereum mainnet, Sepolia testnet,
  L2 chains.
- [LlamaNodes](https://llamanodes.com/): Ethereum mainnet, Sepolia testnet, L2
  chains.

Muchos de los proveedores en [ChainList.org](https://chainlist.org/) se pueden
llamar utilizando el método `request` del canister.

## Importar o desplegar el canister EVM RPC

### Usando `dfx deps`

Para usar el canister EVM RPC, puedes importarlo a tu proyecto usando `dfx deps`
configurando el archivo `dfx.json` de tu proyecto:

```json
{
  "canisters": {
    "evm_rpc": {
      "type": "pull",
      "id": "7hfb6-caaaa-aaaar-qadga-cai"
    }
  }
}
```

Luego, ejecuta los siguientes comandos:

```
# Start the local replica
dfx start --background

# Locally deploy the `evm_rpc` canister
dfx deps pull
dfx deps init evm_rpc --argument '(record {})'
dfx deps deploy
```

### Usando Candid y archivos Wasm

Alternativamente, puedes incluir el canister EVM RPC especificando los archivos
Candid y Wasm en tu archivo `dfx.json`:

```json
{
  "canisters": {
    "evm_rpc": {
      "type": "custom",
      "candid": "https://github.com/internet-computer-protocol/evm-rpc-canister/releases/latest/download/evm_rpc.did",
      "wasm": "https://github.com/internet-computer-protocol/evm-rpc-canister/releases/latest/download/evm_rpc.wasm.gz",
      "remote": {
        "id": {
          "ic": "7hfb6-caaaa-aaaar-qadga-cai"
        }
      }
    }
  }
}
```

Luego, inicia la réplica local y despliega el canister localmente con un número
especificado de nodos (`31` para la
[subred fiduciaria](/docs/building-apps/developing-canisters/create)):

```
dfx start --clean --background
dfx deploy evm_rpc --argument '(record {})'
```

### Fork the EVM RPC canister

Another option is to create a fork of the EVM RPC canister:

```
git clone https://github.com/internet-computer-protocol/evm-rpc-canister
```

Para desplegar tu propio canister en la red principal, ejecuta el comando
`dfx deploy` con la flag `--network ic`:

```
dfx deploy evm_rpc --network ic --argument '(record {})'
```

Ten en cuenta que, al desplegar tu propio canister, podrías encontrarte con
límites en la tasa de solicitudes de la API. Consulta la sección
[reemplazar claves de API](#replacing-api-keys) para aprender cómo configurar
las credenciales de la API.

### `ic-alloy`

El crate de Rust [`ic-alloy`](https://github.com/ic-alloy) se puede utilizar
para interactuar con el canister EVM RPC desde código en Rust. Este crate
simplifica el código necesario para realizar operaciones comunes en la EVM.

El `ic-alloy-toolkit` incluye una colección de ejemplos que muestran cómo se
puede utilizar `ic-alloy`.

[Consulta la documentación de `ic-alloy` para más información](https://o7kje-7yaaa-aaaal-qnaua-cai.icp0.io).

```motoko no-repl
                toBlock = ?#Number 19520940;

                    ["0x4d69d0bd4287b7f66c548f90154dc81bc98f65a1b362775df5ae171a2ccd262b"],
                    [
                        "0x000000000000000000000000352413d00d2963dfc58bc2d6c57caca1e714d428",
                        "0x000000000000000000000000b6bc16189ec3d33041c893b44511c594b1736b8a",
                    ],
                ];
            },
        );

        // Process results
        switch result {
          // Consistent, successful results
          case (#Consistent(#Ok value)) {
            ?value
          };
          // Consistent error message
          case (#Consistent(#Err error)) {
            Debug.trap("Error: " # debug_show error);
            null
          };
          // Inconsistent results between RPC providers
          case (#Inconsistent(results)) {
            Debug.trap("Inconsistent results: " # debug_show results);
            null
          };
        };
    };
};
```

Como se describe en la documentación oficial de
[Ethereum JSON-RPC](https://ethereum.org/en/developers/docs/apis/json-rpc/#eth_getlogs),
el campo de temas es una matriz bidimensional dependiente del orden que codifica
la lógica booleana para los temas relevantes.

Por ejemplo:

- `[[A], [B]]` corresponde a `A y B`.

- `[[A, B]]` corresponde a `A o B`.

- `[[A], [B, C]]` corresponde a `A y (B o C)`.

## Llamar a un contrato inteligente de Ethereum

<AdornedTabs groupId="languages">

```motoko no-repl
import EvmRpc "canister:evm_rpc";

import Cycles "mo:base/ExperimentalCycles";
import Debug "mo:base/Debug";

actor {
  public func call() : async ?Text {

    // Configure RPC request
    let services = #EthMainnet(null);
    let config = null;

    // Add cycles to next call
    Cycles.add<system>(2000000000);

    // Call an Ethereum smart contract. The smart contract's information in this example is hard-coded.
    let result = await EvmRpc.eth_call(services, config, {
      block = null;
      transaction = {
        to = ?"0xA0b86991c6218b36c1d19D4a2e9Eb0cE3606eB48";
        input = ?"0x70a08231000000000000000000000000b25eA1D493B49a1DeD42aC5B1208cC618f9A9B80"; // ABI-encoded
        accessList = null;
        blobVersionedHashes = null;
        blobs = null;
        chainId = null;
        from = null;
        gas = null;
        gasPrice = null;
        maxFeePerBlobGas = null;
        maxFeePerGas = null;
        maxPriorityFeePerGas = null;
        nonce = null;
        type_ = null;
        value = null
      };
    });

    // Process results
    switch result {
      // Prints the response if each RPC provider returns a consistent, successful result
      case (#Consistent(#Ok response)) {
        Debug.print("Success: " # debug_show response);
        ?response // ABI-encoded
      };
      // Trap is an RPC provider that returns an error message consistent with the response of the other providers
      case (#Consistent(#Err error)) {
        Debug.trap("Error: " # debug_show error);
        null
      };
      // Trap if an RPC provider returns a response inconsistent with the other providers
      case (#Inconsistent(_results)) {
        Debug.trap("Inconsistent results");
        null
      };
    };
  };
};
```

```rust
pub async fn eth_call(
    contract_address: String,
    abi: &Contract,
    function_name: &str,
    args: &[Token],
    block_number: &str,
) -> Vec<Token> {
    let f = match abi.functions_by_name(function_name).map(|v| &v[..]) {
        Ok([f]) => f,
        Ok(fs) => panic!(
            "Found {} function overloads. Please pass one of the following: {}",
            fs.len(),
            fs.iter()
                .map(|f| format!("{:?}", f.abi_signature()))
                .collect::<Vec<_>>()
                .join(", ")
        ),
        Err(_) => abi
            .functions()
            .find(|f| function_name == f.abi_signature())
            .expect("Function not found"),
    };
    let data = f
        .encode_input(args)
        .expect("Error while encoding input args");
    let json_rpc_payload = serde_json::to_string(&JsonRpcRequest {
        id: next_id().await.0.try_into().unwrap(),
        jsonrpc: "2.0".to_string(),
        method: "eth_call".to_string(),
        params: (
            EthCallParams {
                to: contract_address,
                data: to_hex(&data),
            },
            block_number.to_string(),
        ),
    })
    .expect("Error while encoding JSON-RPC request");

    let res: CallResult<(RequestResult,)> = call_with_payment(
        crate::declarations::evm_rpc::evm_rpc.0,
        "request",
        (
            RpcService::EthSepolia(EthSepoliaService::BlockPi),
            json_rpc_payload,
            2048_u64,
        ),
        2_000_000_000,
    )
    .await;

    match res {
        Ok((RequestResult::Ok(ok),)) => {
            let json: JsonRpcResult =
                serde_json::from_str(&ok).expect("JSON was not well-formatted");
            let result = from_hex(&json.result.expect("Unexpected JSON response")).unwrap();
            f.decode_output(&result).expect("Error decoding output")
        }
        err => panic!("Response error: {err:?}"),
    }
}
```

```rust
pub async fn fee_history(
    network: String,
    block_count: u128,
    newest_block: BlockTag,
    reward_percentiles: Option<serde_bytes::ByteBuf>,
) -> FeeHistory {
    let config = None;
    let args = FeeHistoryArgs {
        blockCount: block_count,
        newestBlock: newest_block,
        rewardPercentiles: reward_percentiles,
    };

    let services = match network.as_str() {
        "EthSepolia" => RpcServices::EthSepolia(Some(vec![EthSepoliaService::Alchemy])),
        "EthMainnet" => RpcServices::EthMainnet(None),
        _ => RpcServices::EthSepolia(None),
    };

    let cycles = 20000000;
```

Algunas API JSON-RPC pueden devolver solo un estado `NonceTooLow` al enviar una
transacción con éxito. Esto ocurre porque, durante el consenso de las llamadas
HTTPS outcall, solo la primera solicitud se procesa correctamente, mientras que
las demás responden con un estado de transacción duplicada.

Si te encuentras con este problema, una posible solución es utilizar un servidor
proxy que elimine duplicados, como el proxy EVM RPC C-ATTS desarrollado por la
comunidad ([código fuente](https://github.com/c-atts/catts-evm-rpc-proxy)).

### Error "already known"

Enviar una transacción a la red de Ethereum es una operación que cambia el
estado. Como el canister EVM-RPC envía la transacción a varios proveedores
JSON-RPC a través de llamadas HTTPS outcall, cada proveedor recibe la misma
transacción varias veces.

Por lo tanto, es posible que algunos proveedores respondan con el siguiente
error:

```
"{ code: -32603, message: \"already known\" }"
```

Si la transacción enviada es válida, al menos un nodo del proveedor la aceptará,
mientras que los demás podrían devolver un error como el mostrado arriba. Ten en
cuenta que el error exacto depende del cliente EVM que esté en uso, ya que la
API JSON-RPC de Ethereum no especifica errores exactos. Esto significa que
podrías encontrarte con otros errores, como uno que indique que no se alcanzó
consenso en el IC.

Incluso si se devuelve un error, debes asumir que tu transacción ha sido
registrada en la red de Ethereum. Puedes verificar si tu transacción fue
incluida en un bloque consultando el número de transacciones
(`eth_getTransactionCount`) en la altura de bloque más reciente (`Latest`).

```motoko no-repl
import Cycles "mo:base/ExperimentalCycles";
import Debug "mo:base/Debug";

actor {
  public func rawJsonRpcRequest() : async ?Text {

    // Configure JSON-RPC request
    let service = #EthMainnet(#PublicNode);
    let json = "{\"jsonrpc\":\"2.0\",\"method\":\"eth_gasPrice\",\"params\":[],\"id\":1}";
    let maxResponseBytes : Nat64 = 1000;

    // Optionally retrieve the exact number of cycles for an RPC request
    let cyclesResult = await EvmRpc.requestCost(service, json, maxResponseBytes);
    let cycles = switch cyclesResult {

      case (#Err err) {

      };

    Cycles.add<system>(cycles);

    switch result {
      case (#Ok response) {
        Debug.print("Success:" # debug_show response);
        ?response
      };
      case (#Err err) {
        Debug.trap("Error while calling `request`: " # debug_show err);

      };
    };
  };
};
```

## Reemplazo de claves API

Si eres un controlador o un principal autorizado para administrar claves API
(definido en el campo `manageApiKeys` al inicializar el canister), puedes
reemplazar las claves API utilizadas por el canister EVM RPC.

El primer paso es identificar el `providerId` correspondiente a un proveedor
JSON-RPC compatible.

Ejecuta el siguiente comando para ver todos los proveedores registrados:

```bash
dfx canister call evm_rpc getProviders
```

Deberías ver una lista de valores. Busca el `providerId`, que en este caso es
`0`:

```
record {
  access = variant {
    Authenticated = record {
      publicUrl = opt "https://cloudflare-eth.com/v1/mainnet";
      auth = variant { BearerToken = record { url = "https://cloudflare-eth.com/v1/mainnet";} };
    }
  };
  alias = opt variant { EthMainnet = variant { Cloudflare } };
  chainId = 1 : nat64;
  providerId = 0 : nat64;
};
```

Actualiza la configuración de un proveedor existente usando el método
`updateApiKeys`:

```bash
dfx canister call evm_rpc updateApiKeys '(vec { record { 0 : nat64;  opt "TU-API-KEY" } } )'
```

## Mensajes de error

### Error "TooFewCycles"

```
"ProviderError(TooFewCycles { expected: 798336000, received: 307392000 })"
```

Este error puede ocurrir si se consultaron varios proveedores JSON-RPC y uno de
ellos no recibió suficientes ciclos para la solicitud. Puedes adjuntar más
ciclos sin problemas, ya que los ciclos no utilizados serán reembolsados.

## Filtrado de registros (logs)

El argumento `consoleFilter` puede pasarse al canister EVM RPC para filtrar qué
mensajes de registro se muestran.

La configuración predeterminada muestra todos los registros:

```bash
dfx deploy evm_rpc --argument "(record { consoleFilter = opt variant { ShowAll } })"
```

Para ocultar todos los registros:

```bash
dfx deploy evm_rpc --argument "(record { consoleFilter = opt variant { HideAll } })"
```

Los argumentos `ShowPattern` y `HidePattern` pueden usarse para filtrar
registros con expresiones regulares. Por ejemplo, para filtrar registros
etiquetados con `INFO`:

```
dfx deploy evm_rpc --argument "(record { consoleFilter = opt variant { ShowPattern = "^INFO" } })"
```

O para ocultar registros etiquetados con `TRACE_HTTP`:

```bash
dfx deploy evm_rpc --argument "(record { consoleFilter = opt variant { HidePattern = \"^TRACE_HTTP\" } })"
```

`ShowPattern` y `HidePattern` se evalúan usando la librería
[regex](https://docs.rs/regex/latest/regex/).

## Notas importantes

### Consistencia de resultados RPC

Cuando se llaman métodos RPC directamente a través de la interfaz Candid (en
lugar de usar el método `request`), el canister compara los resultados de varias
API JSON-RPC y devuelve una variante `Consistent` o `Inconsistent`, según si las
APIs coinciden en el resultado.

Por defecto, el canister utiliza tres proveedores RPC diferentes, los cuales
pueden cambiar dependiendo de la disponibilidad. Es posible especificar qué
proveedores usar para esta verificación de consistencia. Por ejemplo:

```bash
dfx canister call evm_rpc eth_getTransactionCount '(variant {EthMainnet = opt vec {Cloudflare; PublicNode}}, record {address = "0xdAC17F958D2ee523a2206206994597C13D831ec7"; block = variant {Tag = variant {Latest}}})' --with-cycles 100000000000 --wallet=$(dfx identity get-wallet)
```

### Consenso en llamadas HTTPS outcall

Asegúrate de verificar que las solicitudes RPC funcionen como se espera en la
mainnet de ICP. Las llamadas HTTPS outcall realizadas en el método `request`
solo alcanzan consenso si la respuesta JSON-RPC es la misma en cada solicitud.

Si encuentras un problema con el consenso,
[infórmanos aquí](https://github.com/internet-computer-protocol/evm-rpc-canister)
para analizar si es posible agregar soporte oficial para tu caso de uso.

### Estimaciones del tamaño de respuesta

En algunos casos, es necesario realizar múltiples llamadas HTTPS outcall con
tamaños de respuesta máximos crecientes para completar una solicitud. Esto es
común para el método `eth_getLogs` y puede aumentar el tiempo y costo de
realizar una llamada RPC.

Una solución es especificar una estimación inicial del tamaño de respuesta (en
bytes):

```bash
dfx canister call evm_rpc eth_getLogs "(variant {EthMainnet}, record {responseSizeEstimate = 5000}, record {addresses = vec {\"0xdAC17F958D2ee523a2206206994597C13D831ec7\"}})" --with-cycles=1000000000 --wallet=$(dfx identity get-wallet)
```

Si la respuesta es más grande que la estimación, el canister duplicará el tamaño
máximo de respuesta y reintentará hasta recibir una respuesta o agotar los
ciclos asignados con la bandera `--with-cycles`.
