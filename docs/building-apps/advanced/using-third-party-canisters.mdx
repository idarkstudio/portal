# Uso de canisters de terceros

<MarkdownChipRow labels={["Principiante", "Tutorial"]} />

Los canisters de terceros son canisters creados por DFINITY o miembros de la
comunidad de ICP que proporcionan funcionalidades importantes que otros
desarrolladores pueden querer integrar en sus propios proyectos. Es importante
probar la integración con estos canisters de forma local para:

- Validar la precisión de la integración y del código del canister.
- Probar sin pagar <GlossaryTooltip>cycles</GlossaryTooltip>.
- Usar datos y entornos que no sean de producción.
- Ejecutar operaciones más rápido cuando se ejecutan localmente.

Para integrar canisters de terceros y probarlos en tu proyecto, puedes optar
por:

- Si los archivos Candid y Wasm del canister están disponibles públicamente,
  puedes referenciarlos directamente en el archivo `dfx.json` de tu proyecto.
- Si el canister está configurado como `pullable`, puedes importarlo en tu
  proyecto con `dfx deps`.

## Uso de archivos Candid y Wasm de un canister directamente

Si los archivos Candid y Wasm de un canister están disponibles públicamente,
puedes referenciarlos directamente en el archivo `dfx.json` de tu proyecto.

Si el canister está desplegado en la mainnet, también puedes especificar el ID
del canister `remote`. Cuando tu proyecto se despliegue en la mainnet, usará el
canister de mainnet con ese ID. Cuando se despliegue localmente, `dfx`
descargará los archivos Candid y Wasm especificados y creará un nuevo canister
local con ellos.

```json
{
  "canisters": {
    "icp_ledger_canister": {
      "type": "custom",
      "candid": "https://raw.githubusercontent.com/dfinity/ic/aba60ffbc46acfc8990bf4d5685c1360bd7026b9/rs/ledger_suite/icp/ledger.did",
      "wasm": "https://download.dfinity.systems/ic/aba60ffbc46acfc8990bf4d5685c1360bd7026b9/canisters/ledger-canister.wasm.gz",
      "remote": {
        "id": {
          "ic": "ryjl3-tyaaa-aaaaa-aaaba-cai"
        }
      }
    }
  }
}
```

Alternativamente, puedes referenciar archivos Candid y Wasm almacenados en tu
entorno local:

```json
{
  "canisters": {
    "icp_ledger_canister": {
      "type": "custom",
      "candid": "ledger.did",
      "wasm": "ledger-canister.wasm.gz",
      "remote": {
        "id": {
          "ic": "ryjl3-tyaaa-aaaaa-aaaba-cai"
        }
      }
    }
  }
}
```

Un ejemplo del uso de este método es el
[proyecto demo de XRC](https://github.com/THLO/xrc_demo/blob/main/dfx.json#L15).

## Uso de `dfx deps` para importar canisters de terceros

Este comando y flujo de trabajo permiten importar canisters de terceros en un
proyecto desplegado localmente o en la mainnet.

En este flujo de trabajo, un **proveedor de servicios** configura un canister
como `pullable` y lo despliega en la mainnet. Un proveedor de servicios puede
ser cualquier persona, como un desarrollador de la comunidad que crea un
canister público de terceros.

Luego, un **consumidor de servicios** puede importar el canister como una
dependencia directamente desde la mainnet usando
[`dfx deps`](/docs/building-apps/developer-tools/dfx/dfx-deps) y desplegar la
dependencia localmente.

### Determinar si un canister debe ser `pullable`

Primero, el canister debe estar configurado como `pullable`. Los desarrolladores
deben evaluar si un canister _debería_ ser `pullable`. Un canister debería ser
`pullable` si proporciona un servicio público con un ID de canister estático. Si
depende de otros canisters, esas dependencias también deben ser `pullable`.

### Configuración de un canister como `pullable`

Un proveedor de servicios debe configurar un canister como `pullable` definiendo
los siguientes detalles en el archivo `dfx.json` del proyecto:

- **`wasm_url`**: Una URL para descargar el módulo Wasm del canister, que se
  desplegará localmente.
- **`wasm_hash`**: Un hash SHA256 del módulo Wasm ubicado en `wasm_url`. Este
  campo es opcional. En la mayoría de los casos, el módulo Wasm en `wasm_url`
  será el mismo que el módulo Wasm en la blockchain. Esto significa que `dfx`
  puede leer el árbol de estado para obtener y verificar el hash del módulo. En
  algunos casos, el módulo Wasm en `wasm_url` no es el mismo que el de la
  blockchain. Por ejemplo, el canister de Internet Identity proporciona una
  variante de `desarrollo` para ser integrada localmente. En estos casos,
  `wasm_hash` proporciona el hash esperado, y `dfx` verifica el Wasm descargado
  con este.

Si el `wasm_hash` del módulo Wasm en `wasm_url` no coincide, `dfx` abortará con
un mensaje de error indicando que hay una discrepancia de hash. En este caso, el
consumidor del servicio debe contactar al proveedor del servicio. Es
responsabilidad del proveedor asegurar que el módulo Wasm correcto pueda
descargarse desde `wasm_url`.

- `dependencies`: Un array de IDs de canister (`Principal`) de dependencias
  directas.
- `init_guide`: Un mensaje para guiar a los consumidores sobre cómo inicializar
  el canister.

```json
{
  "canisters": {
    "service": {
      "type": "motoko",
      "main": "src/main.mo",
      "pullable": {
        "wasm_url": "http://example.com/a.wasm",
        "wasm_hash": "d180f1e232bafcee7d4879d8a2260ee7bcf9a20c241468d0e9cf4aa15ef8f312",
        "dependencies": ["yofga-2qaaa-aaaaa-aabsq-cai"],
        "init_guide": "Un número natural, por ejemplo, 10."
      }
    }
  }
}
```

:::danger

El módulo Wasm de un canister `pullable` debe estar alojado en una URL pública
donde los consumidores del servicio puedan descargarlo, como GitHub.

:::

El objeto `pullable` se serializará como parte de los metadatos de `dfx` y se
adjuntará al Wasm.

### Requisitos de metadatos del canister

Un canister de terceros utilizado en producción debe tener metadatos públicos de
`dfx` y metadatos `candid:service` y `candid:args` que pueden ser públicos o
privados. Todas las secciones de metadatos son manejadas por `dfx` cuando se
construye el canister.

### Proceso de despliegue

Los proveedores de servicios deben seguir este proceso para desplegar su
canister `pullable` y ponerlo a disposición de otros:

#### Paso 1: Desplegar el canister en la mainnet

```sh
dfx deploy <canister-name> --network ic
```

- #### Paso 2: Si estás usando GitHub, [`git tag` y `GitHub release`](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository#creating-a-release) con los comandos:

```sh
git tag 0.1.0
git push --tags
```

#### Paso 3: Adjuntar el Wasm a los assets de la versión

Edita la versión en GitHub y adjunta el archivo Wasm desplegado como un asset de
la versión. El archivo Wasm desplegado se encuentra en:

```sh
.dfx/ic/canisters/<CANISTER_NAME>/<CANISTER_NAME>.wasm
```

### Automatización del proceso de proveedor de servicios en CI

Un
[ejemplo de configuración CI](https://github.com/lwshang/pullable/blob/main/.github/workflows/release.yml)
demuestra cómo usar una GitHub Action para automatizar la rutina de despliegue
descrita anteriormente.

El flujo de trabajo con CI seguirá estos pasos:

1. Hacer un push de un tag de git y esperar a que se complete el release en
   GitHub.
2. Descargar el canister Wasm desde los assets del release
   (`wget https://github.com/lwshang/pullable/releases/latest/download/service.wasm`).
3. Instalar (actualizar) el canister utilizando el Wasm descargado
   (`dfx canister --network ic install service --wasm service.wasm --argument '(1 : nat)' --mode upgrade`).

### Importación de un canister de terceros en tu proyecto

El siguiente flujo de trabajo puede ser utilizado por los consumidores para
importar un canister `pullable` como dependencia.

- #### Paso 1: Declarar dependencias "pull" en `dfx.json`.

Un ejemplo de `dfx.json` en el que el consumidor está desarrollando un canister
llamado "dapp" que tiene dos dependencias "pull" puede encontrarse a
continuación:

- "dep_b" tiene un ID de canister de `yhgn4-myaaa-aaaaa-aabta-cai` en la red
  principal.
- "dep_c" tiene un ID de canister de `yahli-baaaa-aaaaa-aabtq-cai` en la red
  principal.

```json
{
  "canisters": {
    "dapp": {
      "type": "motoko",
      "main": "src/main.mo",
      "dependencies": ["dep_b", "dep_c"]
    },
    "dep_b": {
      "type": "pull",
      "id": "yhgn4-myaaa-aaaaa-aabta-cai"
    },
    "dep_c": {
      "type": "pull",
      "id": "yahli-baaaa-aaaaa-aabtq-cai"
    }
  }
}
```

- #### Paso 2: Descargar las dependencias usando el comando `dfx deps pull`.

`dfx deps pull` se conecta por defecto a la red principal (`--network ic`).
También puedes elegir otras redes como de costumbre, por ejemplo,
`--network local`.

- #### Paso 3: Establecer los argumentos de inicialización usando `dfx deps init`.

Ejecutar el comando `dfx deps init` iterará sobre todas las dependencias en el
archivo `pulled.json` y establecerá un argumento vacío para aquellas que no
necesiten un argumento de `init`. Luego, imprimirá la lista de dependencias que
requieren un argumento de `init`.

Ejecutar el comando `dfx deps init <CANISTER> --argument <ARGUMENT>` establecerá
el argumento de inicialización para una dependencia individual. Los argumentos
de inicialización se registrarán en `deps/init.json`.

Para establecer los argumentos de inicialización:

```
dfx deps init
```

<details>
<summary>Salida</summary>

```
WARN: The following canister(s) require an init argument. Please run `dfx deps init <NAME/PRINCIPAL>` to set them individually:
yofga-2qaaa-aaaaa-aabsq-cai
yahli-baaaa-aaaaa-aabtq-cai (dep_c)
```

</details>

Si intentas establecer un argumento `init` para una dependencia individual sin
un argumento, se mostrará el siguiente error:

```
Error: Canister yofga-2qaaa-aaaaa-aabsq-cai requires an init argument. The following info might be helpful:
init_guide => A natural number, e.g., 10.
candid:args => (nat)
```

Para establecer un argumento de inicialización con un valor utilizando el flag
`--argument`:

```
dfx deps init <canister-id> --argument 10
dfx deps init deps_c --argument 20
```

El archivo generado `init.json` tendrá el siguiente contenido:

```json
{
  "canisters": {
    "yofga-2qaaa-aaaaa-aabsq-cai": {
      "arg_str": "10",
      "arg_raw": "4449444c00017d0a"
    },
    "yhgn4-myaaa-aaaaa-aabta-cai": {
      "arg_str": null,
      "arg_raw": null
    },
    "yahli-baaaa-aaaaa-aabtq-cai": {
      "arg_str": "20",
      "arg_raw": "4449444c00017d14"
    }
  }
}
```

- #### Paso 4: Desplegar las dependencias descargadas en tu entorno local utilizando el comando `dfx deps deploy`.

```
dfx deps deploy
```

Ejecutar el comando `dfx deps deploy` hará lo siguiente:

1. Creará las dependencias en tu entorno local con el mismo ID de canister de la
   red principal.
2. Luego, instalará el Wasm descargado con los argumentos de inicialización en
   el archivo `init.json`.

También puedes especificar el nombre del canister o

<GlossaryTooltip>principal</GlossaryTooltip> para desplegar una dependencia en particular.

`dfx deps deploy` siempre crea el canister con la identidad anónima, por lo que
las dependencias y los canisters de la aplicación tendrán controladores
diferentes. También instalará siempre el canister en modo "reinstalar" para que
el estado del canister sea descartado.

### Preguntas frecuentes

- #### ¿Por qué descargar el Wasm en una caché compartida en lugar de una subcarpeta del proyecto?

No se recomienda incluir archivos binarios en el control de versiones. En el
Internet Computer, cada canister solo tiene una versión más reciente corriendo
en la red principal. Los consumidores de servicio deberían integrarse con esa
última versión.

`dfx deps pull` siempre obtiene las dependencias más recientes en lugar de
bloquear una en una ejecución particular. Cada canister descargado tiene la
última versión en la caché compartida y puede ser reutilizado por diferentes
proyectos.

- #### ¿Debo incluir la carpeta `deps/` en el control de versiones?

Sí. Los archivos de `deps/` permiten que el canister dependiente se construya y
obtenga soporte en el IDE. Si los archivos Wasm requeridos también están
disponibles en la caché compartida, todas las aplicaciones y dependencias pueden
ser desplegadas y probadas de manera integral.

Considerando un equipo de desarrollo de canisters:

1.  El Desarrollador 1 sigue el
    [flujo de trabajo del consumidor de servicios](#flujo-de-trabajo-del-consumidor-de-servicios)
    e incluye todos los archivos generados de `deps/` en el control de
    versiones.
2.  El Desarrollador 2 descarga la rama del Desarrollador 1 y ejecuta nuevamente
    el comando `dfx deps pull`.
    - Si el archivo `pulled.json` no ha cambiado, todas las dependencias siguen
      actualizadas. El Desarrollador 2 puede ejecutar `dfx deps deploy` sin
      necesidad de establecer los argumentos de inicialización nuevamente.
    - Si hay cambios en `pulled.json`, el Desarrollador 2 puede intentar
      ejecutar `dfx deps deploy` para ver si todos los argumentos de
      inicialización siguen siendo válidos. Luego, el Desarrollador 2 puede
      ejecutar `dfx deps init` si es necesario y actualizar el control de
      versiones.

Estos archivos también ayudan al CI a detectar dependencias desactualizadas.
