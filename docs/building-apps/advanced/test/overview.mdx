# Pruebas de canisters

<MarkdownChipRow labels={["Principiante", "Desarrollando canisters"]} />

Probar el código de tu canister durante el proceso de desarrollo es un paso
importante para verificar que funcione como se espera y no produzca errores,
fallos o termine atrapado. Antes de desplegar y usar el código en un entorno de
producción, este debe someterse a pruebas.

## Tipos de pruebas

Existen tres tipos de pruebas:

- **Pruebas unitarias**: Evalúan cada unidad individual del código por separado,
  como una función o un cálculo.
- **Pruebas de integración**: Verifican cómo varias funciones o partes del
  código se integran y operan juntas.
- **Pruebas de extremo a extremo**: Evalúan el flujo de trabajo completo de la
  aplicación, incluida la interfaz de usuario del frontend.

### Pruebas unitarias

Las pruebas unitarias consisten en evaluar una sola función o componente del
código de forma aislada, probando así una _unidad_ específica. Estas pruebas no
consideran cómo la unidad interactúa con otros componentes de la aplicación. Su
objetivo es detectar errores en cada parte individual del código.

En Motoko, la
[librería base](https://github.com/dfinity/motoko-base/tree/master/test)
contiene archivos útiles para pruebas unitarias. La mayoría utiliza la librería
de pruebas **Motoko Matchers**, que ofrece funcionalidad para pruebas dentro de
canisters.

Para pruebas con grandes volúmenes de datos o lotes de pruebas de larga
duración, Motoko también proporciona la
[librería BigTest](https://github.com/matthewhammer/motoko-bigtest).

Para pruebas unitarias en Rust, consulta la guía sobre
[contenedores efectivos en Rust](https://mmapped.blog/posts/01-effective-rust-canisters).

### Pruebas de integración

Las pruebas de integración verifican que múltiples componentes de una aplicación
funcionen correctamente juntos. Estas pruebas pueden incluir:

- La interacción entre varias funciones dentro de un canister.
- La comunicación entre diferentes canisters.
- La obtención y procesamiento de información externa mediante _HTTPS outcalls_.

Un tipo común de prueba de integración es la **integración continua (CI)**, que
utiliza flujos de trabajo automatizados para probar componentes de una
aplicación en cada nueva actualización de código.

GitHub permite configurar flujos de CI para ejecutar pruebas automáticamente al
enviar nuevo código a un repositorio.  
[Más información sobre pruebas CI](https://docs.github.com/en/actions/using-workflows).

### Pruebas de extremo a extremo

Las pruebas de extremo a extremo se refieren a probar la funcionalidad completa
de una aplicación, incluyendo la interfaz de usuario del frontend. Esto incluye
probar botones, formularios de entrada, métodos de autenticación y el recorrido
general del usuario dentro de la aplicación. Las pruebas de extremo a extremo
pueden ser simples, como probar que un canister de frontend se comunique
exitosamente con un canister de backend.

Para más información, consulta el  
[módulo Developer Liftoff sobre pruebas](/docs/tutorials/developer-liftoff/level-2/2.5-unit-testing#end-to-end-e2e-testing).

## Herramientas para probar canisters

Existen varias herramientas para probar canisters en ICP. Algunas son
específicas para Motoko y se mencionaron en la sección de
[pruebas unitarias](#pruebas-unitarias). A continuación, se presentan
herramientas más avanzadas para pruebas integrales.

### PocketIC

**PocketIC** es un conjunto de pruebas avanzado que permite probar canisters en
entornos personalizados, simulando escenarios del mundo real que tu aplicación
podría enfrentar en la red principal (_mainnet_). Los tests de PocketIC pueden
escribirse en varios lenguajes:

- [PocketIC Rust](https://crates.io/crates/pocket-ic)
- [PocketIC Python](https://pypi.org/project/pocket-ic/)
- [Pic JS para JavaScript/TypeScript](https://www.npmjs.com/package/@hadronous/pic)
- [PocketIC GoLang](https://pkg.go.dev/github.com/aviate-labs/agent-go/pocketic)

[Más información sobre PocketIC](/docs/building-apps/advanced/test/pocket-ic).

### Light Replica

Light Replica es una herramienta contribuida por la comunidad diseñada para
replicar el entorno de prueba local que proporcionan las herramientas Ethereum
Hardhat o Truffle. Light Replica replica el comportamiento de un nodo ICP real
ejecutando una instancia local de un nodo, y luego proporciona registros y
funcionalidades adicionales para habilitar las pruebas de canisters. Light
Replica se puede utilizar para probar cualquier archivo Wasm como si fuera un
canister desplegado en la red principal.

[Más información sobre Light Replica](https://github.com/icopen/lightic/tree/main).
