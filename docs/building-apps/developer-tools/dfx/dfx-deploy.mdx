# dfx deploy

<MarkdownChipRow labels={["Referencia"]} />

Usa el comando `dfx deploy` para registrar, construir y desplegar una dapp en el
entorno de ejecución local de canisters, en la IC o en una testnet especificada.
De forma predeterminada, se despliegan todos los canisters definidos en el
archivo de configuración `dfx.json` del proyecto.

Este comando simplifica el flujo de trabajo del desarrollador al permitirte
ejecutar un solo comando en lugar de ejecutar los siguientes comandos como pasos
separados:

```shell
dfx canister create --all
dfx build
dfx canister install --all
```

Note que solo puede ejecutar este comando desde el directorio del proyecto. Por
ejemplo, si el nombre de su proyecto es `hello_world`, su directorio de trabajo
actual debe ser el directorio principal del proyecto `hello_world` o uno de sus
subdirectorios.

## Uso básico

```bash
dfx deploy [options] [canister_name]
```

## Opciones

Puedes usar las siguientes opciones con el comando `dfx deploy`.

| Opción                             | Descripción                                                                                                                                                                                                                                                                                     |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--network <network>`              | Sobrescribe el entorno al que conectarse. De forma predeterminada, se usa el entorno local de ejecución de canisters.                                                                                                                                                                           |
| `--playground`                     | Alias para `--network playground`. De forma predeterminada, los canisters en esta red se toman del Motoko Playground.                                                                                                                                                                           |
| `--ic`                             | Alias para `--network ic`.                                                                                                                                                                                                                                                                      |
| `--argument <argument>`            | Especifica un argumento para pasar al canister durante la instalación.                                                                                                                                                                                                                          |
| `--argument-type <argument-type>`  | Especifica el tipo de dato para el argumento al hacer la llamada utilizando un argumento [valores posibles: idl, raw]                                                                                                                                                                           |
| `--argument-file <argument-file>`  | Especifica el archivo desde el cual leer el argumento para pasar al método de inicialización. Stdin puede referirse como `-`.                                                                                                                                                                   |
| `--created-at-time <timestamp>`    | Marca temporal de la transacción, en nanosegundos, para su uso en el control de deduplicación de transacciones. El valor predeterminado es la hora del sistema. https://internetcomputer.org/docs/developer-docs/integrations/icrc-1/#transaction-deduplication                                 |
| `--from-subaccount <subaccount>`   | Subcuenta de la identidad seleccionada para gastar ciclos.                                                                                                                                                                                                                                      |
| `-m`, `--mode <mode>`              | Especifica si deseas `instalar`, `reinstalar` o `actualizar` canisters. El valor predeterminado es `auto`. Para más información sobre modos de instalación y gestión de canisters, consulta [gestión de canisters](/docs/building-apps/canister-management/settings).                           |
| `--with-cycles <number-of-cycles>` | Te permite especificar el número inicial de ciclos para un canister en un proyecto.                                                                                                                                                                                                             |
| `--specified-id <PRINCIPAL>`       | Intenta crear el canister con este Canister ID.                                                                                                                                                                                                                                                 |
| `--by-proposal`                    | Sube los activos propuestos cambiados, pero no los confirma. Luego, haz un seguimiento llamando a `commit_proposed_batch()` o `delete_batch()`.                                                                                                                                                 |
| `--compute-evidence`               | Construye un canister de frontend, determina las operaciones por lotes necesarias para sincronizar los contenidos del canister de activos y calcula un hash sobre esas operaciones. Muestra este hash ("evidence"), que debe coincidir con el evidence mostrado por `dfx deploy --by-proposal`. |
| `--subnet-type <subnet-type>`      | Especifica el tipo de subnet para crear el canister. Si no se proporciona un tipo de subnet, el canister se creará en una subnet predeterminada aleatoria.                                                                                                                                      |
| `--subnet <subnet-principal>`      | Especifica la subnet para crear el canister. Si no se proporciona una subnet, el canister se creará en una subnet predeterminada aleatoria.                                                                                                                                                     |
| `--next-to <canister-principal>`   | Crea los canisters en la misma subnet que este canister.                                                                                                                                                                                                                                        |
| `--skip-pre-upgrade`               | Omite el hook de `pre_upgrade` en la actualización. Esto requiere el modo de actualización/auto.                                                                                                                                                                                                |
| `--wasm-memory-persistence <mode>` | Mantén o reemplaza la memoria principal Wasm en la actualización. Valores posibles: `keep`, `replace`. Esto requiere el modo de actualización/auto.                                                                                                                                             |

### Especifica el argumento a pasar al punto de entrada de inicialización

Con `--argument-type`, puedes especificar el formato de datos para el argumento
al instalar usando la opción `--argument`. Los valores válidos son `idl` y
`raw`. De forma predeterminada, puedes especificar los argumentos utilizando la
sintaxis de
[Candid](/docs/building-apps/interact-with-canisters/candid/candid-concepts)
(`idl`) para valores de datos. Para obtener información sobre el uso de Candid y
sus tipos admitidos, consulta
[Interactuar con un servicio en la terminal](/docs/building-apps/interact-with-canisters/candid/using-candid#idl-syntax)
y [Tipos admitidos](/docs/references/candid-ref). Puedes usar `raw` como el tipo
de argumento si deseas pasar bytes crudos a un canister.

## Argumentos

Puedes especificar los siguientes argumentos para el comando `dfx deploy`.

| Argumento       | Descripción                                                                                                                                                                                                                                                                                                                                                                                 |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `canister_name` | Especifica el nombre del canister que deseas registrar, construir y desplegar. Ten en cuenta que el nombre del canister que especifiques debe coincidir con al menos un nombre en la sección `canisters` del archivo de configuración `dfx.json` para el proyecto. Si no especificas un nombre de canister, `dfx deploy` desplegará todos los canisters definidos en el archivo `dfx.json`. |

## Ejemplos

Puedes usar el comando `dfx deploy` para desplegar todos o canisters específicos
en el entorno local de ejecución de canisters, en la IC o en una testnet
especificada.

Por ejemplo, para desplegar el proyecto `hello` en la testnet hipotética
`ic-pubs` configurada en el archivo de configuración `dfx.json`, puedes ejecutar
el siguiente comando:

```bash
dfx deploy hello_backend --network ic-pubs
```

Para desplegar un proyecto en el entorno local de ejecución de canisters y pasar
un solo argumento al paso de instalación, puedes ejecutar un comando similar al
siguiente:

```bash
dfx deploy hello_actor_class --argument '("from DFINITY")'
```

Nota que actualmente debes usar una clase de actor en tu dapp de Motoko. En este
ejemplo, el comando `dfx deploy` especifica un argumento para pasar al canister
`hello_actor_class`. El programa principal para el canister `hello_actor_class`
se ve así:

```motoko
actor class Greet(name: Text) {
    public query func greet() : async Text {
        return "Hello, " # name # "!";
    };
};
```

Puedes usar el comando `dfx deploy` con la opción `--with-cycles` para
especificar el saldo inicial de un canister creado por tu wallet. Si no
especificas un canister, el número de ciclos que especifiques se agregará a
todos los canisters de forma predeterminada. Para evitar esto, especifica un
canister específico por nombre. Por ejemplo, para agregar un saldo inicial de
8000000000000 ciclos a un canister llamado "hello-assets", ejecuta el siguiente
comando:

```bash
dfx deploy --with-cycles 8000000000000 hello-assets
```
