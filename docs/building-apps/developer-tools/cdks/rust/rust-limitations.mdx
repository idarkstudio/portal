# Limitaciones de Rust en Wasm

<MarkdownChipRow labels={["Intermedio", "Rust", "Tutorial"]} />

WebAssembly (Wasm) es un formato de código binario que no proporciona acceso a
red, sistema de archivos u otras funcionalidades más allá de computación pura.
Cualquier función que necesite comunicarse fuera del módulo Wasm debe usar una
API de IC. Esta guía detalla las limitaciones que Wasm impone a los canisters
escritos en Rust.

## Limitaciones de Wasm

- No puedes crear hilos. En su lugar, usa
  [`ic_cdk::spawn`](https://docs.rs/ic-cdk/0.16.0/ic_cdk/fn.spawn.html).
- No puedes usar sleep. En su lugar, usa
  [`ic_cdk_timers`](https://docs.rs/ic-cdk-timers/latest/ic_cdk_timers/).
- No puedes usar `Instant`. En su lugar, usa
  [`ic_cdk::api::time`](https://docs.rs/ic-cdk/0.16.0/ic_cdk/api/fn.time.html).
- No puedes acceder a variables de entorno con `std::env::var`, pero puedes
  incrustar variables de entorno en tiempo de compilación con la macro `env!`.

## Limitaciones de crates

La mayoría de los crates funcionan en ICP, pero cualquier cosa que realice
entrada/salida no funcionará. Normalmente está bien usar un crate que realiza
E/S siempre que no llames a la función que lo ejecuta. Si intentas desplegar un
canister que use este flujo, ICP devolverá un error sobre importar una función
desde `"env"`.

Los crates que específicamente tienen un modo Wasm generalmente no funcionan
como se espera, ya que usualmente tienen un modo especial para ejecutarse en el
navegador y realizarán su funcionalidad usando funciones JavaScript, que no
existen en ICP. Si intentas desplegar un canister que use este flujo, ICP
devolverá un error sobre importar una función llamada `__wbindgen_describe`.

Un ejemplo es el crate `getrandom`, que normalmente es incluido por otra
dependencia. Si intentas importar `uuid` con la feature `v4`, se niega a
compilar a Wasm, pero si activas su modo Wasm, simplemente da un error diferente
porque intenta usar JavaScript.

En su lugar, `getrandom` te permite crear tu propia función aleatoria con la
macro `register_custom_getrandom!`. El siguiente boilerplate eliminará el error
y permitirá que otros crates obtengan aleatoriedad como de costumbre:

```rust
thread_local! {
// A global random number generator, seeded when the canister is initialized
static RNG: RefCell<Option<StdRng>> = RefCell::new(None);
}
#[init]
fn init() {
init_rng();
}
// Static variables are cleared on upgrade, so also initialize it on post-upgrade.
#[post_upgrade]
fn post_upgrade() {
init_rng();
}
// Randomness on the IC is async, and the custom getrandom function can't be async,
// so we seed an RNG instead of always calling raw_rand directly
fn init_rng() {
// raw_rand is technically an inter-canister call, and you can't make those from lifecycle functions like #[init],
    // so we schedule an immediate timer to make the call instead
    ic_cdk_timers::set_timer(Duration::ZERO, || ic_cdk::spawn(async {
        let (seed,) = ic_cdk::api::management_canister::main::raw_rand().await.unwrap();
// StdRng is from the `rand` crate. It makes for a good default but any RNG implementation would work
        RNG.with(|rng| *rng.borrow_mut() = Some(StdRng::from_seed(seed.try_into().unwrap())));
    }));
}
register_custom_getrandom!(custom_getrandom);
fn custom_getrandom(buf: &mut [u8]) -> Result<(), getrandom::Error> {
    RNG.with(|rng| rng.borrow_mut().as_mut().unwrap().fill_bytes(buf));
    Ok(())


```

Los crates en la categoría [`no-std`](https://crates.io/categories/no-std)
generalmente funcionan como se espera.

Limitaciones adicionales de crates incluyen:

- No puedes usar `tokio`, usa
  [`ic_cdk::spawn`](https://docs.rs/ic-cdk/0.16.0/ic_cdk/fn.spawn.html) en su
  lugar.
- No puedes usar crates que realicen o sirvan solicitudes HTTP. En su lugar,
  utiliza
  [Llamadas externas HTTP](/docs/building-apps/network-features/using-http/https-outcalls/overview)
  o la [API de gateway](/docs/references/http-gateway-protocol-spec/)
