# Estados mutables globales

<MarkdownChipRow labels={["Principiante", "Rust"]} />

Por diseño, los canisters en ICP están estructurados de manera que obliga a los
desarrolladores a usar un estado mutable global. Sin embargo, el diseño de Rust
dificulta el uso de variables globales mutables. Esto hace que los
desarrolladores de Rust necesiten elegir un método de organización de código que
tenga en cuenta el diseño de ICP. Esta guía cubrirá algunas de esas opciones de
organización de código.

### Usar `thread_local!` con `Cell/RefCell` para variables de estado

Usar `thread_local!` con `Cell/RefCell` es la opción más segura para evitar
problemas con llamadas asíncronas y corrupción de memoria. El siguiente es un
ejemplo de cómo se puede usar `thread_local!`:

```rust
thread_local! {
    static NEXT_USER_ID: Cell<u64> = Cell::new(0);
    static ACTIVE_USERS: RefCell<UserMap> = RefCell::new(UserMap::new());
}
```

### El código del canister debe ser independiente del objetivo

Vale la pena dividir la mayor parte del código del canister en módulos y
paquetes débilmente acoplados y probarlos de forma independiente. La mayor parte
del código que depende de la API del sistema debe ir en el archivo principal.

También es posible crear una abstracción delgada para la API del sistema y
probar tu código con una implementación falsa pero fiel. Por ejemplo, podrías
usar el siguiente trait para abstraer la API de memoria estable:

```rust
pub trait Memory {
    fn size(&self) -> WasmPages;
    fn grow(&self, pages: WasmPages) -> WasmPages;
    fn read(&self, offset: u32, dst: &mut [u8]);
    fn write(&self, offset: u32, src: &[u8]);
}
```

## Observabilidad

Las métricas se pueden usar para obtener información sobre una amplia gama de
aspectos relacionados con los servicios de producción de tu canister. Estos
datos son importantes para conocer las estadísticas y productividad de tu
canister. Las siguientes métricas pueden ser importantes de monitorear:

- El tamaño de la memoria estable del canister.
- El tamaño de las estructuras de datos internas del canister.
- Los tamaños de los objetos asignados dentro del heap.
- La fecha y hora en que el canister se actualizó por última vez.

En Rust, puedes exponer una llamada de consulta que devuelva una estructura de
datos que contenga las métricas de tu canister. Si estos datos no están
destinados a ser públicos, esta consulta se puede configurar para que se rechace
según el principal del llamante. Este enfoque proporciona una respuesta
estructurada y fácil de analizar.

```rust
pub struct MyMetrics {
  pub stable_memory_size: u32,
  pub allocated_bytes: u32,
  pub my_user_map_size: u64,
  pub last_upgraded_ts: u64,
}
#[query]
fn metrics() -> MyMetrics {
  check_acl();
  MyMetrics {
    // ...
  }
}
```

También puedes exponer las métricas del canister en un formato que tu sistema de
monitoreo pueda ingerir a través de la puerta de enlace HTTP del canister. Para
formatos de exposición basados en texto, se puede usar el siguiente ejemplo:

```rust
fn http_request(req: HttpRequest) -> HttpResponse {
  match path(&req) {
    "/metrics" => HttpResponse {
        status_code: 200,
        body: format!("\
stable_memory_bytes {}
allocated_bytes {}
registered_users_total {}",
                      stable_memory_bytes, allocated_bytes, num_users),
        // ...
    }
  }
}
```
