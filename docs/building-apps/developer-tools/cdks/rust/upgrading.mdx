# Actualización de un canister Rust

<MarkdownChipRow labels={["Principiante", "Rust", "Tutorial"]} />

A diferencia de una reinstalación de canister que preserva el identificador pero
no el estado, una actualización de canister permite preservar el estado mientras
se cambia el código.

Por ejemplo, supongamos que tienes una dapp que gestiona perfiles profesionales
y conexiones sociales. Si deseas añadir una nueva funcionalidad, necesitas poder
actualizar el código del canister sin perder los datos almacenados previamente.
Una actualización de canister te permite modificar el código manteniendo el
mismo identificador y conservando el estado del programa.

## Proceso de actualización de canisters

Cuando un canister necesita actualizarse, se sigue este flujo:

1. El sistema descarta la memoria del canister e instancia la nueva versión del
   módulo WebAssembly. La memoria estable se preserva y queda disponible en la
   nueva versión.
2. El sistema llama al hook `post_upgrade` en la nueva instancia si está
   definido. La función `init` no se ejecuta.
3. Si ocurre un error irrecuperable (trap) durante estos pasos, el sistema
   revierte el canister a su estado previo a la actualización.

### Versionado de memoria estable

La memoria estable es un mecanismo de persistencia de datos en ICP que persiste
entre actualizaciones, con capacidad máxima de 500GiB (según disponibilidad de
la subred).

Comparativamente, la memoria heap (o "memoria principal") es el almacenamiento
regular Wasm de un canister, limitado a 4GiB y no persistente entre
actualizaciones.

La memoria estable actúa como canal de comunicación entre versiones antiguas y
nuevas de un canister. Como buena práctica, estos protocolos de comunicación
deben versionarse. En cambios radicales (como modificar formatos de
serialización o disposición de datos), el mecanismo de decodificación podría
necesitar adivinar el formato, lo que puede volverse complejo. Para
simplificarlo, se recomienda implementar versionado, que puede ser tan simple
como usar el primer byte de la memoria estable para indicar el número de
versión.

### Pruebas de hooks de actualización

Es una mejor práctica probar las actualizaciones antes de aplicarlas para
detectar posibles errores que podrían causar pérdida irreversible de datos. Para
probar actualizaciones se pueden usar varios enfoques:

- Scripts en shell/bash
- Scripts de prueba en Rust

El siguiente pseudocódigo muestra un ejemplo en Rust que añade un paso adicional
para validar el estado después de una prueba de actualización:

```
let canister_id = install_canister(WASM);
populate_data(canister_id);
if should_upgrade { upgrade_canister(canister_id, WASM); }
let data = query_canister(canister_id);
assert_eq!(data, expected_value);
```

Luego, tus pruebas deben ejecutarse dos veces en dos escenarios diferentes:

1. **Escenario sin actualizaciones**: Para verificar que las pruebas funcionan
   correctamente sin ejecutar una actualización.
2. **Escenario con actualización**: Para asegurar que las pruebas funcionan
   correctamente durante una actualización.

Al ejecutar ambos tipos de pruebas, los desarrolladores pueden confirmar que
cuando se aplica una actualización a un canister, se preserva correctamente el
estado del mismo.

:::caution

Advertencia sobre hooks de actualización El uso de hooks `pre_upgrade` y
`post_upgrade` está desaconsejado porque:

- Son propensos a errores
- Pueden dejar el canister inutilizable
- Según las mejores prácticas, deberían evitarse cuando sea posible

Si decides usarlos:

- Evita que el hook `pre_upgrade` falle (haga trap), ya que mientras un error en
  `post_upgrade` permite depurar y crear otra versión, un error en `pre_upgrade`
  te deja sin opciones para cambiar el comportamiento del canister.

:::

### Usar memoria estable como almacenamiento principal

Durante una actualización, existe un límite de cycles que el canister puede
consumir. Si se excede este límite:

- El sistema cancelará la actualización
- Revertirá el estado del canister

Esto es especialmente problemático si:

- Serializas todo el estado del canister a memoria estable en `pre_upgrade`
- El estado es muy grande (podría impedir futuras actualizaciones)

**Solución alternativa**: Usar memoria estable como almacenamiento principal
desde el inicio, guardando cada llamada de actualización. Esto permite:

- Eliminar la necesidad del hook `pre_upgrade`
- Reducir el consumo de cycles en `post_upgrade`

:::caution

Consideraciones importantes Este enfoque tiene desventajas:

1. Organizar el espacio de direcciones plano de la memoria estable en
   estructuras de datos complejas es difícil (puedes usar el paquete
   [ic-stable-structures](https://crates.io/crates/ic-stable-structures) para
   ayudar)
2. Modificar el diseño de datos puede ser contraproducente
3. Necesidad de mantener compatibilidad hacia atrás (nuevas versiones deben
   poder leer datos de versiones anteriores)

:::

**Recomendación**: Vale la pena considerar este enfoque si tu canister:

- Almacenará gigabytes de datos
- Necesitará actualizaciones frecuentes de código

## Procedimiento para actualizar un canister

Para actualizar un canister:

1. Obtén el identificador del canister usando el comando:

```bash
dfx canister id [canister-name]
```

Luego, haz cualquier cambio en el código del canister que desees incluir en la
actualización.

Para actualizar todos los canisters, usa el comando:

```bash
dfx canister install --all --mode upgrade
```

Para actualizar un solo canister, usa el comando:

```bash
dfx canister install [canister-id] --mode upgrade
```
