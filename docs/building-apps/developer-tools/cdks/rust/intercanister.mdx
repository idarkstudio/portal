# Llamadas entre canisters

<MarkdownChipRow labels={["Principiante", "Rust", "Tutorial"]} />

Así como los usuarios pueden llamar a canisters, los canisters también pueden
llamar a otros canisters. Este tutorial proporciona una introducción al uso de
estas llamadas entre canisters en Rust.

Este ejemplo mostrará cómo llamar al canister contador, que proporciona cuatro
operaciones sobre un contador:

1. Obtener el valor del contador.
2. Incrementar el contador.
3. Establecer el contador a un valor arbitrario.
4. Establecer el contador a un valor arbitrario mientras se devuelve el valor
   anterior.

## Prerrequisitos

Para seguir este tutorial, clona el
[repositorio Git](https://github.com/dfinity/examples) del ejemplo. El código
para este tutorial está en el directorio `rust/inter-canister-calls`, donde
puedes encontrar el código completo en el paquete `caller`. Ten en cuenta que
este ejemplo usa la versión alpha del Rust CDK.

Clona el repositorio Git del tutorial. Luego, en el directorio del tutorial,
inicia una instancia local de IC en segundo plano e instala el canister
contador:

```bash
dfx start --background
dfx deploy counter
```

## Ejemplo básico: obtener y establecer el valor del contador

Tu primer ejemplo será un método `call_get_and_set` en el canister llamador
(caller), que simplemente invoca el método `get_and_set` del proyecto contador y
devuelve el resultado. Este método establece el contador a un nuevo valor y
retorna el valor previo del contador.

El código terminado para este proyecto ya está disponible en `src/caller`.
Puedes borrar el contenido de `src/caller/src/lib.rs` y pegar el siguiente
código. La explicación se encuentra en los comentarios.

```rust reference
https://github.com/dfinity/examples/blob/d0d3fc814d8ae646d6aba3878d01f08d42da0d4f/rust/inter-canister-calls/src/caller/src/lib.rs#L1-L40
```

Ahora, despliega este código en la réplica local. Esto te dará algunas
advertencias sobre importaciones no utilizadas, pero estas se usarán más tarde
en el tutorial.

```bash
dfx deploy caller
```

Vamos a probarlo. Haz una llamada al canister `caller`:

```bash
dfx canister call caller call_get_and_set
```

Ahora, `dfx` usará el archivo `dfx.json` proporcionado en el repositorio de este
tutorial para buscar qué parámetros requieren los diferentes endpoints del
canister `caller`. El archivo `dfx.json` apunta al archivo
`src/caller/caller.did`, que describe los parámetros de `call_get_and_set`. Con
esto, `dfx` primero te pedirá que proporciones un principal para el parámetro
`counter` del método `call_get_and_set`.

Puedes escribir `counter` y presionar `TAB` en tu teclado para pasar el
principal del canister contador como parámetro, y luego `Enter` para confirmar.
También selecciona un número para establecer el contador, digamos `42`.
Entonces, verás una salida como:

```bash
(0 : nat, 42 : nat)
```

Aquí, el contador se incrementó de `0` a `42`.

Como señala el ejemplo, hacer panic al manejar errores de llamadas generalmente
es una mala idea más allá de ejemplos triviales como este. Esto se debe a la
naturaleza del modelo de mensajería de Internet Computer.

## Las llamadas en IC son asíncronas: set-then-get no atómico

Ya has visto que las llamadas entre canisters usan la sintaxis `async/await` de
Rust, lo que sugiere que estas llamadas son **asíncronas**. Esta es una
diferencia profunda con el modelo de mensajería de otras cadenas (como
Ethereum). Permite un rendimiento significativamente mayor, pero también puede
afectar la corrección.

Para ilustrarlo, veamos el siguiente ejemplo donde primero llama al método `set`
en el contador, y luego llama a `get` después. Agrega el siguiente código a tu
`src/caller/src/lib.rs`:

```rust reference
https://github.com/dfinity/examples/blob/d0d3fc814d8ae646d6aba3878d01f08d42da0d4f/rust/inter-canister-calls/src/caller/src/lib.rs#L42-L60
```

Vamos a probarlo. Como se muestra a continuación, también puedes pasar los
argumentos directamente a `dfx` en lugar de usar el menú codificando los
[valores Candid](/docs/building-apps/interact-with-canisters/candid/candid-concepts)
manualmente.

```bash
dfx canister call caller set_then_get "( principal \"`dfx canister id counter`\", 7 : nat )"
```

Deverías obtener el resultado esperado:

```bash
(7 : nat)
```

El valor leído del contador es exactamente el mismo que el valor establecido.
Pero como se menciona en los comentarios, ¡esto no siempre tiene que ser así!
Como las llamadas en IC se ejecutan de forma asíncrona, entre la ejecución de
las llamadas `set` y `get` en `call_get_and_set`, otro canister podría llamar al
contador y cambiar su valor. Esto no puede ocurrir en tu instalación local ya
que controlas exactamente qué llamadas se hacen, pero sí puede pasar cuando el
código se instale en la mainnet de IC.

Este comportamiento permite un mayor rendimiento concurrente entre diferentes
canisters, ya que el canister contador no se bloquea para procesar otras
solicitudes mientras el canister llamador realiza su procesamiento. Sin embargo,
también tiene implicaciones para la corrección y seguridad. Un aspecto
particularmente importante es que los cambios de estado no son atómicos. Si
haces múltiples llamadas, el fallo de una llamada posterior no revierte los
efectos de llamadas anteriores.

Esto también aplica para los efectos en el propio canister llamador.
Específicamente, un llamador que entra en pánico después de hacer una llamada
puede terminar en un estado inconsistente. Esto no es un problema para los
ejemplos mostrados hasta ahora, ya que el estado interno del llamador no existe
y por lo tanto no puede volverse inconsistente.

Para más información sobre el modelo de ejecución asíncrono y sus implicaciones,
consulta la documentación sobre:

- [Llamadas entre canisters y código asíncrono](/docs/references/async-code)
- [Propiedades de ejecución de mensajes](/docs/references/message-execution-properties)
- [Mejores prácticas de seguridad](/docs/building-apps/security/security-best-practices/inter-canister-calls)

:::info

En resumen, Internet Computer tiene un modelo de mensajería asíncrono diferente
al de Ethereum y otras blockchains. Esto mejora la escalabilidad, pero necesitas
entender las implicaciones, especialmente sobre cuándo y cómo se persiste el
estado.

:::

## Llamadas de espera no acotada: semántica y casos de error

Los ejemplos hasta ahora han usado _llamadas de espera no acotada_ sin explicar
qué son. Una llamada de espera no acotada instruye al sistema a esperar el
tiempo que sea necesario para recibir una respuesta. Esto permite que el sistema
siempre proporcione al llamador la respuesta exacta a la llamada. Como se
garantiza que la respuesta será entregada al llamador, estas llamadas también se
conocen como _llamadas con respuesta garantizada_.

Ten en cuenta que esta respuesta aún puede ser un fallo. Por ejemplo, una
llamada podría fallar porque el canister llamado no existe (fue eliminado), o
porque el sistema está sobrecargado y no puede entregar la llamada, devolviendo
un error al llamador. También puede fallar si el canister llamado falla, por
ejemplo, si entra en pánico. Cuando no hay fallos en el canister llamado, un
resultado de error en una llamada de espera no acotada garantiza que la llamada
no se ejecutó, es decir, que fue limpiamente rechazada. Extiende el ejemplo
añadiendo este código a `src/caller/src/lib`:

```rust reference
https://github.com/dfinity/examples/blob/d0d3fc814d8ae646d6aba3878d01f08d42da0d4f/rust/inter-canister-calls/src/caller/src/lib.rs#L62-L80
```

Un rechazo limpio de la llamada de incremento significa que el contador no ha
cambiado. En general, si una llamada que cambia el estado del destinatario (como
`increment`) es rechazada, esto significa que el estado no ha cambiado. Con un
rechazo no limpio, puede que no sepas qué pasó en el lado del destinatario y
podría ser necesario un análisis exhaustivo.

Las únicas causas de rechazos no limpios para llamadas no acotadas son panics y
rechazos en el lado del destinatario. Estos pueden ser rechazos intencionales, o
panics intencionales en condiciones de error (como los ejemplos con las
funciones `expect` usadas anteriormente). También pueden ser bugs en el
destinatario o que el runtime Wasm falle (el equivalente Wasm de los panics)
porque el destinatario se quedó sin recursos, como memoria disponible o cycles
para realizar algunas operaciones. En configuraciones locales por defecto, no
tienes que preocuparte por estos recursos.

Vuelve a desplegar el canister para compilar el código añadido, luego observa el
efecto de `call_increment`:

```bash
dfx deploy caller
dfx canister call counter get
(7: nat)
dfx canister call caller call_increment "( principal \"`dfx canister id counter`\" )"
()
dfx canister call counter get
(8: nat)
```

Sin embargo, en mainnet, sin precauciones adicionales incluso incrementar
nuestro simple canister contador podría fallar porque no puede asignar memoria
para procesar la solicitud. Para manejar esto, la
[mejor práctica](/docs/building-apps/best-practices/idempotency) es modificar el
destinatario para proporcionar un endpoint que permita a los llamadores
consultar el resultado de llamadas que cambian el estado. Además, cuando sea
posible, también es una buena práctica hacer que los endpoints sean
_idempotentes_, donde ejecutar una llamada dos veces (y por lo tanto múltiples
veces) tiene el mismo efecto que ejecutarla una sola vez, permitiendo al
llamador simplemente reintentar su llamada. Estas prácticas también son útiles
para llamadas de entrada, es decir, para usuarios externos y aplicaciones que
interactúan con tu aplicación a través de HTTP.

Las llamadas de espera no acotada pueden proporcionar una semántica simple de
manejo de errores, siempre que estés muy seguro de que el destinatario no
fallará, o por alguna razón no te importen los casos en que el destinatario
falle. Sin embargo, el hecho de que estas llamadas esperarán todo el tiempo
necesario para recibir una respuesta significa que no regresarán mientras el
destinatario esté retrasando la respuesta. En el caso de destinatarios con
bugs - o incluso maliciosos - el llamador podría terminar esperando para
siempre. Esto puede bloquear al llamador para actualizarse limpiamente, ya que
una actualización limpia requiere que todas las llamadas pendientes del llamador
se completen. Como alternativa, puedes usar llamadas de _espera acotada_, que
veremos a continuación.

:::info

En resumen, las llamadas de espera no acotada esperan una respuesta para
siempre, pero la respuesta aún podría ser un fallo. Con llamadas de espera no
acotada, los fallos significan que o la llamada no se ejecutó, o que el
destinatario falló o rechazó la llamada. Esperar para siempre conlleva riesgos
al llamar a canisters no confiables.

:::

## Llamadas de espera acotada: semántica y casos de error

Las _llamadas de espera acotada_ no esperan para siempre a que llegue la
respuesta, sino que efectivamente expirarán después de un tiempo y simplemente
devolverán un error al llamador. Por esta razón, también se les conoce como
llamadas de _respuesta de mejor esfuerzo_. Estas llamadas tienen dos ventajas
significativas sobre las llamadas de espera no acotada:

1. Aseguran que tu canister no se bloqueará (en particular, no se volverá
   incapaz de detenerse y actualizarse) si llama a canisters que no controlas o
   en los que no confías.
2. Escalan mucho mejor.

Sin embargo, tienen un manejo de errores más complicado: los rechazos no
limpios - donde no sabes si la llamada se ejecutó - pueden resultar no solo de
panics en el llamador, sino también de que la llamada expire. Esto aumenta
significativamente la probabilidad de rechazos no limpios. Los panics del
destinatario deberían ser casos extremos, pero los timeouts también ocurrirán
cuando la carga en el sistema o el destinatario sea alta.

Por lo tanto, las llamadas de espera acotada solo son adecuadas para lecturas, o
para llamadas que cambian el estado y siguen la mejor práctica de proporcionar
un endpoint de consulta separado para el resultado, y/o son idempotentes.

Por ejemplo, puedes llamar de forma segura al endpoint `get` del contador usando
una llamada de espera acotada, ya que esto es solo una lectura. Edita
`src/caller/src/lib.rs` para añadir el siguiente método:

```rust reference
https://github.com/dfinity/examples/blob/d0d3fc814d8ae646d6aba3878d01f08d42da0d4f/rust/inter-canister-calls/src/caller/src/lib.rs#L82-L99
```

Vamos a probarlo. Despliega el canister y llama al nuevo método:

```bash
dfx deploy caller
dfx canister call caller call_get "( principal \"`dfx canister id counter`\" )"
(variant { Ok = 8 : nat })
```

Idempotent endpoints give the caller a chance to try and clean errors up by
simply retrying. For example, the `set` endpoint of the counter is idempotent.
But even with idempotent endpoints, there are limits to what the caller can do.
For example, it shouldn't retry forever, because, as mentioned earlier, this
might block the canister from upgrading.

Furthermore, there are also errors that are likely to be hit again if you just
retry immediately. In this case, you will have to leave the clean up to the
upstream caller. Let's see an example of what a retry strategy might look like.

```rust reference
https://github.com/dfinity/examples/blob/d0d3fc814d8ae646d6aba3878d01f08d42da0d4f/rust/inter-canister-calls/src/caller/src/lib.rs#L101-L137
```

Para probar, llamemos al nuevo endpoint con el valor 42.

```bash
dfx canister call caller stubborn_set "( principal \"`dfx canister id counter`\", 42 : nat )"
(variant { Ok })
```

El Rust CDK proporciona funciones útiles como `is_clean_reject` e
`is_immediately_retryable` para ayudar con el manejo de errores. Internamente,
estas interpretan los diferentes códigos de rechazo generados por el sistema. Si
tienes más conocimiento sobre cómo funciona tu canister, podrías proporcionar
una interpretación más precisa para tu caso de uso. Consulta la
[especificación de interfaz](/docs/references/ic-interface-spec/) y su sección
sobre [códigos de rechazo](/docs/references/ic-interface-spec/#reject-codes)
para más detalles.

:::info

En resumen, las llamadas de espera acotada expirarán después de un tiempo, pero
podrías no saber si el destinatario ejecutó la llamada o no. Úsalas para
lecturas o endpoints que sean idempotentes o que proporcionen una forma de
consultar sus resultados.

:::

## Adjuntar cycles: firmas de canister

Un canister puede adjuntar
[cycles](/docsbuilding-apps/getting-started/tokens-and-cycles) (el "gas" de
Internet Computer) a cualquier llamada que realice, transfiriendo cycles del
balance del llamador al del destinatario. El destinatario debe
[aceptar](https://docs.rs/ic-cdk/latest/ic_cdk/api/call/fn.msg_cycles_accept128.html)
explícitamente estos cycles; los cycles no aceptados son reembolsados al
llamador.

Las transferencias de cycles generalmente se usan para pagar los costos de
procesamiento de la llamada por parte del destinatario o para mover y almacenar
cycles como activos. Un ejemplo donde se usan para pagar costos de procesamiento
es la
[función de firmas de umbral](/docs/building-apps/network-features/signatures/t-ecdsa)
del IC, que permite a un canister mantener una clave criptográfica y firmar
mensajes con ella. Un ejemplo de cycles usados como activos es el
[libro mayor de cycles](/docs/defi/token-ledgers/cycles-ledger/).

A continuación se muestra un ejemplo de firma de umbral que ilustra cómo
adjuntar cycles a una llamada:

```rust reference
https://github.com/dfinity/examples/blob/d0d3fc814d8ae646d6aba3878d01f08d42da0d4f/rust/inter-canister-calls/src/caller/src/lib.rs#L139-L181
```

Vamos a probar esto llamando al método `sign_message`. La firma exacta en tu
respuesta será diferente, ya que se basará en una clave secreta de tu réplica
local.

```bash
dfx canister call caller sign_message '("Some text to be signed")'
(
  variant {
    Ok = "394b7250ab7a088238fae3af9b60fec521584ac8c874b2ca72e6b950cda509452f307006693c342636afb5b2cb7a395106cc04365bd499c0064f5842a0bdbe2f"
  },
)
```

Los cycles pueden adjuntarse tanto a mensajes de espera acotada como no acotada.
Para mensajes de espera no acotada, los cycles no consumidos por el destinatario
están garantizados de ser reembolsados al llamador. Como señala el ejemplo, no
hay reembolsos para llamadas de espera acotada que resulten en un error con el
código de rechazo `SysUnknown`, que es el código emitido cuando el sistema
decide dejar de esperar una respuesta.

Sin embargo, esto suele ser aceptable para llamadas API que cobran cycles, ya
que el monto cargado suele ser bajo (10 mil millones de cycles para firmas con
la clave de prueba). Para transferir cantidades mayores de cycles, cambia a usar
llamadas de espera no acotada. Consulta la sección sobre
[llamadas entre canisters](/docs/references/async-code) para más detalles.

:::info

En resumen, puedes transferir cycles al destinatario adjuntándolos a una llamada
de espera acotada o no acotada. Las llamadas de espera acotada pueden perder los
cycles adjuntos, así que evita usarlas para cantidades grandes de cycles.

:::
