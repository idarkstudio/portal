# Orígenes alternativos de frontend

<MarkdownChipRow labels={["Intermedio", "Autenticación"]} />
Si tu aplicación ha alcanzado la etapa en la que deseas cambiar los nombres de dominio
y has estado autenticando con Internet Identity (II), querrás asegurarte de que tus
usuarios puedan mantener sin problemas los mismos principals que ya han estado utilizando.
Para admitir esta funcionalidad, puedes configurar tu aplicación para orígenes alternativos
de frontend utilizando esta guía.

![Resultado final](./_attachments/alternative-origins.png)

Es posible que necesites esta guía si estás realizando alguna de las siguientes
acciones:

- Migrando de `<canister-id>.icp0.io` a un
  [dominio personalizado](/docs/building-apps/frontends/custom-domains/using-custom-domains/).
- Pidiendo a los usuarios que inicien sesión en `/login` en lugar de `/`.
- Admitiendo usuarios que usan `raw.icp0.io`.
- Configurando varias aplicaciones en tu organización para que usen los mismos
  principals.

## Restricciones

Actualmente, se pueden listar un máximo de **10** orígenes alternativos.

Internet Identity solo seguirá esta especificación cuando el origen que
configura estos alternativos esté alojado en un canister que utilice **activos
certificados**.

Para más información, consulta la
[especificación de Internet Identity](/docs/references/ii-spec/#alternative-frontend-origins).

## Configuración de orígenes alternativos

En este ejemplo, tendrás dos dominios, **A** y **B**. **A** será el origen
canónico y **B** será el dominio alternativo. Para ilustrar este modelo,
considera un sitio web alojado tanto en `https://yourcustomdomain.com` como en
`https://www.yourdomain.com`.

En este caso, **A** sería `https://yourcustomdomain.com`.

:::info Para casos de uso en producción, el dominio **A** debería ser un dominio
en ICP, como `ic0.app` o `icp0.io`. :::

**B** sería el origen alternativo, es decir, `https://www.yourdomain.com`.

### Listado de orígenes

En el origen **A**, debes proporcionar un archivo que indique a Internet
Identity que **B** es un origen alternativo válido. Debes colocar los archivos
de configuración en el directorio `src/assets` de tu canister de frontend. Si tu
canister de frontend está configurado actualmente para desplegar activos desde
una carpeta `dist`, asegúrate de actualizar las `sources` de tu canister para
incluir ambas:

```json title="dfx.json"
"source": [
    "dist",
    "src/assets"
]
```

Dentro de `src/assets`, crea una carpeta `.well-known` y agrega un archivo
llamado `ii-alternative-origins`.

:::info

El archivo debe llamarse exactamente `ii-alternative-origins`, sin extensión de
archivo. El contenido será en formato JSON, pero el archivo no debe terminar en
`.json`.

:::

Dentro del archivo, lista tu origen alternativo para **B**. Se verá algo como
esto:

```json title="src/assets/.well-known/ii-alternative-origins"
{
  "alternativeOrigins": ["https://internetcomputer.org"]
}
```

:::info

Asegúrate de eliminar cualquier barra final o parámetros de consulta del origen.

:::

Ahora, tu proyecto debería tener una estructura similar a esta:

```
├── dfx.json
├── src
│   ├── assets
│   │   ├── .well-known
│   │   │   └── ii-alternative-origins
```

### Configuración de tu canister de frontend

Dado que la sintaxis de punto en `.well-known` generalmente se trata como
"oculta" por el sistema de archivos, el canister de frontend debe configurarse
para subir este documento. Para ello, crea un nuevo archivo llamado
`.ic-assets.json` dentro del directorio `src/assets` o cualquier otro listado en
`sources` de tu canister. Ahora, la lista de archivos debería verse así:

```
├── dfx.json
├── package.json
├── src
│   ├── project_frontend
│   │   ├── src
│   │   │   ├── .ic-assets.json
│   │   │   ├── .well-known
│   │   │   │   └── ii-alternative-origins
```

Luego, configura el directorio `.well-known` para que sea incluido con:

```json title="src/project_frontend/src/.ic-assets.json"
[
  {
    "match": ".well-known",
    "ignore": false
  },
  {
    "match": ".well-known/ii-alternative-origins",
    "headers": {
      "Access-Control-Allow-Origin": "*",
      "Content-Type": "application/json"
    },
    "ignore": false
  }
]
```

Esto incluye una regla general para no ignorar el directorio `.well-known` y
reglas específicas para servir `ii-alternative-origins` con cabeceras de control
de acceso y tipo de contenido.

Luego, solo necesitas desplegar tu canister. A partir de este momento, cuando
intentes autenticarte desde el origen **B**, recibirás el mismo principal que
obtienes al usar **A**. Esto debe complementarse con la configuración del
`AuthClient` para solicitar específicamente el uso del dominio **A** al
autenticar desde **B**, es decir, estableciendo `derivationOrigin` en las
opciones de la llamada a `login`.
