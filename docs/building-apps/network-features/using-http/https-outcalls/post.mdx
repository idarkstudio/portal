# HTTPS outcalls: POST

<MarkdownChipRow labels={["Avanzado", "Tutorial"]} />

Un ejemplo mínimo de cómo hacer una solicitud HTTP `POST`. El propósito de esta
dapp es solo mostrar cómo hacer solicitudes HTTP desde un canister. Envía una
solicitud `POST` con un JSON a una API gratuita donde se puede verificar que los
encabezados y el cuerpo se enviaron correctamente.

:::caution

La función de HTTPS outcalls solo funciona para enviar solicitudes HTTP `POST` a
servidores o endpoints de API que admitan **IPv6**.

:::

Para verificar que tu canister envió la solicitud HTTP esperada, este canister
está enviando solicitudes HTTP a un
[servicio de API público](https://putsreq.com/aL1QS5IbaQd4NTqN3a81/inspect),
donde se puede inspeccionar la solicitud HTTP. Como se muestra en la imagen a
continuación, se pueden revisar los encabezados y el cuerpo de la solicitud
`POST` para asegurarse de que es lo que el canister envió.

![API pública para inspeccionar solicitud POST](../../_attachments/https-post-requestbin-result.webp)

## Notas importantes sobre solicitudes `POST`

Dado que las HTTPS outcalls pasan por consenso, un desarrollador debe esperar
que cualquier solicitud HTTP `POST` desde un canister se envíe múltiples veces a
su destino. Incluso ignorando el componente Web3, las solicitudes `POST`
duplicadas no son un problema nuevo en HTTPS, donde los clientes suelen
reintentar solicitudes por diversas razones (por ejemplo, si el servidor de
destino no está disponible).

La forma recomendada de manejar solicitudes HTTP `POST` es agregar claves de
idempotencia en los encabezados para que el servidor de destino pueda
identificar qué solicitudes `POST` del cliente son las mismas.

Los desarrolladores deben asegurarse de que el servidor de destino entienda y
utilice claves de idempotencia. Un canister puede enviar claves de idempotencia,
pero en última instancia, depende del servidor receptor saber qué hacer con
ellas. Aquí tienes un
[ejemplo de un servicio API que usa claves de idempotencia](https://stripe.com/docs/api/idempotent_requests).

Los encabezados en la respuesta pueden no ser siempre idénticos en todos los
nodos que procesan la solicitud para el consenso, lo que provoca que el
resultado de la llamada sea "No se pudo alcanzar consenso". Este mensaje de
error en particular puede ser difícil de depurar, pero un método para resolver
este error es editar la respuesta usando la función transform. La función
transform se ejecuta antes del consenso y se puede utilizar para eliminar
algunos encabezados de la respuesta.
