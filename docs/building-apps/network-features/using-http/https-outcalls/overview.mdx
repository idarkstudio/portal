# HTTPS outcalls

<MarkdownChipRow labels={["Avanzado", "Network feature"]} />

Los canisters pueden hacer una solicitud a una URL utilizando
[HTTPS outcalls](https://internetcomputer.org/https-outcalls). Los HTTPS
outcalls se pueden utilizar para obtener datos fuera de la cadena o interactuar
con sistemas externos, como servicios Web 2.0 o infraestructura de TI
empresarial.

Los HTTPS outcalls permiten una amplia gama de aplicaciones. Por ejemplo, los
servicios oráculo pueden integrarse directamente con ICP de manera confiable, y
las dapps pueden proporcionar notificaciones a los usuarios o cualquier otra
funcionalidad que requiera comunicación con servidores en Internet.

Algunos ejemplos de servicios onchain tipo oráculo que obtienen datos de fuentes
externas a través de HTTPS outcalls incluyen el
[EVM RPC canister](/docs/building-apps/chain-fusion/ethereum/evm-rpc/overview),
el [exchange rate canister](/docs/references/system-canisters/) y la
[dapp Orally](https://kclew-uiaaa-aaaal-qbuiq-cai.ic0.app/sybil).

## Cómo funciona

Actualmente, la funcionalidad admite los métodos `GET`, `HEAD` y `POST` para
solicitudes HTTP.

Para que un canister utilice HTTPS outcalls, debe llamar a la API del sistema de
ICP. Los canisters pueden llamar a la API del sistema enviando mensajes al
[ICP management canister](/docs/references/ic-interface-spec#ic-management-canister)
utilizando el identificador `"aaaaa-aa"`.

Los [Cycles](/docs/building-apps/essentials/gas-cost) utilizados para pagar la
llamada deben transferirse explícitamente con la solicitud. No se deducen
automáticamente del saldo del remitente.

Para obtener información detallada sobre su funcionamiento, consulta la
[documentación de referencia de HTTPS outcalls](/docs/references/https-outcalls-how-it-works).

## La API para enviar HTTPS outcalls

Según la
[especificación de la interfaz de Internet Computer](/docs/references/ic-interface-spec),
un canister puede utilizar el método `http_request` siguiendo la
[especificación](/docs/references/ic-interface-spec#ic-http_request):

### La solicitud

Los siguientes parámetros deben proporcionarse en la solicitud:

- `url`: La URL solicitada debe ser válida según
  [RFC-3986](https://www.ietf.org/rfc/rfc3986.txt) y su longitud no debe exceder
  `8192`. La URL puede especificar un número de puerto personalizado.

- `max_response_bytes`: Opcional; especifica el tamaño máximo de la respuesta en
  bytes. Si se proporciona, el valor no debe superar `2MB` (`2_000_000B`). El
  costo de la llamada se basará en este parámetro. Si no se proporciona, se
  usará el máximo de `2MB`.

- `method`: Actualmente, solo se admiten `GET`, `HEAD` y `POST`.

- `headers`: Lista de encabezados de solicitud HTTP y sus valores
  correspondientes.

- `body`: Opcional; el contenido del cuerpo de la solicitud.

- `transform`: Una función opcional que transforma respuestas sin procesar en
  [respuestas sanitizadas](https://en.wikipedia.org/wiki/HTML_sanitization), y
  un contexto codificado en bytes que se proporciona a la función al momento de
  la invocación, junto con la respuesta a sanitizar. Si se proporciona, el
  propio canister que realiza la llamada debe exportar esta función.

### La respuesta

La respuesta devuelta (y la respuesta proporcionada a la función `transform`, si
se especifica) contiene los siguientes campos:

- `status`: El estado de la respuesta (por ejemplo, 200, 404).

- `headers`: Lista de encabezados de respuesta HTTP y sus valores
  correspondientes.

- `body`: El cuerpo de la respuesta.
