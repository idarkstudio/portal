# Convertirse en un emisor

<MarkdownChipRow labels={["Intermedio", "Tutorial"]} />

Un **emisor** es un servicio o aplicación que puede emitir una credencial
verificable (VC) a un usuario. En ICP, un emisor es una API expuesta que recibe
llamadas de un proveedor de identidad y no activa ningún flujo de trabajo por sí
mismo. Para convertirse en un emisor, tu canister debe implementar la API del
emisor según lo descrito en la  
[especificación de credenciales verificables](https://github.com/dfinity/internet-identity/blob/main/docs/vc-spec.md).

Los emisores reciben solicitudes de credenciales de partes dependientes a través
de un proveedor de identidad como Internet Identity (II). El usuario final debe
permitir o revocar la comunicación antes de que la credencial sea emitida.

En este tutorial, Internet Identity se utiliza como proveedor de identidad.

## Desarrollo de la API del emisor

La API del emisor consta de cuatro endpoints:

1. [`vc_consent_message`](https://github.com/dfinity/internet-identity/blob/main/docs/vc-spec.md#1-consent-message):  
   Responde con un mensaje de consentimiento para mostrar al usuario y obtener
   su aprobación para la emisión de la credencial.

2. [`derivation_origin`](https://github.com/dfinity/internet-identity/blob/main/docs/vc-spec.md#2-derivation-origin):  
   Devuelve la URL utilizada para derivar el principal del usuario para el
   emisor.

3. [`prepare_credential`](https://github.com/dfinity/internet-identity/blob/main/docs/vc-spec.md#3-prepare-credential):  
   Verifica la validez de la solicitud y prepara la credencial solicitada.

4. [`get_credential`](https://github.com/dfinity/internet-identity/blob/main/docs/vc-spec.md#4-get-credential):  
   Emite la credencial solicitada por el usuario.

### Paso 1: Obtener un mensaje de consentimiento (`vc_consent_message`)

Primero, el proveedor de identidad envía una solicitud al endpoint
`vc_consent_message` de la API del emisor para obtener el mensaje de
consentimiento que se mostrará al usuario.  
Un mensaje de consentimiento es un texto que el usuario debe aceptar para
confirmar la emisión de una credencial verificable.

```rust reference
https://github.com/dfinity/vc-playground/blob/b2f8cd5f5397b7b355b6503df5af3789834b79e9/issuer/src/main.rs#L677-L689
```

### Paso 2: Implementar un origen de derivación (`derivation_origin`)

Luego, el proveedor de identidad llama al endpoint `derivation_origin` del
emisor para obtener la URL que se usará como origen de derivación para el
principal del usuario.

Si el emisor no utiliza orígenes de derivación alternativos, debe devolver la
URL del canister:  
`https://<issuer-canister-id>.icp0.io`.

Si el emisor sí usa  
[orígenes de derivación alternativos](/docs/references/ii-spec#alternative-frontend-origins),  
el endpoint debe devolver el mismo valor de `derivationOrigin` que se usó al
iniciar sesión.

El valor devuelto está sujeto a verificación mediante
`.well-known/ii-alternative-origins`, como se describe en la  
[documentación sobre orígenes alternativos](/docs/references/ii-spec#alternative-frontend-origins).

```rust reference
https://github.com/dfinity/vc-playground/blob/b2f8cd5f5397b7b355b6503df5af3789834b79e9/issuer/src/main.rs#L659-L675
```

:::info

El origen de derivación devuelto está sujeto a verificación mediante
`.well-known/ii-alternative-origins`,  
como se describe en la  
[documentación de la funcionalidad](/docs/references/ii-spec#alternative-frontend-origins).

:::

### Paso 3: Preparar la credencial (`prepare_credential`)

Antes de emitir una credencial, la solicitud debe ser validada a través del
endpoint `prepare_credential`.  
El objetivo de este endpoint es verificar la solicitud y actualizar el
`certified_data` con un nuevo hash raíz  
que incluya la firma en la credencial.  
Si la solicitud es válida, la credencial se prepara.

Para más detalles sobre cómo validar la solicitud o generar la credencial,
revisa la  
[especificación de credenciales verificables](https://github.com/dfinity/internet-identity/blob/main/docs/vc-spec.md).

```rust reference
https://github.com/dfinity/vc-playground/blob/b2f8cd5f5397b7b355b6503df5af3789834b79e9/issuer/src/main.rs#L557-L585
```

:::info

El valor de `prepared_context` se usa para transferir información entre
`prepare_credential` y `get_credential`.  
El contenido de este campo lo define el emisor, ya que es el único que lo genera
y consume.

Por ejemplo, cuando se usan  
[firmas de canisters](/docs/references/ic-interface-spec#canister-signatures),  
`prepared_context` puede contener una credencial verificable con marca de tiempo
pero sin firmar.  
La firma del canister estará disponible en la llamada `get_credential`.

:::

### Paso 4: Emitir la credencial (`get_credential`)

Finalmente, el endpoint `get_credential` se usa para emitir la credencial
solicitada por el usuario.  
Se ejecutan nuevamente las validaciones realizadas en `prepare_credential`, con
una verificación adicional  
para confirmar que `prepared_context` es consistente con la solicitud original.

Si todo es válido, el emisor devuelve la credencial firmada en formato JWT.

Puedes ver una implementación en el  
[ejemplo del playground de credenciales verificables](

```rust reference
https://github.com/dfinity/vc-playground/blob/b2f8cd5f5397b7b355b6503df5af3789834b79e9/issuer/src/main.rs#L601-L649
```

## Convenciones recomendadas

Un emisor puede seguir la siguiente convención para facilitar la verificación de
las credenciales emitidas.

Dado un esquema de credencial como:

```json
"credentialSpec": {
    "credentialType": "SomeVerifiedProperty",
    "arguments": {
        "argument_1": "value_1",
        "another_argument": 42
    }
}
```

El JWT devuelto debe contener una propiedad con el valor de `credentialType`  
en `credentialSubject`, con las claves y valores de los argumentos de la
credencial:

```json
"SomeVerifiedProperty": {
    "argument_1": "value_1",
    "another_argument": 42
}
```

Por ejemplo, para una credencial `VerifiedAdult`, la especificación sería:

```json
"credentialSpec": {
    "credentialType": "VerifiedAdult",
    "arguments": {
        "minAge": 18
    }
}
```

Un emisor compatible emitiría una credencial con `credentialSubject`
estructurado así:

```json
"VerifiedAdult": {
    "minAge": 18
}
```
