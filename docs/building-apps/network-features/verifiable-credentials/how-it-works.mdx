# Cómo funcionan las credenciales verificables

<MarkdownChipRow labels={["Intermedio", "Concepto"]} />

Las credenciales verificables (VCs) en ICP dependen de Internet Identity (II),
que proporciona identidades distintas para cada dapp, preservando la no
vinculabilidad.

Una dapp que utiliza credenciales verificables no puede solicitar directamente
las credenciales del  
[emisor](/docs/building-apps/network-features/verifiable-credentials/overview#terminology).

Cuando una  
[parte dependiente](/docs/building-apps/network-features/verifiable-credentials/overview#terminology)  
quiere obtener una credencial de un emisor, debe solicitarla a través de un  
[proveedor de identidad](/docs/building-apps/network-features/verifiable-credentials/overview#terminology),  
como Internet Identity.

Internet Identity actúa como un enlace de comunicación entre la parte
dependiente y la API del emisor, conectándose con la API del emisor y
solicitando las credenciales del usuario. Una vez recibidas, las credenciales se
reenvían a la parte dependiente.

## Perspectiva del usuario

Desde la perspectiva del usuario, la parte dependiente abre una nueva ventana
para permitir la credencial, que se cierra cuando el proceso finaliza.

## Perspectiva del desarrollador

Desde la perspectiva del desarrollador, la interacción entre dapps utiliza
mensajes de ventana y llamadas a canisters:

1. El usuario accede a la parte dependiente e inicia el proceso para solicitar
   credenciales.  
   Esto puede ocurrir al iniciar sesión en una dapp o al acceder a un servicio
   privado que requiera autorización.

2. La parte dependiente inicia el flujo con Internet Identity (II):

   a. La parte dependiente abre una nueva ventana de II y espera un mensaje de
   ventana.

   b. El frontend de II envía un mensaje de ventana para iniciar la solicitud.

   c. La parte dependiente responde con la solicitud de credenciales y los datos
   del emisor.

3. El frontend de II llama al canister del emisor para recuperar el mensaje de
   consentimiento.

4. El frontend de II muestra al usuario todos los detalles:  
   la parte dependiente, el mensaje de consentimiento y la URL del emisor,  
   y luego espera la acción del usuario.

5. El usuario decide si permite o revoca la acción.

   a. Si se permite, el frontend de II solicita el alias de ID al backend de II.

6. El backend de II calcula un **alias de ID**, un identificador opaco que
   mantiene la no vinculabilidad entre el emisor y la parte dependiente.

7. El frontend de II solicita la credencial al emisor.

8. El emisor recibe la solicitud de credencial, valida la llamada de II y
   responde con una **presentación verificable**, si el usuario cumple con los
   requisitos de la credencial.

9. El frontend de II recibe la credencial del emisor y la reenvía a la parte
   dependiente, cerrando la ventana.

10. La parte dependiente verifica las credenciales.

## Prueba de credenciales verificables

Hay una **parte dependiente de demostración** desplegada en ICP disponible para
pruebas:  
[https://l7rua-raaaa-aaaap-ahh6a-cai.icp0.io/](https://l7rua-raaaa-aaaap-ahh6a-cai.icp0.io/).

Primero, debes iniciar sesión con un **proveedor de identidad**.  
Para evitar el uso de usuarios reales, se recomienda utilizar la instancia de
prueba de Internet Identity:  
[https://fgte5-ciaaa-aaaad-aaatq-cai.ic0.app/](https://fgte5-ciaaa-aaaad-aaatq-cai.ic0.app/).

También hay un **emisor de demostración** en ICP disponible para pruebas.  
Emitirá cualquier credencial solicitada, por lo que puedes usarlo para probar el
flujo:  
[https://qdiif-2iaaa-aaaap-ahjaq-cai](https://dashboard.internetcomputer.org/canister/qdiif-2iaaa-aaaap-ahjaq-cai).
