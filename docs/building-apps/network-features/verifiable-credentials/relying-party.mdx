# Convertirse en una parte confiable

<MarkdownChipRow labels={["Intermedio", "Tutorial"]} />

Una **parte confiable** es un servicio o aplicación que solicita las
credenciales verificables de un usuario a un [emisor](issuer.mdx). Las partes
confiables utilizan un **proveedor de identidad**, como Internet Identity, para
comunicarse con el emisor. Los proveedores de identidad deben admitir la
[especificación de credenciales verificables](https://github.com/dfinity/internet-identity/blob/main/docs/vc-spec.md).
La comunicación con el proveedor de identidad utiliza el canal de comunicación
[`window.postMessage()`](https://developer.mozilla.org/en-US/docs/Web/API/Window/postMessage).

La parte confiable debe realizar dos tareas principales:

- Solicitar las credenciales al emisor a través de un proveedor de identidad.
- Verificar las credenciales recibidas de un proveedor de identidad.

## Solicitar credenciales

Existen dos formas de solicitar credenciales:

- Usando el
  [SDK de JavaScript para credenciales verificables](https://www.npmjs.com/package/@dfinity/verifiable-credentials).

- Integrando manualmente un proveedor de identidad.

## SDK de JavaScript para credenciales verificables

Puedes solicitar credenciales a los emisores a través de proveedores de
identidad utilizando el paquete de NPM para partes confiables
[@dfinity/verifiable-credentials](https://www.npmjs.com/package/@dfinity/verifiable-credentials).
A continuación, se muestra un ejemplo:

```javascript reference
https://github.com/dfinity/verifiable-credentials-sdk/blob/8fe23fa830017d4d666d6fcdad38c1de7e99ca54/js-library/README.md#L50-73
```

[Aprende más sobre el SDK de JavaScript para VCs](https://github.com/dfinity/verifiable-credentials-sdk/tree/main/js-library).

Este código ejecuta los siguientes pasos:

- Abre una nueva ventana o pestaña con el proveedor de identidad (Internet
  Identity (II)).
- Espera un mensaje de ventana de II.
- Envía una solicitud a II a través del mensaje de ventana.
- Espera la respuesta de II.
- Llama a un callback `onSuccess` si el proceso fue exitoso, aunque eso no
  necesariamente significa que se recibió una credencial.
- Llama a un callback `onError` si ocurre un error técnico, si el usuario cierra
  la ventana de II o si II se agota el tiempo de espera.

Aprende más sobre [cómo funciona este flujo de trabajo](how-it-works.mdx).

## Integración manual

Para implementar un servicio de parte confiable, tu canister debe realizar tres
pasos:

1. Cargar un proveedor de identidad como Internet Identity: Abrir una ventana
   con un proveedor de identidad que actuará como puente de comunicación entre
   la parte confiable y el emisor.

2. Solicitar credenciales: Enviar una solicitud JSON RPC a la API del emisor
   para obtener las credenciales de un usuario.

3. Recibir una respuesta: Recibir un mensaje de éxito o error del proveedor de
   identidad.

### Paso 1: Cargar el proveedor de identidad en una nueva ventana

Primero, tu canister debe iniciar y cargar un proveedor de identidad (en este
caso, Internet Identity) en una nueva ventana con la ruta de URL `/vc-flow`.
Abrir esta ventana activará el proveedor de identidad, que enviará una
notificación a la interfaz
[`window.postMessage()`](https://developer.mozilla.org/en-US/docs/Web/API/Window/postMessage)
con el siguiente contenido JSON-RPC:

```json
{
  "jsonrpc": "2.0",
  "method": "vc-flow-ready"
}
```

El usuario interactuará con esta ventana para autenticarse con su Internet
Identity. Si el usuario cierra esta ventana o se agota el tiempo de espera, la
solicitud de credenciales se cerrará y se devolverá un error a la parte
confiable.

### Paso 2: Solicitar una credencial verificable

Una vez que el usuario haya iniciado sesión en Internet Identity y el servicio
esté listo, la parte confiable puede solicitar una credencial verificable para
el usuario enviando una solicitud JSON RPC a la API del emisor. El usuario debe
haber iniciado sesión en Internet Identity para que la solicitud sea exitosa. A
continuación, se muestra un ejemplo de una solicitud JSON RPC para solicitar una
credencial:

```json
{
  "id": 1,
  "jsonrpc": "2.0",
  "method": "request_credential",
  "params": {
    "issuer": {
      "origin": "https://employment-info.com",
      "canisterId": "rwlgt-iiaaa-aaaaa-aaaaa-cai"
    },
    "credentialSpec": {
      "credentialType": "VerifiedEmployee",
      "arguments": {
        "employerName": "XYZ Ltd."
      }
    },
    "credentialSubject": "2mdal-aedsb-hlpnv-qu3zl-ae6on-72bt5-fwha5-xzs74-5dkaz-dfywi-aqe"
  }
}
```

En esta solicitud, se deben establecer los siguientes parámetros:

- `method`: Debe ser `"request_credential"`, que es el método esperado.
- `params`: Parámetros de configuración para identificar qué credencial se está
  solicitando.
- `issuer`: Información para identificar a qué instancia de la API del emisor se
  enviará la solicitud.

  - `origin`: La URL de origen del emisor.
  - `canisterId`: El ID del canister de la API del emisor. Este campo es
    opcional.

- `credentialSpec`: La especificación de la credencial solicitada.

  - `credentialType`: El tipo de credencial solicitada.
  - `arguments`: Claves y valores específicos de la credencial. Este campo es
    opcional.

- `credentialSubject`: El principal del usuario que solicita la credencial.

- `derivationOrigin`: Un origen alternativo que se debe utilizar para la
  derivación del principal de la parte confiable en lugar del hostname del
  frontend. Debe coincidir con el `derivationOrigin` utilizado al iniciar sesión
  en la parte confiable.

Puedes encontrar más ejemplos en la
[especificación de credenciales verificables](https://github.com/dfinity/internet-identity/blob/main/docs/vc-spec.md#examples).

### Paso 3: Recibir una respuesta

Si la solicitud JSON RPC se envía y recibe correctamente por la API del emisor,
Internet Identity devolverá la siguiente respuesta JSON-RPC a la parte
confiable:

```json
{
  "id": 1,
  "jsonrpc": "2.0",
  "result": {
    "verifiablePresentation": "eyJQ..."
  }
}
```

En esta respuesta, `verifiablePresentation` es una presentación verificable (VP)
basada en JWT que contiene dos credenciales:

1. Una credencial verificable emitida por Internet Identity que relaciona el
   `credentialSubject` con el principal del usuario.
2. Una credencial verificable emitida por el emisor al principal del usuario.

La especificación garantiza que no haya vinculación directa entre la parte
confiable y el emisor. Por eso se necesitan dos credenciales. La primera
credencial prueba la relación entre el principal de la parte confiable y el
`id_alias` creado en el proveedor de identidad. La segunda credencial es la
credencial real asociada al `id_alias`.

Nota cómo el principal del emisor nunca aparece en las credenciales. En su
lugar, la parte confiable y el emisor solo conocen el `id_alias`. Por lo tanto,
este `id_alias` necesita la credencial para verificar el vínculo entre el
principal del usuario y el `id_alias`.

El orden de las credenciales en la VP debe coincidir con el orden mencionado, de
modo que la credencial del `id_alias` vinculada al principal de la parte
confiable debe aparecer primero.

[Consulta un ejemplo de una presentación verificable](https://www.w3.org/TR/vc-data-model/#example-jwt-payload-of-a-jwt-based-verifiable-presentation-non-normative)
como referencia.

La parte confiable no debe esperar recibir una respuesta inmediata, sino que
debe esperar uno de los siguientes eventos:

- II envía una respuesta JSON-RPC como se describió anteriormente.
- II envía una respuesta de error JSON-RPC como se describe a continuación.
- El usuario cierra la ventana de II. Esto debe tratarse como un error.

La parte confiable también puede cerrar la ventana de II después de un tiempo de
espera. En este caso, se debe notificar al usuario que la solicitud falló.

### Mensajes de error

Si el flujo de trabajo falla por cualquier motivo, Internet Identity devolverá
un error. El error no proporciona detalles sobre la causa de la falla para
proteger la privacidad.

Un ejemplo de error se muestra a continuación:

```json
{
  "id": 1,
  "jsonrpc": "2.0",
  "error": {
    "version": "1",
    "code": "UNKNOWN"
  }
}
```

## Verificación de credenciales

Para verificar las credenciales, la parte confiable debe validar el JWT recibido
del proveedor de identidad.

### Formato de las credenciales

La parte confiable recibe la credencial en formato JWT, que contiene un texto
largo dividido en partes comunes:

```
<header>.<payload>.
```

La funcionalidad de credenciales verificables de ICP se basa en el  
[modelo de datos de credenciales verificables de W3C](https://www.w3.org/TR/vc-data-model/).

:::info

No hay firma en esta primera presentación.

:::

Cuando se decodifica, el formato es el siguiente:

```json
{
  "iss": <issuer>,
  "vp": {
    "@context": "https://www.w3.org/2018/credentials/v1",
    "type": "VerifiablePresentation",
    "verifiableCredential": [
      "<header>.<payload>.<signature>",
      "<header>.<payload>.<signature>"
    ]
  }
}
```

El campo `verifiableCredential` dentro de `vp` debe contener dos credenciales
verificables en el orden especificado:

- Una credencial `id_alias` que vincula el sujeto efectivo de la credencial con
  un alias temporal. Esta credencial es firmada por el proveedor de identidad.

- La credencial real solicitada por el usuario. El sujeto de esta credencial es
  `id_alias`, y debe estar firmada por el emisor.

Cuando se decodifica la credencial `id_alias`, se obtiene la siguiente
información:

```json
{
  "exp": <expiration>,
  "iss": "https://identity.ic0.app/",
  "nbf": <not-before>,
  "jti": <jwt-id>,
  "sub": <relying-party-user-principal>,
  "vc": {
    "@context": "https://www.w3.org/2018/credentials/v1",
    "type": [
      "VerifiableCredential",
      "InternetIdentityIdAlias"
    ],
    "credentialSubject": {
      "InternetIdentityIdAlias": {
        "hasIdAlias": <id-alias>,
        "derivationOrigin": <user-principal-derivation-origin>
      }
    }
  }
}
```

Cuando se decodifica la credencial real, se obtiene la siguiente información:

```json
{
  "exp": <expiration>,
  "iss": <issuer>,
  "nbf": <not-before>,
  "jti": <jwt-id>,
  "sub": <did-id-alias>,
  "vc": {
    "@context": "https://www.w3.org/2018/credentials/v1",
    "type": [
      "VerifiableCredential",
      "<credential-type>"
    ],
    "credentialSubject": {
      "<credential-type>": {
        "<argument1-key>": "<argument1-value>",
        "<argument2-key>": "<argument2-value>",
        ...
      }
    }
  }
}
```

### Verificación criptográfica

Para verificar las dos firmas JWT, es necesario verificar la firma de `id_alias`
firmada por el proveedor de identidad y la firma de la credencial real firmada
por el emisor. Ambas se encuentran al decodificar el JWT recibido.

Estas firmas son [firmas de canister](/docs/references/glossary#c) y hay un
ejemplo sobre  
[cómo verificarlas en el repositorio de Internet Identity](https://github.com/dfinity/internet-identity/blob/2ae06956f9cabc048b8536b29b9f861092958515/src/vc_util/src/lib.rs#L193).

### Verificación semántica

La parte confiable debe verificar los siguientes datos:

- Desde el JWT de la credencial recibida:

  - El campo `iss` coincide con el ID del canister del proveedor de identidad.

  - La credencial inicial decodificada contiene dos credenciales dentro de
    `vp.verifiableCredential`:  
    primero la credencial `id_alias` y luego la credencial solicitada.

- Desde el JWT de `id_alias`:

  - El campo `iss` es el proveedor de identidad esperado.

  - El campo `sub` en `id_alias` contiene el principal del usuario en la parte
    confiable.

  - El tipo de credencial es `InternetIdentityIdAlias`.

  - El `derivationOrigin` coincide con el origen de derivación al iniciar sesión
    en la parte confiable.

- Desde el JWT de la credencial solicitada:

  - El tipo de credencial dentro de `vc.type` coincide con el primer campo en
    `vc.credentialSubject` y ambos son los mismos que se solicitaron.

  - Los argumentos dentro de `vc.credentialSubject.<credential-type>` son los
    esperados.

- Entre credenciales:

  - El campo `sub` de la credencial solicitada contiene el valor de `id_alias`
    dentro de `vc.credentialSubject.InternetIdentityIdAlias`.

Para aprender más sobre la verificación de credenciales, revisa el  
[código de la parte confiable en la demo](https://github.com/dfinity/vc-playground/blob/b2f8cd5f5397b7b355b6503df5af3789834b79e9/rp/src/main.rs#L262)  
y el asistente utilizado en el  
[repositorio de Internet Identity](https://github.com/dfinity/internet-identity/blob/fd38b48f9fdf9085b4903d865a1f5e79ad24f81a/src/vc_util/src/lib.rs#L319).
