# Tareas periódicas y temporizadores

<MarkdownChipRow labels={["Avanzado", "Concepto"]} />

A diferencia de otras blockchains, los canisters en ICP pueden ejecutar tareas
automáticamente después de un tiempo o intervalo específico.

Existen dos formas de programar la ejecución automática de un canister en ICP:

1. **Timers**: Llamadas al canister con una expiración única o periódica, con un
   tiempo mínimo o intervalo definido. Un canister puede implementar múltiples
   temporizadores. Cada temporizador recibe un ID único para identificarlo
   dentro del contexto del canister.
2. **Heartbeats**: Invocaciones periódicas heredadas con intervalos cercanos a
   la tasa de finalización de la blockchain (1s). Los heartbeats son compatibles
   en ICP por razones de retrocompatibilidad y algunos casos de uso especiales.
   **Para nuevos canisters, se recomienda usar temporizadores en lugar de
   heartbeats.**

## Temporizadores

Los temporizadores se implementan en dos niveles:

- **Implementación a nivel de protocolo:** El protocolo del Internet Computer
  admite un temporizador global minimalista por canister a través de la llamada
  API del sistema `ic0.global_timer_set()` y el manejador
  `canister_global_timer` (consulta la
  [especificación de interfaz de Internet Computer](/docs/references/ic-interface-spec#timer)).
- **Biblioteca de temporizadores del CDK:** Esta biblioteca envuelve la
  implementación minimalista del protocolo, permitiendo múltiples temporizadores
  y temporizadores periódicos. Los desarrolladores pueden usar la biblioteca de
  temporizadores del CDK para:

  - [Rust](https://crates.io/crates/ic-cdk-timers)
  - [Motoko](/docs/motoko/main/writing-motoko/timers)
  - [TypeScript (Azle)](https://demergent-labs.github.io/azle/timers.html)
  - [Python (Kybra)](https://demergent-labs.github.io/kybra/timers.html)

Internamente, las bibliotecas de temporizadores del CDK realizan lo siguiente:

1. Mantienen una lista global de todas las tareas periódicas dentro del
   canister.
2. Llaman a la API del sistema `ic0.global_timer_set()` para programar la
   siguiente tarea de la lista.
3. Implementan el método `canister_global_timer` con la siguiente lógica:
   - Para cada tarea expirada, el manejador inicia una llamada al propio
     canister para aislar las tareas entre sí y del código de la biblioteca.
     Nota: se aplican los
     [costos normales de llamadas entre canisters](/docs/building-apps/essentials/gas-cost).
   - Reprograman las tareas periódicas al final de su ejecución.
   - Llaman a la API del sistema `ic0.global_timer_set()` para programar la
     siguiente tarea.

La biblioteca no maneja las actualizaciones del canister. Es responsabilidad del
desarrollador serializar los temporizadores en el hook `canister_pre_upgrade` y
reactivarlos en `canister_post_upgrade` si es necesario.

El uso de los hooks `pre_upgrade` y `post_upgrade` no se recomienda, ya que es
propenso a errores y puede hacer que un canister quede inoperable. Como mejor
práctica, estos métodos deben evitarse si es posible.

Para una mejor compatibilidad con otras bibliotecas que usen temporizadores en
un mismo proyecto, se recomienda que los desarrolladores usen las bibliotecas de
temporizadores del CDK en lugar de la API a nivel de protocolo o los
\_heartbeats.

### Limitaciones de la biblioteca de temporizadores

A pesar de ser superior a los heartbeats\_, la biblioteca de temporizadores del
CDK tiene algunas limitaciones:

- **Actualizaciones del canister:** La biblioteca mantiene una lista global de
  tareas dentro de la memoria del canister. Durante una actualización del
  canister, se crea un nuevo estado de WebAssembly, desactivando todos los
  temporizadores y limpiando la lista de tareas. El desarrollador debe
  serializar los temporizadores en `canister_pre_upgrade` y reactivarlos en
  `canister_post_upgrade` si es necesario.
- **Llamadas al propio canister:** Para aislar las tareas entre sí y del código
  de programación, la biblioteca inicia una llamada al propio canister para
  ejecutar cada tarea. Esto implica lo siguiente:
  - Se aplican los
    [costos normales de llamadas entre canisters](/docs/building-apps/essentials/gas-cost)
    para ejecutar cada tarea. Sin embargo, los temporizadores siguen siendo
    [más eficientes en costos](https://github.com/dfinity/examples/tree/master/rust/periodic_tasks)
    que los heartbeats.
  - Las tareas se añaden al final de la cola de entrada del canister, lo que
    podría causar retrasos en la ejecución dependiendo de la carga del canister
    y la subred.
- **Cola de salida limitada:** Como la cola de salida de un canister está
  limitada en tamaño (actualmente 500 mensajes), esto impone un límite implícito
  en la cantidad de tareas que pueden programarse en una sola ronda.
- **Programación avanzada:** La biblioteca de temporizadores del CDK usa tiempo
  relativo para programar tareas. Para usar un tiempo absoluto, los
  desarrolladores deben calcular la duración entre el momento actual y el
  momento deseado o utilizar una biblioteca externa.

## Heartbeats

Cuando un canister exporta la función `canister_heartbeat`, esta se ejecuta en
cada intervalo de heartbeat de la subred (consulta la
[especificación de interfaz de Internet Computer](/docs/references/ic-interface-spec#heartbeat)).

La única forma de desactivar los heartbeats es actualizar el canister a una
versión que no exporte el método `canister_heartbeat`. Además, el intervalo del
heartbeat está definido por la implementación y no puede ajustarse.

Debido a estas limitaciones, en la mayoría de los casos, la biblioteca de
temporizadores del CDK para [Rust](https://crates.io/crates/ic-cdk-timers) o
[Motoko](/docs/motoko/main/writing-motoko/timers) es una mejor opción para
programar tareas periódicas.

## Preguntas frecuentes

- #### ¿Los temporizadores admiten Deterministic Time Slicing (DTS)?

  Sí, como la biblioteca de temporizadores del CDK inicia una llamada al propio
  canister para ejecutar cada tarea, se aplican los
  [límites de instrucciones de mensajes de actualización](/docs/building-apps/canister-management/resource-limits)
  con DTS habilitado.

- #### ¿Qué sucede si un manejador de temporizador usa `await`?

  Se aplican las reglas normales de `await`: cualquier nueva ejecución puede
  comenzar en el punto de espera, como un nuevo mensaje, otro manejador de
  temporizador o un heartbeat. Una vez que esa ejecución termina o alcanza su
  propio `await`, la ejecución del temporizador actual puede reanudarse.

- #### ¿Qué pasa si un temporizador periódico de 1s tarda 2s en ejecutarse?

  Si no hay puntos de `await` en el manejador del temporizador, este se
  reprogramará al final de la ejecución. Si hay `await`, el momento en que se
  reprograma depende de la implementación.
