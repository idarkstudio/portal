# Threshold Schnorr

<MarkdownChipRow labels={["Avanzado", "Concepto"]} />

Schnorr signatures son un tipo de esquema de firma digital ampliamente utilizado
en redes blockchain debido a su eficiencia, simplicidad y capacidad para admitir
firmas múltiples, firmas threshold y firmas agregadas. En ICP, las firmas
threshold Schnorr permiten a los canisters mantener una gama más amplia de
activos digitales y permiten integraciones directas con otras cadenas como
Solana.

Específicamente, las firmas threshold Schnorr en ICP proporcionan:

- Soporte para BIP-340, que es la variante de Schnorr utilizada en Bitcoin en
  Ordinals, Runes y BRC-20.

- Soporte para firmas Ed25519, que son utilizadas por cadenas como Solana,
  Cardano, Polkadot y Ripple. Ed25519 también es un esquema de firma popular
  fuera de blockchain para funciones Web2 como la firma de certificados X.509.

- Mayor rendimiento en la generación de firmas en comparación con firmas
  threshold ECDSA.

- Permite a los canisters obtener su propia clave pública Schnorr y dirección,
  desbloqueando la capacidad de derivar direcciones en otras cadenas, autorizar
  y enviar transacciones en dichas cadenas.

- Habilita la firma de mensajes arbitrarios mediante Schnorr.

## Firmar mensajes y transacciones

La API threshold Schnorr permite a los canisters firmar mensajes y transacciones
de manera segura sin que las claves privadas correspondientes existan. Cada
canister puede controlar un número ilimitado de claves especificando diferentes
`derivation_path`s y `key_id`s.

La API proporciona dos métodos:

- `sign_with_schnorr`: Se usa para firmar mensajes.

- `schnorr_public_key`: Se usa para obtener claves públicas.

Las firmas tendrán una codificación diferente según el algoritmo del `key_id`
proporcionado:

- `bip340secp256k1`: La firma se codificará de acuerdo con
  [BIP340](https://github.com/bitcoin/bips/blob/master/bip-0340.mediawiki),
  utilizando 64 bytes. Opcionalmente, el remitente puede proporcionar una raíz
  de árbol de Merkle taproot de 0 o 32 bytes como una modificación de clave
  según lo definido en
  [BIP341](https://github.com/bitcoin/bips/blob/master/bip-0341.mediawiki).

- `ed25519`: La firma se codificará de acuerdo con
  [RFC8032, 5.1.6 Sign](https://datatracker.ietf.org/doc/html/rfc8032#section-5.1.6),
  utilizando 64 bytes.

### Diferencia entre los endpoints de t-ECDSA y t-Schnorr

El endpoint `sign_with_schnorr` toma un mensaje completo como entrada en lugar
de un hash del mensaje, como lo hace el endpoint `sign_with_ecdsa`. Esto se debe
a que los mensajes de firma en BIP340 y Ed25519 se mezclan con otra información
durante la firma, lo que impide que un canister realice el hash del mensaje de
la misma manera que se hace en `sign_with_ecdsa`.

## Firmar mensajes

Los canisters pueden firmar mensajes con threshold Schnorr sin poseer
directamente las claves Schnorr. Cada clave se deriva de una clave maestra
mantenida por la subnet threshold Schnorr. Cuando un canister necesita una
firma, se envía una solicitud a la subnet threshold Schnorr, que calcula la
firma basándose en la clave raíz del canister solicitante y devuelve la firma.

Para firmar un mensaje, se usa el método `sign_with_schnorr`, que requiere
especificar el algoritmo Schnorr a utilizar: `bip340secp256k1` o `ed25519`.

El método `sign_with_schnorr` requiere que se adjunten cycles.
[Más información sobre los costos de threshold Schnorr](/docs/building-apps/essentials/gas-cost).

Para implementar código usando el método `sign_with_schnorr`, es necesario
especificar el `key_id` correcto para el entorno en el código fuente del
canister. Los siguientes `key_id`s son compatibles:

- `dfx_test_key`: Solo disponible en la réplica local iniciada por `dfx`.
- `test_key_1`: Clave de prueba disponible en el ICP mainnet.
- `key_1`: Clave de producción disponible en el ICP mainnet.

Opcionalmente, se puede proporcionar una raíz de árbol de Merkle taproot de 0 o
32 bytes como una modificación de clave para `bip340secp256k1`, según lo
definido en
[BIP341](https://github.com/bitcoin/bips/blob/master/bip-0341.mediawiki).

## Obtener claves públicas

Para obtener claves públicas, es necesario llamar al método `schnorr_public_key`
del canister de gestión de IC (`aaaaa-aa`). Se puede implementar la muestra
threshold Schnorr
[localmente](https://github.com/dfinity/examples/tree/master/motoko/threshold-schnorr)
y usar la Candid UI para llamar a este método, o se puede llamar
programáticamente usando Motoko o Rust.
