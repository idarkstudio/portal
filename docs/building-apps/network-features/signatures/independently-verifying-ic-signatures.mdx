# Verificación de firmas

<MarkdownChipRow labels={["Intermedio", "Firmas"]} />

Cada llamada en ICP requiere una `Firma` y un `Principal` criptográficos. Estos
generalmente se adjuntan en forma de una identidad que puede ser autenticada o
anónima. Una identidad incluye tanto la clave privada como la clave pública. La
clave pública se envía junto con la identidad codificada como un `Principal` y
se firma con una `Firma`. Los canisters utilizan esta identidad para responder a
la llamada y procesar flujos de autenticación. Cuando se envía una
[identidad delegada](#delegación-de-transacciones), se usa el mismo flujo de
trabajo, pero se incluye una cadena de delegación.

En algunos flujos de trabajo, puede ser beneficioso verificar la firma de la
identidad de forma independiente de la verificación automática de ICP como una
capa adicional de validación.

Cuando se realiza una llamada a un canister a través de la interfaz HTTPS, los
siguientes campos están presentes:

- `nonce` (`blob`, opcional): Datos generados aleatoriamente por el usuario; se
  pueden usar para crear llamadas distintas con los mismos campos.

- `ingress_expiry` (`nat`, requerido): Límite superior de validez de la llamada,
  expresado en nanosegundos, lo que previene ataques de repetición, ya que ICP
  rechazará llamadas cuya fecha de expiración haya pasado o sea demasiado
  futura.

- `sender` (`Principal`, requerido): La entidad que realiza la llamada.

La autenticación de la llamada incluye los siguientes campos:

- `content` (`record`): Contenido de la llamada.

- `sender_pubkey` (`blob`, opcional): Clave pública utilizada para autenticar la
  llamada.

- `sender_delegation` (`array de mapas`, opcional): Cadena de delegaciones
  comenzando con una firmada por `sender_pubkey` y terminando con la delegación
  a la clave relacionada con `sender_sig`; cada clave pública debe aparecer una
  sola vez.

- `sender_sig` (`blob`, opcional): Firma utilizada para autenticar la llamada.

La clave pública debe autenticar el `sender` si el `Principal` es un ID
autoautenticado derivado de esa clave pública.

Si el `sender` es un principal anónimo, los campos `sender_pubkey`, `sender_sig`
y `sender_delegation` deben omitirse. Si el `sender` está autenticado,
`sender_pubkey` y `sender_sig` deben estar presentes.

La autenticación de la llamada se basa en el contenido del `record`, lo que
permite que la firma se genere a partir del ID de la solicitud.

## Delegación de transacciones

La firma de una transacción puede ser delegada de una clave a otra. Si se usa
delegación, el campo `sender_delegation` contiene un array de delegaciones con
los siguientes campos:

`delegation` (`map`): Un mapa con los campos:

    - `pubkey` (`blob`): Clave pública.

    - `expiration` (`nat`): Expiración de la delegación, en nanosegundos, similar a
    `ingress_expiry`.

    - `targets` (`array` de `CanisterId`, opcional): Limita la delegación a
    solicitudes enviadas a los canisters especificados; máximo 1_000 canisters.

    - `senders` (`array` de `Principal`, opcional): Limita la delegación a
    solicitudes originadas por los `Principals` en la lista.

    - `signature` (`blob`): Firma del mapa de delegación de 32 bytes, usando los 27
    bytes `\x1Aic-request-auth-delegation` como separador de dominio.

La primera delegación en el array tiene una firma creada con la clave pública
correspondiente a `sender_pubkey`. Todas las delegaciones posteriores son
firmadas con la clave pública contenida en la delegación anterior.

El campo `sender_sig` se calcula concatenando el separador de dominio
`\x0Aic-request` (11 bytes) con el ID de solicitud de 32 bytes, usando la clave
privada correspondiente a la clave pública en la última delegación. Si no hay
delegaciones, se usa la clave pública de `sender_pubkey`. El campo de delegación
no debe contener más de 20 delegaciones.

## Verificación de firmas con un agente

Para verificar una firma con un agente, se requiere una identidad aceptada. Las
siguientes identidades y tipos de firma son compatibles:

- Firmas Ed25519 y ECDSA: Se admiten firmas simples para estos esquemas.

- Ed25519 o ECDSA en la curva P-256 (secp256r1): Se admite el uso de SHA-256
  como función hash o la curva Koblitz en secp256k1.

Cuando estas identidades se codifican como un `Principal`, el agente adjunta un
byte de sufijo que indica si la identidad es anónima o autoautenticada.

Las identidades autoautenticadas con Ed25519 o ECDSA tienen un sufijo `2`,
mientras que una identidad anónima tiene un solo byte `4`.

## Verificación de firmas con la biblioteca Rust `ic-validator-ingress-message`

La biblioteca Rust
[ic-validator-ingress-message](https://github.com/dfinity/ic/tree/master/rs/validator)
se desarrolló específicamente para validar firmas de mensajes. La clase
`IngressMessageVerifier` permite validar `InternetIdentityAuthResponse` junto
con la cadena de delegación.

Ejemplo de verificación de mensajes de entrada:

```rust
use ic_types::messages::{HttpCallContent, HttpRequest, SignedIngressContent};
use ic_types::Time;
use ic_validator_ingress_message::{RequestValidationError, HttpRequestVerifier, IngressMessageVerifier, TimeProvider};
fn anonymous_http_request_with_ingress_expiry(
    ingress_expiry: u64,
) -> HttpRequest<SignedIngressContent> {
    use ic_types::messages::Blob;
    use ic_types::messages::HttpCanisterUpdate;
    use ic_types::messages::HttpRequestEnvelope;
    HttpRequest::try_from(HttpRequestEnvelope::<HttpCallContent> {
        content: HttpCallContent::Call {
            update: HttpCanisterUpdate {
                canister_id: Blob(vec![42; 8]),
                method_name: "some_method".to_string(),
                arg: Blob(b"".to_vec()),
                sender: Blob(vec![0x04]),
                nonce: None,
                ingress_expiry,
            },
        },
        sender_pubkey: None,
        sender_sig: None,
        sender_delegation: None,
    })
        .expect("invalid http envelope")
}
let current_time = Time::from_nanos_since_unix_epoch(1_000);
let request = anonymous_http_request_with_ingress_expiry(current_time.as_nanos_since_unix_epoch());
let verifier = IngressMessageVerifier::default();

let result = verifier.validate_request(&request);

match result {
    Err(RequestValidationError::InvalidIngressExpiry(_)) => {}
     _ => panic!("unexpected result type {:?}", result)
}
```

[Consulta la implementación de la biblioteca](https://sourcegraph.com/github.com/dfinity/ic/-/blob/rs/validator/src/ingress_validation.rs?L605)
para más detalles.

## Verificación de firmas con `@dfinity/standalone-sig-verifier-web`

Existe una biblioteca `npm` como wrapper en JavaScript/TypeScript para la
biblioteca Rust
[`ic-standalone-sig-verifier`](https://github.com/dfinity/ic/tree/master/rs/crypto/standalone-sig-verifier).

Ejemplo de uso:

```javascript
import initSigVerifier, {
  verifyIcSignature,
} from "@dfinity/standalone-sig-verifier-web";

async function example(dataRaw, signatureRaw, derPublicKey, root_key) {
  // load wasm module
  await initSigVerifier();
  try {
    // call the signature verification wasm function
    verifyIcSignature(dataRaw, signatureRaw, derPublicKey, root_key);
    console.log("signature verified successfully");
  } catch (error) {
    // the library throws an error if the signature is invalid
    console.error("signature verification failed", error);
  }
}
```

:::caution

- Verificar firmas en el frontend es inseguro, ya que el código puede ser
  modificado por actores malintencionados. Se recomienda su uso en backends o
  entornos controlados.

- Esta biblioteca se compila desde la rama `master` de IC, lo que puede hacer
  que la API cambie.

- Su módulo Wasm es grande (400 KiB comprimido con gzip).

:::

[Descargar la biblioteca](https://www.npmjs.com/package/@dfinity/standalone-sig-verifier-web).
