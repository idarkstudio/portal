# Ejecución de mensajes

<MarkdownChipRow labels={["Principiante", "Concepto"]} />

Los mensajes de entrada (ingress) son solicitudes a los
<GlossaryTooltip>canisters</GlossaryTooltip> de ICP enviadas por entidades
externas como usuarios, generalmente a través de un
[agente](/docs/building-apps/developer-tools/dev-tools-overview/#agents), como
el [agente JavaScript de ICP](https://github.com/dfinity/agent-js/tree/main) que
se ejecuta en una aplicación web, o el
[agente Rust de ICP](https://github.com/dfinity/agent-rs/tree/main) en una
aplicación Rust.

Por ejemplo, puedes explorar qué mensajes de entrada se pueden enviar al ledger
de ckBTC navegando por su
[API usando el dashboard](https://dashboard.internetcomputer.org/canister/mxzaz-hqaaa-aaaar-qaada-cai).
La herramienta también te permite enviar mensajes, usando agent-js detrás de
escena.

Esta página cubre las APIs de mensajes de entrada de ICP. Si bien estas APIs
están definidas en detalle en la
[especificación de interfaz HTTPS](/docs/references/ic-interface-spec#http-interface),
aquí se ofrece una visión más general e intuitiva con especial enfoque en el
manejo de errores. Este aspecto es particularmente importante, ya que puede ser
complicado determinar si un mensaje de entrada se ha ejecutado correctamente.
Malinterpretar errores podría llevar a bugs como doble gasto.

ICP soporta varios tipos de llamadas, definidos en la
[especificación de interfaz HTTPS](/docs/references/ic-interface-spec#http-interface),
incluyendo llamadas de consulta (query) y actualización (update).

Más información sobre:

- [Llamadas de consulta](/docs/building-apps/interact-with-canisters/query-calls)
- [Llamadas de actualización](/docs/building-apps/interact-with-canisters/update-calls)
- [Tipos avanzados de llamadas](/docs/building-apps/interact-with-canisters/advanced-calls)

## Llamadas de consulta (Query)

Las consultas no modifican el estado de un canister y son respondidas y firmadas
por una sola réplica. Las respuestas se obtienen en milisegundos, pero
típicamente no están firmadas por la subred, lo que significa que una réplica o
nodo límite malicioso podría modificar arbitrariamente la respuesta.

Algunas aplicaciones pueden requerir mayor autenticidad en las respuestas. Por
ejemplo, si un dapp consulta la descripción de una propuesta sobre la cual el
usuario votará, podría no ser aceptable que el resultado pueda ser alterado, ya
que podría engañar a los usuarios para votar a favor del atacante. Como
alternativa, puedes realizar consultas como llamadas de actualización. Aunque es
fácil de implementar, esto hace las llamadas significativamente más lentas.

Otra alternativa es firmar los datos previamente y proveer
[_variables certificadas_](/docs/tutorials/developer-liftoff/level-3/3.3-certified-data/)
en las respuestas. Aunque este enfoque tiene mejor rendimiento que convertir
consultas en actualizaciones, puede ser complejo de implementar dependiendo del
caso de uso. Un ejemplo donde se usan variables certificadas es en la
[certificación de assets HTTP](/docs/building-apps/security/data-integrity-and-authenticity#use-http-asset-certification-and-avoid-serving-your-dapp-through-rawicp0io).
También se recomienda ver las
[mejores prácticas de seguridad](/docs/building-apps/security/data-integrity-and-authenticity#certified-variables)
para variables certificadas.

El manejo de errores en consultas es típicamente simple: ante un error, se puede
reintentar hasta recibir una respuesta exitosa.

[Más sobre llamadas de consulta](/docs/building-apps/interact-with-canisters/query-calls).

## Llamadas de actualización (Update)

Las actualizaciones pueden modificar el estado de un canister y por tanto deben
pasar por consenso, típicamente tomando 1-3 segundos. Devuelven respuestas
certificadas (firmadas por la subred), proporcionando autenticidad dentro de los
límites de corrupción de la subred.

Las llamadas de actualización pueden ser:

- [Síncronas](/docs/references/ic-interface-spec#http-sync-call-overview)
- [Asíncronas](/docs/references/ic-interface-spec#http-async-call-overview)

Una [llamada síncrona](/docs/references/ic-interface-spec#http-call) sigue el
patrón "llamar y esperar". En caso de éxito, mantiene la conexión HTTPS hasta
obtener una respuesta certificada, como se ilustra:

![Llamadas síncronas de entrada](_attachments/ingress_sync_call.png)

Comparado con el endpoint
[asíncrono](/docs/references/ic-interface-spec#http-async-call), donde se usa
[`read_state`](/docs/references/ic-interface-spec#http-read-state) para
consultar el estado de la solicitud y obtener la respuesta, el endpoint síncrono
elimina la necesidad de sondear la respuesta en caso de éxito.

Sin embargo, si no se produce una respuesta antes de un timeout específico, el
endpoint síncrono se comporta como el asíncrono: devuelve un código `202` y el
cliente debe usar
[`read_state`](/docs/references/ic-interface-spec#http-read-state) para obtener
el estado de la solicitud y eventualmente la respuesta, como se ilustra:

![Llamadas asíncronas de entrada](_attachments/ingress_async_call.png)

[Más sobre llamadas de actualización](/docs/building-apps/interact-with-canisters/update-calls).
