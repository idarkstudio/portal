# Redes de desarrollo personalizadas

<MarkdownChipRow labels={["Avanzado", "Desarrollo de canisters"]} />

ICP no tiene una red de prueba pública porque los

<GlossaryTooltip>canisters</GlossaryTooltip> desplegados en la mainnet pueden ser
actualizados y modificados. Además, los costos de despliegue son relativamente bajos
en comparación con otras blockchains.

ICP ofrece una red de [playground](https://m7sm4-2iaaa-aaaab-qabra-cai.ic0.app/)
como un entorno similar a un testnet para pruebas pequeñas y temporales. Los
canisters desplegados en el playground están sujetos a ciertas restricciones:

- Las instrucciones de transferencia de cycles son ignoradas sin notificación
  por el playground. Los canisters no pueden hacer llamadas que requieran que se
  adjunten cycles a la llamada.
- Los canisters pueden utilizar como máximo 1GiB de memoria.
- Los canisters pueden llamar al canister de gestión para administrarse a sí
  mismos sin ser el controlador.
- Los canisters desplegados caducan después de 20 minutos. Las actualizaciones a
  los canisters reinician este temporizador. Cuando el temporizador se agota, el
  canister será desinstalado.
- Los archivos Wasm no pueden ser comprimidos en formato gzip.
- Los archivos Wasm serán analizados para eliminar operaciones costosas o
  maliciosas.

Para desarrolladores avanzados y casos de uso que deseen usar un entorno de
testnet sin estas restricciones, existen dos opciones:

- **Playground personalizado**: Desplegar tu propia instancia del playground, lo
  que te permite controlar la configuración del playground, eliminar
  restricciones y modificar el grupo de canisters. Esta opción tiene un costo en
  cycles, ya que necesitarás financiar tu instancia del playground con cycles
  que serán utilizados para financiar los canisters desplegados en tu
  playground.

- **Red dfx personalizada**: Utiliza la característica de red con nombre de
  `dfx` para crear una red local que esté segmentada del resto de redes locales
  creadas por `dfx`.

## Playground personalizado

Utilizar tu propia instancia del playground permite una personalización extensa,
como:

- Habilitar control de acceso restringiendo el uso del playground solo a ciertos
  principios.

- Configurar plazos de tiempo más generosos para los canisters y la cantidad de
  cycles disponibles.

- Permitir algunas o todas las funciones que el playground público no permite,
  como enviar cycles a otros canisters.

Utilizar un playground personalizado también puede ayudar a simplificar el
desarrollo para equipos, ya que todo el equipo puede usar un playground
personalizado sin tener que gestionar balances de cycles individuales.

### Crear una instancia de playground personalizada

- #### Paso 1: [Instalar el playground de Motoko localmente](https://github.com/dfinity/motoko-playground/tree/main?tab=readme-ov-file#running-locally) siguiendo las instrucciones del repositorio del playground.

- #### Paso 2: Edita el archivo `service/pool/Main.mo` para cambiar la configuración del playground personalizado, como:

  - Añadir control de acceso como desees, por ejemplo, creando una lista de
    permisos (`allowList`) de principios que estén autorizados para usar el
    playground personalizado.

  - Configurar el
    [tiempo de vida del canister](https://github.com/dfinity/motoko-playground/blob/main/service/pool/Types.mo#L27).

  - Cambiar la
    [transformación de Wasm para adaptarla a tu configuración deseada](https://github.com/dfinity/motoko-playground/blob/main/service/pool/Main.mo#L348).
    En algunos casos, esto puede ser simplemente `wasm = args.wasm_module`, ya
    que si existe una `allowlist`, los principios permitidos para instalar
    canisters pueden ser confiables.

- #### Paso 3: Finalmente, define la red de playground local en el archivo `dfx.json` de tu proyecto.

En esta definición, deberás establecer el ID del canister de playground (el ID
del canister de `pool`) y definir el número de segundos antes de que un canister
sea devuelto al grupo, como se muestra a continuación:

```json title="dfx.json"
"<network name>": {
  "playground": {
    "playground_canister": "<canister pool id>",
    "timeout_seconds": <amount of seconds after which a canister is returned to the pool>
  },
  "providers": [
      "https://icp0.io"
  ]
}
```

Si el valor `<network name>` se establece como `playground`, entonces el comando
`dfx deploy --playground` desplegará en tu playground personalizado. De lo
contrario, el comando debe usar `--network <network name>`.

Esta definición de red también puede ir en el archivo `networks.json`, por lo
que se aplica a cada proyecto. Para ver dónde se encuentra el archivo
`networks.json`, utiliza el comando `dfx info networks-json-path`.

- #### Paso 4: Para usar el playground personalizado, [desplégalo localmente](https://github.com/dfinity/motoko-playground?tab=readme-ov-file#deploy-the-motoko-playground-to-your-local-replica-using-the-following-command).

## Red dfx personalizada

En una red personalizada, es posible ejecutar cualquier comando `dfx` que de
otra manera tomaría `--network ic`, pero usando `--network myNetwork` en su
lugar. `myNetwork` puede ser reemplazado por cualquier otro nombre, excepto los
tres reservados: `ic`, `local` y `playground`. Utilizar una red local
personalizada te permite probar integraciones con servicios y estimar los costos
de despliegue.

Las redes se definen de dos formas: asumidas y explícitamente configuradas.
`dfx` solo contiene la red `ic` como entorno asumido. Todas las demás redes
deben configurarse explícitamente en los archivos `networks.json` o `dfx.json`.
La sección de "networks" del archivo `dfx.json` debe contener al menos la red
local, que se elige por defecto si no se especifica ninguna otra red con la
opción `--network`.

Puedes crear una red personalizada con nombre para cada proyecto, creando así
una red sintética que esté segmentada de los otros proyectos probados localmente
en tu entorno, o puedes crear redes a nivel de sistema que puedan ser utilizadas
por cualquier proyecto.

### Crear una red personalizada de `dfx` a nivel de sistema

Las redes personalizadas pueden configurarse en el archivo `networks.json` para
`dfx`, el cual se puede encontrar utilizando el siguiente comando de `dfx`:

```bash
dfx info networks-json-path
```

Esto devolverá la ruta del archivo donde se encuentra el archivo `networks.json`
de tu sistema. Las redes definidas en este archivo pueden ser utilizadas por
cualquier proyecto en tu entorno local.

- #### Paso 1: Edita el archivo `networks.json` para definir una dirección de enlace como `localhost` o cualquier otro nombre de dominio.

Por ejemplo:

```json title="networks.json"
{
  "myNetwork1": {
    "bind": "localhost:4943",
    "replica": {
      "subnet_type": "application"
    }
  }
}
```

Para definir múltiples redes, utiliza múltiples definiciones en diferentes
nombres de dominio:

```json title="networks.json"
{
  "myNetwork1": {
    "bind": "localhost:4943",
    "replica": {
      "subnet_type": "application"
    }
  },
  "myNetwork2": {
    "bind": "127.0.0.1:4943",
    "replica": {
      "subnet_type": "application"
    }
  }
}
```

- #### Paso 2: Despliega en una de estas redes con `dfx deploy`:

```bash
dfx deploy --network myNetwork2
```

### Crear una red personalizada de `dfx` para un proyecto específico

Alternativamente, las redes también pueden definirse en el archivo `dfx.json` de
un proyecto. Solo los canisters definidos en ese archivo `dfx.json` podrán
desplegarse en esa red.

Para definir una red específica de proyecto, agrega una sección "networks" a tu
archivo `dfx.json`:

```json title="dfx.json"
"networks": {
    "myNetwork": {
      "providers": [
        "https://icp0.io"
      ],
      "type": "persistent"
    }
  }
```

Esta definición usa los siguientes parámetros:

- `providers`: El proveedor de la red; puede ser `localhost` o cualquier otro
  nombre de dominio. Los nombres de dominio deben ser URLs completas, como
  `https://domain.com`.
- `type`: El tipo de red, ya sea `ephemeral` o `persistent`. Las redes efímeras
  no retienen los mismos IDs para los canisters, mientras que las redes
  persistentes retendrán los mismos IDs para los canisters.

:::caution

Si estás usando una billetera de cycles, la billetera de cycles para cada red se
guarda por separado.

[Aprende más sobre las wallet de cycles](/docs/building-apps/canister-management/topping-up).

:::
