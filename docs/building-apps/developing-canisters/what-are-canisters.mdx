# ¿Qué son los canisters?

<MarkdownChipRow labels={["Principiante", "Desarrollando canisters"]} />

Los smart contracts que se ejecutan en ICP representan una evolución poderosa de
los contratos inteligentes tradicionales. En ICP, los smart contracts se llaman
**canisters** y son unidades computacionales que combinan código y datos. Los
canisters pueden contener cualquier tipo de código o datos, desde servir páginas
web hasta crear una aplicación de mensajería segura o implementar un intercambio
descentralizado de tokens.

<div class="text--center">
  <img src="/img/docs/canister.png" alt="Canister" width="400" />
</div>

Los canisters tienen propiedades especiales que permiten a los desarrolladores
construir servicios Web3 escalables. Para comprender mejor estas propiedades, es
necesario considerar los canisters desde diferentes perspectivas para obtener
una imagen completa de sus capacidades.

El Internet Computer Protocol (ICP) acepta y ejecuta canisters en formato
binario
[WebAssembly (Wasm)](https://internetcomputer.org/capabilities/webassembly). En
teoría, los desarrolladores podrían escribir canisters directamente en bytecode
Wasm. Sin embargo, dado que esto sería tedioso y consumiría mucho tiempo, la
práctica estándar es escribir el código en un lenguaje de alto nivel como
JavaScript/TypeScript, Motoko, Python o Rust, y luego compilarlo a Wasm.

La principal herramienta de desarrollo en el ecosistema de ICP es el **IC SDK**,
que incluye `dfx`. `dfx` es una herramienta de línea de comandos que asiste al
desarrollador en todo el proceso de desarrollo, desde la generación de claves
hasta la configuración de un nuevo proyecto, la compilación, el despliegue y la
administración de canisters.

</div>

Por defecto, `dfx` genera una estructura de proyecto que consiste en dos
canisters: el **frontend <GlossaryTooltip>canister</GlossaryTooltip>** y el
**backend <GlossaryTooltip>canister</GlossaryTooltip>**. El canister de frontend
contiene los archivos web como JavaScript, HTML, CSS e imágenes que se sirven al
navegador. La lógica del programa de la aplicación está definida en el canister
de backend.

:::info  
La configuración con un frontend y un backend canister es solo una convención.
Es posible escribir un único canister que contenga tanto la lógica del programa
como los archivos web.  
:::

Dado que los canisters pueden escribirse en diferentes lenguajes, es importante
que todos utilicen un formato binario común para aceptar argumentos y devolver
resultados. Este formato permite que los usuarios y canisters interactúen entre
sí, sin importar en qué lenguaje fueron escritos. En la programación
tradicional, este concepto es conocido como
[Application Binary Interface (ABI)](https://en.wikipedia.org/wiki/Application_binary_interface).
ICP tiene su propio lenguaje ABI llamado
**[Candid](/docs/building-apps/interact-with-canisters/candid/candid-concepts)**,
que es similar a JSON o Protobuf, pero adaptado a ICP.

Durante el proceso de compilación, `dfx` utiliza el ABI del backend para generar
automáticamente código JavaScript que facilita la interacción con el frontend.
Bajo el capó, este código usa una librería llamada
[ICP JavaScript agent](https://github.com/dfinity/agent-js/tree/main) para
codificar valores en Candid y hacer peticiones HTTP desde el navegador al
canister de backend. Esto es similar a `web3.js` en Ethereum.

El estándar [Wasm](https://webassembly.org/) solo define las instrucciones y la
memoria de la máquina virtual Wasm. La manera en que un programa Wasm interactúa
con otros programas y usuarios depende del host que lo ejecuta. En ICP, el host
proporciona un conjunto de funciones que el código Wasm puede usar para leer
argumentos, llamar a otros canisters y devolver resultados. Estas funciones
forman la **System API**. Sin embargo, los desarrolladores no deberían usar
directamente la System API, ya que es de bajo nivel y propensa a errores. En su
lugar, deben utilizar las librerías Canister Development Kit (CDK) específicas
para cada lenguaje, que actúan como wrappers de alto nivel sobre la System API.

## Ciclo de vida de un canister

### Escribir

ICP acepta y ejecuta código de <GlossaryTooltip>canister</GlossaryTooltip> en
formato binario WebAssembly (Wasm). Normalmente, los desarrolladores escriben
código en un lenguaje de alto nivel y luego lo compilan a un binario Wasm que
puede desplegarse en un canister.

[Aprende más sobre cómo escribir código para canisters](/docs/building-apps/developing-canisters/what-are-canisters).

### Crear

Un desarrollador puede crear un canister vacío en ICP usando el comando  
[`dfx canister create`](/docs/building-apps/developer-tools/dfx/dfx-canister#dfx-canister-create)
en la línea de comandos o la  
[<GlossaryTooltip>NNS</GlossaryTooltip> frontend dapp](/docs/building-apps/governing-apps/nns/overview)
en el navegador.  
El desarrollador puede establecer configuraciones iniciales y elegir el

<GlossaryTooltip>subnet</GlossaryTooltip> de destino. Una vez creado, el canister
recibe un ID y el desarrollador se convierte en su controlador.

[Aprende más sobre la creación de canisters](/docs/building-apps/developing-canisters/what-are-canisters).

<div class="text--center">
  <img src="/img/docs/create-canister.png" alt="Crear canister" width="600" />
</div>

### Compilar

Después de crear un canister vacío, su código debe ser compilado en un binario
Wasm utilizando  
[`dfx build`](/docs/building-apps/developer-tools/dfx/dfx-build).

[Aprende más sobre la compilación de código en Wasm](/docs/building-apps/developing-canisters/compile).

### Instalar

Después de escribir, crear y compilar el código, el siguiente paso es instalarlo
en el canister.  
Esto se hace llamando al endpoint `install_code` del canister de gestión,
pasando el ID del canister y el binario Wasm.  
El comando  
[`dfx canister install`](/docs/building-apps/developer-tools/dfx/dfx-canister#dfx-canister-install)  
se usa para hacer esta llamada.

<div class="text--center">
  <img
    src="/img/docs/install-canister.png"
    alt="Instalar canister"
    width="600"
  />
</div>

### Desplegar

Una vez que un canister tiene instalado un binario Wasm, puede desplegarse en
entornos locales, de prueba o en mainnet con  
[`dfx deploy`](/docs/building-apps/developer-tools/dfx/dfx-deploy).

[Aprende más sobre el despliegue de canisters](/docs/building-apps/developing-canisters/deploy).

### Llamar

Después del despliegue, el canister acepta y procesa mensajes (llamadas) de
usuarios y otros canisters.  
Solo se pueden llamar los endpoints públicos del canister, que corresponden a
funciones Wasm con las anotaciones  
`canister_update` o `canister_query`.

<div class="text--center">
  <img src="/img/docs/call-canister.png" alt="Llamar canister" width="600" />
</div>

### Mantener

Los controladores del canister pueden realizar ciertas operaciones como
actualizar su código.  
En las primeras etapas, el canister suele estar controlado por su
desarrollador,  
pero a medida que madura, el control puede transferirse a una DAO para mayor
seguridad y confianza.
[Aprende más sobre la gestión de canisters](/docs/building-apps/canister-management/control).

<div class="text--center">
  <img
    src="/img/docs/manage-canister.png"
    alt="Administrar canister"
    width="600"
  />
</div>

Dado que ICP utiliza un modelo de gas inverso, el canister paga por su
ejecución, almacenamiento y otras operaciones con **cycles**. Esto significa que
los controladores y/o usuarios del canister deben asegurarse de que el canister
no se quede sin cycles. Si el canister se queda sin cycles, se desinstalará
eliminando su binario Wasm y su almacenamiento.

Si el canister ya no se utiliza o no es necesario, un controlador del canister
puede eliminarlo. ICP garantiza que el ID del canister no se reutilizará para
otro canister.
