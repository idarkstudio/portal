# Rastreo de errores en canisters

<MarkdownChipRow labels={["Intermedio", "Tutorial", "Motoko", "Rust"]} />

Cuando los canisters generan un error, ICP reporta un rastreo de pila que
contiene los nombres de las funciones en la pila de llamadas. Estos rastreos se
agregan a los registros del canister y, si el llamador tiene
[acceso a los registros del canister](/docs/building-apps/canister-management/logs#log-visibility),
también se incluirán en la respuesta del mensaje de error.

Por ejemplo, si el siguiente canister en Rust accidentalmente intenta acceder
fuera de los límites de la memoria estable:

```rust
#[update]
fn outer() {
	inner();
}

fn inner() {
	inner_2();
}

fn inner_2() {
	ic_cdk::api::stable::stable_write(0xdeadbeef, b"foo")
}
```

El error resultante de acceso fuera de los límites de la memoria estable también
contendrá el siguiente rastreo de pila, el cual puede ayudar a determinar que el
error ocurre en `inner_2`, alcanzado a través de `outer` y `inner`:

```
Canister Backtrace:
ic0::ic0::stable64_write
_wasm_backtrace_canister::inner_2
_wasm_backtrace_canister::inner
_wasm_backtrace_canister::outer
```

## Verificación de soporte para rastreo de errores en canisters

El soporte para rastreo de errores depende de que los nombres de las funciones
se almacenen en la sección
[`name`](https://webassembly.github.io/spec/core/appendix/custom.html#name-section)
del módulo Wasm del canister. Cualquier canister construido con `dfx` versión
`>= 0.24.2` debería tener soporte automático para rastreos de errores. Si estás
modificando manualmente el código Wasm de tu canister con los comandos
`ic-wasm shrink`, `ic-wasm optimize` o `ic-wasm metadata`, necesitarás agregar
el flag `--keep-name-section` para asegurarte de que el canister pueda seguir
proporcionando rastreos de errores. Esto requiere la versión `ic-wasm`
`>= 0.8.6`.
