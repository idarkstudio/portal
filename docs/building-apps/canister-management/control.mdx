# Controladores de Canister

<MarkdownChipRow labels={["Principiante", "Administración"]} />

Un <GlossaryTooltip>canister</GlossaryTooltip> es administrado por una lista de
controladores. Un controlador está definido por un
<GlossaryTooltip>principal</GlossaryTooltip>, el cual puede ser
auto-autenticable (por ejemplo, una identidad de desarrollador de `dfx`) o
incluso otro canister. Un canister puede tener múltiples controladores, donde
cada uno tiene los mismos derechos administrativos, o puede no tener ningún
controlador, en cuyo caso el canister se vuelve inmutable (blackholed) y no se
puede actualizar ni eliminar.

Cuando se crea un canister, la lista de controladores por defecto contiene la
identidad del desarrollador que lo creó. Se pueden especificar controladores
adicionales durante la creación del canister o agregarlos más adelante.

Para especificar un controlador diferente al momento de crear el canister, se
puede usar el comando  
[`dfx canister create --controller <controller>`](/docs/building-apps/developer-tools/dfx/dfx-canister#dfx-canister-create).

Para actualizar la lista de controladores de un canister después de su creación,
se puede utilizar el comando  
[`dfx canister update-settings`](/docs/building-apps/developer-tools/dfx/dfx-canister#dfx-canister-update-settings)  
junto con los flags `--add-controller <controller>` o
`--remove-controller <controller>` para agregar o eliminar controladores,
respectivamente.

## Acciones disponibles solo para controladores

- Detener e iniciar el canister.
- Instalar código en el canister.
- Actualizar el canister.
- Obtener el estado del canister, que incluye su balance de
  <GlossaryTooltip>cycles</GlossaryTooltip>, uso de memoria y lista de
  controladores.
- Eliminar el canister.
- Actualizar configuraciones como el umbral de congelación, asignación de
  recursos y controladores.

## Modelos comunes de control

### Desarrollador o equipo de desarrolladores

Un canister es controlado por un solo desarrollador o un equipo de
desarrolladores. Cada desarrollador tiene los mismos derechos administrativos
sobre el canister. Este es el modelo de control más común en las primeras etapas
de desarrollo. Se puede aumentar la seguridad utilizando un módulo de seguridad
de hardware (HSM) para almacenar la clave privada de la identidad del
desarrollador.

### MultiFirma (MultiSig)

Un canister es controlado por un canister de múltiples firmas. Este canister
está administrado por una lista de desarrolladores y requiere un número mínimo
de firmas para realizar acciones administrativas. Este modelo es más seguro que
el de un solo desarrollador, ya que se necesita consenso entre varios
desarrolladores antes de ejecutar una acción.

Un canister que se puede utilizar para este propósito es el  
[Threshold canister](https://github.com/dfinity/threshold).

### Launchtrail

El [canister Launchtrail](https://github.com/spinner-cash/launchtrail) permite
programar la actualización de un canister en un momento futuro, dando al público
tiempo suficiente para revisar los cambios propuestos. Además, mantiene un
registro completo de todas las acciones y sus resultados. Para garantizar su
integridad, el propio canister Launchtrail debería ser inmutable y no tener un
controlador.

### Organización Autónoma Descentralizada (DAO)

Un canister puede ser controlado por una DAO, donde todas las actualizaciones y
acciones administrativas son decididas mediante votación de los miembros de la
DAO. El modelo de DAO más común para aplicaciones en Internet Computer es el  
[Service Nervous System (SNS)](/docs/building-apps/governing-apps/index.mdx).

Los canisters del sistema en ICP son controlados por el canister raíz del
Network Nervous System (NNS), lo que permite su administración a través de
propuestas en el NNS.

### Sin controlador

Un canister sin controlador es completamente inmutable. En ICP, este modelo se
conoce como un canister "blackholed". Es similar al modelo utilizado por los
contratos inteligentes en Ethereum.
