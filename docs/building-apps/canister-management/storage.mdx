# Almacenamiento de Canisters

<MarkdownChipRow labels={["Principiante", "Gestión"]} />

Cuando desarrollas proyectos en ICP, existen dos formas principales de
almacenamiento de datos que tus **canisters** pueden utilizar. El primer tipo de
almacenamiento es la **memoria heap** del canister, a veces conocida como la
_memoria principal_ del canister. La memoria heap es **temporal**, y cualquier
dato almacenado en ella se elimina siempre que el canister sea reinstalado o
actualizado.

El segundo tipo de almacenamiento disponible para un canister es la **memoria
estable**. La memoria estable es una característica única de ICP que define un
almacenamiento de datos separado de la memoria regular del heap del canister. Es
un tipo de almacenamiento secundario que se puede utilizar para almacenar datos
a largo plazo, ya que todos los datos almacenados en la memoria estable
persistirán a través de todos los procesos del canister.

## Memoria Heap

La memoria heap se refiere a la memoria regular de un canister en Wasm. No
persiste y no almacena datos a largo plazo. La memoria heap de un canister se
borra siempre que el canister sea reinstalado o actualizado. Esta memoria se
utiliza por defecto para almacenar cosas como valores de variables, el resultado
de una función ejecutada u otros argumentos pasados al canister.

La memoria heap tiene un límite máximo de 4GiB de datos.

## Memoria Estable

La memoria estable es una característica única del Protocolo Internet Computer
que proporciona una opción de almacenamiento de datos persistente a largo plazo,
separada de la memoria heap del canister. A menos que un canister sea
reinstalado o sus datos sean borrados debido a la agotación de ciclos, los datos
almacenados en la memoria estable no se eliminan ni se retiran. La memoria
estable se conserva durante todo el proceso, mientras que cualquier otro estado
de WebAssembly se descarta.

Para utilizar memoria estable, debes anticipar qué partes de los datos del
canister deseas que persistan a través de las actualizaciones indicando esto en
el código del canister. Más información sobre esto se encuentra en la sección
siguiente,
[Manejo de almacenamiento en diferentes lenguajes](#manejo-de-almacenamiento-en-diferentes-lenguajes).

Por defecto, la memoria estable de un canister está vacía. El límite máximo de
almacenamiento para la memoria estable es de 500GiB, si la **subred** en la que
el canister está desplegado lo permite. Si un canister utiliza más de 500GiB de
memoria estable, el canister atrapará el error y se volverá irrecuperable.

## Costo de Almacenamiento

El costo de almacenamiento se calcula en base a los GiB de almacenamiento
utilizados por un canister por segundo, costando `127_000` **ciclos** en una
subred de 13 nodos y `127_000 / 13 * 34` ciclos en una subred con 34 nodos. En
USD, esto equivale a aproximadamente $0.43 y $1.13, respectivamente, por
almacenar 1 GiB de datos durante un mes de 30 días. El costo es el mismo, ya sea
que el canister utilice memoria heap, memoria estable o ambas.

[Aprende más sobre los costos de almacenamiento](/docs/building-apps/essentials/gas-cost).

## Manejo de Almacenamiento en Diferentes Lenguajes

### Manejo de Almacenamiento en Motoko

En los canisters de Motoko, la memoria estable se puede utilizar a través de las
características de **almacenamiento estable** y **variables estables**. El
almacenamiento estable es un término específico de Motoko que se refiere a la
implementación de la memoria estable de Motoko para persistir datos a través de
actualizaciones del canister. Las variables estables son variables definidas en
Motoko que utilizan la palabra clave `stable` para indicar que el valor de la
variable debe persistir a través de las actualizaciones del canister, como se
muestra a continuación:

```motoko
actor Counter {
  stable var value = 0;
  public func inc() : async Nat {
    value += 1;
    return value;
  };
}
```

Para utilizar memoria estable al actualizar un canister de Motoko, el siguiente
flujo de trabajo se utiliza:

- El canister debe detenerse.
- La memoria heap del canister se descarta y se inicializa una nueva versión del
  módulo Wasm del canister. Los datos almacenados en la memoria estable se hacen
  disponibles para el nuevo módulo Wasm.
- El nuevo código del canister se instala usando la bandera `--mode upgrade`.
- El canister se reinicia y ahora ejecuta el código actualizado.
- Las variables estables se recargan. Los bytes de memoria estable que almacenan
  esas variables se sobrescriben con ceros para minimizar los costos de memoria
  estable del canister.

#### Recolección de Basura

Un proceso de recolección de basura es una utilidad automática que se utiliza
para gestionar la cantidad de memoria utilizada. Para la memoria heap, la
recolección de basura se utiliza para eliminar objetos no referenciados o
muertos con el fin de liberar memoria heap previamente asignada.

En Motoko, el proceso de recolección de basura por defecto utiliza un enfoque de
copiado, que depende del tamaño de la memoria heap utilizada en ese momento. En
contraste, se puede seleccionar un colector de basura adicional que utiliza un
enfoque de marcado, basado en la cantidad de memoria heap libre. Estos métodos
de recolección de basura se activan cuando se realizan suficientes cambios en la
memoria heap desde la última ronda de recolección de basura. La recolección de
basura puede forzarse para que se ejecute después de cada mensaje utilizando la
bandera `--force-gc` en el archivo `dfx.json` del proyecto:

```json
"defaults": {
  "build": {
    "packtool": "",
    "args": "--force-gc"
  }
},
```

Ambos recolectores de basura, sin embargo, no pueden recolectar toda la memoria
heap debido al límite de instrucciones por mensaje en ICP. Dado que estos
recolectores no pueden recolectar toda la memoria heap, los canisters no se
benefician completamente del uso de todo el espacio de memoria de 4GiB, ya que
debe quedar algo de espacio de memoria heap libre para que el recolector de
basura opere.

Actualmente está disponible un proceso de recolección de basura incremental en
fase beta, el cual utiliza mensajes incrementales para distribuir el trabajo de
recolección de basura a través de varios mensajes cuando sea necesario. Este
tipo de recolección de basura permite asignar hasta 3 veces más espacio en
memoria heap después de que se haya ejecutado, consumiendo menos ciclos en
promedio. Con este servicio de recolección de basura, los canisters pueden
beneficiarse de utilizar toda la memoria heap de 4GiB, ya que pueden recolectar
toda la memoria heap.

El colector de basura incremental se puede utilizar especificando la bandera
`--incremental-gc` en el archivo `dfx.json` del proyecto, como sigue:

```json
{
  "canisters": {
    "my_dapp": {
      "main": "src/my-dapp.mo",
      "type": "motoko",
      "args": "--incremental-gc"
    }
  }
}
```

:::info

Este colector de basura aún está en fase beta y debe ser utilizado con
precaución.

:::

[Aprende más sobre el colector de basura incremental](https://github.com/dfinity/motoko/pull/3837).

### Manejo de Almacenamiento en Rust

Para utilizar memoria estable en canisters escritos en Rust, se puede usar la
crate [ic-stable-structures](https://github.com/dfinity/stable-structures). Se
recomienda revisar la documentación de estas crates para aprender más o
[revisar el tutorial sobre la crate de estructuras estables](https://mmapped.blog/posts/14-stable-structures.html).

Como buena práctica, la memoria estable debe versionarse, ya que el mecanismo de
decodificación de memoria estable puede necesitar adivinar el formato de los
datos en situaciones donde el formato de serialización o el diseño de datos
estables de un canister cambian drásticamente. Esto puede ser tan simple como
declarar que el primer byte de la memoria estable del canister se utilizará para
representar el número de versión.

Para utilizar memoria estable al actualizar un canister de Rust, el siguiente
flujo de trabajo se utiliza:

- El canister debe detenerse.
- La memoria heap del canister se descarta y se inicializa una nueva versión del
  módulo Wasm del canister. Los datos almacenados en la memoria estable se hacen
  disponibles para el nuevo módulo Wasm.
- El nuevo código del canister se instala usando la bandera `--mode upgrade`.
- El canister se reinicia y ahora ejecuta el código actualizado. La función
  `init` no se ejecuta.
